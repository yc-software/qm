# Discord surface (Gateway)

The surface runs in-process with the agent core over an outbound Gateway WebSocket (`discord.js`): no public URL or ingress. It serves DMs and guild channels. `@mention` the bot in a configured channel to open a thread; follow-ups in the thread need no mention.

## Setup

The admin Discord installation record is the only config channel. There are no `DISCORD_*` environment variables.

1. Developer Portal: create an application, copy the Application ID, reset and copy the bot token.
2. Bot, Privileged Gateway Intents: turn on **Server Members** (member cache for reader checks) and **Message Content** (guild text and thread follow-ups).
3. OAuth2 URL Generator: scope `bot` only; permissions View Channels, Send Messages, Send Messages in Threads, Create Public Threads, Read Message History, Attach Files, Add Reactions.
4. OAuth2 Redirects: add the redirect URI shown in the admin card (needed for "Connect Discord" in user settings).
5. QM web app, Admin, Integrations, Discord: enter the bot token, OAuth2 client secret, server ids and internal role ids, then Save. The runtime activates within seconds. Disconnect removes the record and stops the surface.

Users approving by DM buttons must allow DMs from server members; with DMs closed the thread fallback link still works.

## Reader audience and private threads

- Guest guard: if any member who can view a guild channel is an external guest, channel turns are refused and outbound deliveries dropped.
- While member hydration is in progress (startup, reconnect), readers cannot be verified: mentions get a retry notice and queued deliveries wait.
- Audience cap: more than 500 eligible viewers counts as guest-accessible.
- **Private threads**: a private thread is its own scope (`channel:<thread id>`), not its parent's; its readers are the parent's viewers who are thread members (fetched from Discord per turn) or hold `ManageThreads`. A failed member fetch means readers are unknown (retry later); a deleted thread is refused. Public threads keep the parent channel's scope and readers. Its config layers (instructions, command policy, security and sharing posture, approval grant modes, egress) come from the parent channel, so the parent's policy still applies inside it; memory, files, readers, sessions and entitlements stay under the thread's own scope. The thread-to-parent link is recorded server-side from Discord's own data, and no client field can set or change it. Every resolution of a private thread by the Discord surface links it first: its creation event, the active-thread scan on gateway ready, a turn in it, and every channel fetch or cache lookup the bot makes (channel lookups for reach and triggers, visibility and reader checks, history reads, sends). A failed link write fails closed: the lookup reports the channel as not visible yet (retry), and no turn runs there on an unlinked thread; a mention only gets the fixed retry notice above, which reads no config or content. If the thread scope already holds config layers of its own, the link is refused with a typed error and the lookup fails closed like any failed link write, until an admin clears that configuration. Every config read, including triggers (cron, loop, monitor) homed in the thread, the admin console and the control service, follows that link, and a config write to the thread's scope is refused with an error that names the parent, so a private thread is never configured weaker than its parent. Proof boundary: a private thread the Discord surface has not resolved yet (for example an archived one nobody has named) has no link, and nothing can act in it before then, because shared-scope entitlement for a Discord id comes only from a Discord lookup (which links it) or the channel directory (which the Discord surface never populates); clearing a thread's own security posture, command policy, approval modes, SOUL or egress has no admin control yet; other per-scope settings (for example the base model) are not inherited; content stored under the parent scope is not visible inside the thread; and a member added to the thread between the fetch and the reply is not seen until the next turn.

## Known limits

- **Command cap**: the card summary is clipped to 400 characters before the fit check (see Interactive approval buttons); the card links to the web app only when the public URL is http(s).
- **Route per delivery**: the Slack-or-Discord route for a person-addressed notice is chosen at each delivery, so if a person links or unlinks Slack between a post and a later edit or delete of it, the edit may target the other surface and is reported undeliverable.
- **Message limit**: Discord enforces a 2,000-character limit. Replies exceeding this limit are split along paragraph, line, and word boundaries. Markdown code fences are cleanly closed before a cut and reopened in the next chunk.
- **Emoji reactions**: custom guild emoji need their id (`<:name:id>`); a bare custom `:name:` cannot be resolved and is reported undeliverable.
- **Cross-channel reach ceilings**: reach resolves a channel only when the Slack directory has no match for the name, so a Slack channel with the same name wins. Discord names are matched against the bot's cached channels and threads of the configured servers; an id that is not cached is fetched, so an archived thread is reachable by id; a name shared by several channels is refused with the candidate ids. Reach cannot start a new thread, and `threadTs` is Slack-only. Reading a named Discord channel through `/v1/surface-context` still resolves names through the Slack directory only.
- **Directory sync ceilings**: internal guild members (per section 6, bots and guests excluded) are pushed to the org directory as `discord:<user id>` with display name and avatar, from the hydrated member cache only (no extra gateway requests), after every full hydration and then every 5 minutes, single-flight and under the `discord:directory-sync` lease. A Discord member whose Discord id is linked to a QM principal that already has its own Slack directory entry is not listed again, so they resolve under that entry (and its Slack avatar); principals that only exist through sign-in or an email allow-list keep their Discord row. A name that matches both a Slack member and a Discord member is ambiguous rather than resolved to either (for example a Discord nickname equal to the start of a Slack display name), except that a Slack member whose name matches exactly wins over Discord members whose names only start with or contain it; an exact id still wins. The Discord rows are a separate slice of the directory: a Slack directory push never removes or deactivates them and a Discord push never touches Slack rows. A member who leaves the guild drops out of the directory at the next sync but is not deactivated. Channels, rosters and group DMs are not synced from Discord, and a user who is in no configured guild is never listed.
- **Inbox**: Discord asks and mentions do not create Inbox items. Inbox items come from the Inbox loop reading a user's own connected Slack or Gmail, and the Slack events only refresh items already on a ledger; Discord has no per-user connector, no send-as-user action and no item source adapter.
- **Core ambient triggers**: Core ambient proactive wakeups are disabled for Discord; ambient responses occur only within staked threads.
- **Snowflake comparison**: `read_thread`, `whats_new` and catch-up order ids by length then value, which is correct for mixed 18/19-digit ids. The surface cache's stored last id per channel is still compared as text, so a channel that mixes 18- and 19-digit ids can start its catch-up from an older id than necessary (harmless: duplicates are dropped by the replay key).
- **Unprompted turns stay quiet**: ambient thread turns and reaction turns that are refused, fail, or need approval only log. In DMs they post no "Working…" message; a real reply is still posted.
- **Reaction directives**: the `[[react: ...]]` reply-text directive is not parsed on Discord. Guild turns react through the `react` tool; DM turns can only react through the detect-time outcome.
- **Message-id tokens**: `~id` tokens are decoded for reactions and the `whats_new` `since` cursor, not for edit or delete references.
- **Revisions in DMs**: DM messages are not mirrored, so DM edits and deletes are not tracked. Guild deletes of messages no longer cached are mirrored as tombstones without checking relevance.
- **Acknowledgement emoji**: picked at random from the default acknowledgement set (no model pick), guild turns only; DMs already show the Working status message.
- **Reaction threads**: a thread opened for a reaction is deleted when the turn ends silent or react-only, (also when it ends refused or failed, since unprompted turns stay quiet; a turn that ends pending approval keeps it, because the approved reply is delivered there later), but only if it holds nothing but the system thread-starter message and no other reaction turn has resolved it. Once another turn resolves a thread, this process never deletes it. The deletion applies only when the turn ended with a known non-reply status or a finished run with no stored result; a turn whose run is still live (for example a wait that gave up) never deletes it.
- **Catch-up ceilings**: the cursor is the in-process `seen` id when present, else the mirrored watermark, so DMs are never caught up (they are not mirrored, so no starting id exists) and a never-mirrored channel is covered only after it has live traffic in this process; at most the 500 most recently updated Discord containers are tracked; one page per channel per run; a mention mirrored just before a crash is not re-run when the mirror already advanced past it; messages older than 6 hours are not answered.
- **Half-streamed replies after a restart**: the stream status message is finalized in place by the recovered delivery (its id is saved on the run), so a single-message reply is neither duplicated nor lost. A reply that spilled into extra chunks or files, or an unprompted reply (no status message), can post again if the process died between sending and acknowledging; there is no verify-first step like Slack's. Chunk progress is not recorded either: a queued delivery whose later chunk fails (for example a transient Discord error) is retried from its first chunk, so the chunks already sent post again.
- **One installation per org**: Only one Discord application can be configured per QM organization.
