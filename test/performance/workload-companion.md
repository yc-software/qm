# Controlled auxiliary and loop responses

`workload-companion.ts` serves the fixture-only Anthropic messages endpoint while running the unchanged `workload-provider.ts` on an internal loopback listener. There is no configurable forwarding destination or external fallback. Its fixture/database and synthetic-token checks are the same as the frozen provider's. Keep the frozen provider source digest in the executable artifact manifest.

```sh
node test/performance/workload-companion.ts --profile /private/companion.json --provider /private/provider.json --fixture /private/fixture.json --out /private/companion-events.jsonl
```

Configure QM's ordinary Anthropic endpoint to this listener only after checking the isolated runtime and enabling the intended real Pi utility adapter. A per-turn Pi choice with a mock default does not enable all native utility traffic. This program does not change QM policy or runtime configuration. It writes a new mode-0600 JSONL file and never logs request bodies, response bodies, headers or keys.

The companion profile has `schemaVersion:1`, matching `fixtureId`, listener `host`/`port`, the provider's `tokenEnv`, `utilities`, and optional `loop`. Remote binding requires the exact `QM_PERFORMANCE_BIND_HOST` value. Each utility rule contains:

| Field                                | Contract                                                                     |
| ------------------------------------ | ---------------------------------------------------------------------------- |
| `name`, `model`                      | Unique rule name and exact request model ID                                  |
| `systemSha256`                       | SHA-256 of the exact system text; text blocks are joined by a single newline |
| `response`                           | Fixed synthetic text matching the real utility's response contract           |
| `delayMs`                            | Wait before the response or first stream event                               |
| `chunkCharacters`, `chunkIntervalMs` | Unicode code points per text chunk and time between chunks                   |

Utility requests must contain one text-only user message and no tools. Streaming SSE and ordinary JSON responses use the same rule. Pi `oneShot` appends `\nCurrent working directory: <cwd>` to the source system prompt. Its ordinary cwd is stable for each prefix (`join(tmpdir(), prefix + '-cwd')`); its random agent directory does not appear in the prompt. Bind exact wire digests for the actual runtime paths. If Pi cannot create its stable directory and falls back to a random cwd, the request is rejected. There is no prefix match or automatic prompt learning. Acknowledgment requests use their source system text directly. Direct compaction has its own installed-client system prompt and also needs an explicit digest. Native compaction uses the configured turn model, while acknowledgment and default title/detection helpers use the auxiliary model.

`loop` contains the same pacing fields plus exact `model` and `shipAction`. A native loop's playbook must carry `[qm-perf-loop:<fixtureId>:<nonce>]`. Only one current user stage header and its matching end header are accepted: `[Loop intake]`, `[Loop work]` or `[Loop judge]`. A unique matching fixture marker must occur in that current message. Intake produces one synthetic item whose `sourceKey` preserves the marker plus a deterministic request digest. That source key reaches the real judge prompt, which omits the playbook. Work prepares one output with the configured action; judge returns `met` with no checks. Create this diagnostic loop with a matching synthetic success condition, no declared checks, no destination, a **hold** ship gate, and bounded caps. This responder never executes a ship action. Distinct intake requests produce distinct keys; repeatability across native recurring fires still requires live proof of distinct request identities and expected item counts.

Ordinary c35 turns must have a complete marker in the current user message, the actual QM `files` tool, and pass the frozen provider's own model/shape/tool checks. Empty, image-only and incomplete-marker user messages cannot fall back to an older marker. A continuation must contain exactly one successful tool result matching the immediately preceding expected `files(action: "read")` call, including its ID and path; the validated chain must lead back to a marked originating user turn. Unknown requests fail before forwarding. The provider identity endpoint exposes both profile hashes and separate counters; frozen-provider counters retain their original meaning. `companion-call` records retain exact request/system digests, request bytes and gzip bytes, response bytes, timing, stream mode, matched rule and errors. Frozen-provider calls also retain their original records. A forwarded request has one record at each layer; do not sum both as separate model calls.

Admitted utility receipts also retain `utilityInputSha256`, the digest of the complete text-only user input with text blocks joined by a newline. It binds title, compaction and other utility inputs without logging their plaintext. The digest alone does not establish run ownership or utility completion.

Shutdown aborts both listeners and waits for companion and frozen-provider terminal evidence before resolving. Repeated close calls share the same promise; repeated process signals close the evidence sink once.

Optional `nativeShapes` admit `[qm-perf-native:<fixtureId>:<shape>:<nonce>]` on the current user turn. Each shape declares an exact `model`, independent `modelCalls` and `toolCalls`, `batches` with one positive count per nonterminal model response, and matching `operations`. Operations are either an actual `files(action: "read")` with exact durable path/bytes/hash, or a fixed `sandbox(action: "exec")` command that prints deterministic synthetic bytes on an explicitly owned sandbox. The profile cannot supply a command or network destination. Every continuation validates the complete preceding batch, input identities, successful results and actual returned bytes. Earlier conversation markers cannot authorize a new turn.

Native shapes also declare `outputBytes`, `repeatedFraction`, the ordinary pacing fields and a terminal contract: `reply` or `loop-intake-empty`. The latter requires the actual current intake stage and returns no items, so one native intake run can represent one controlled arrival without creating work/judge descendants. It does not prove the historical loop-stage mix. Impossible call/tool joints must be resolved explicitly in the external workload mapping or rejected; the responder never invents extra calls or tools. Native records include the shape, nonce, step and batch size. Run `node --test test/performance/workload-native.test.ts` for the installed-client multi-tool protocol and malformed-continuation checks.

Every companion evidence record remains `qualified:false`. Synthetic token counts estimate bytes divided by four. These responses exercise QM's real client, scheduler, persistence and delivery work under explicit pacing; they do not establish real provider inference capacity, correctness of arbitrary model outputs, complete source-mix coverage, or production byte/latency parity. Calibrate response sizes, pacing, source arrivals and resulting DB/CPU/SSE pressure from measured evidence before using a separate campaign attestation.

```sh
node --test test/performance/workload-companion.test.ts
```

The focused tests use the installed Pi `oneShot`, the actual Pi acknowledgment helper, and the installed Anthropic streaming client. They verify native compaction model binding, loop-stage contracts, the unchanged provider's two-call tool continuation, active-response shutdown drainage, and rejection of altered utility prompts, wrong models/fixtures, ambiguous loop stages, unauthorized access and stale markers.

Optional `loopPlans` provide finite recurring-loop correctness and pressure envelopes. They cannot overlap the legacy `loop` rule. Each plan contains the exact native `definition` snapshot (native 16-hex or canonical lowercase UUID-shaped fixture ID), a stable `[qm-perf-loop:<fixtureId>:<label>]` `sourceKey`, and ordered `occurrences` with unique `id`, explicit `item` boolean, optional stable `sourceKey` override and `stages:[{stage,shape}]`. Shape names refer to `nativeShapes` with terminal `reply`; ordinary shape model, tool, result-byte and pacing validation is shared. A maximum of 32 definitions and 1,000 occurrences per definition is admitted.

Tasks are generated through the actual native loop-fire service against disposable in-memory stores; no production prompts are copied or approximated. Inbox and source-specific inbox tasks use the native renderers. Regular plans require one held ship action, no declared checks, and open-output headroom above the number of distinct declared item keys; activation must also account for already retained outputs. The first occurrence with `item:true` for each declared key must include intake, work and judge; subsequent occurrences using that same key declare intake only, exercising native deduplication. Each distinct key renders its own exact native work/judge tasks, allowing a repeated-hour plan to declare new held items without deriving keys from mutable wire bodies. Empty intake and sync occurrences each declare one stage. The fixed work result creates one reviewable output and the fixed judge passes it; the helper never executes shipment. Sync returns the shape’s deterministic nonempty terminal text using its declared `outputBytes`; the native sync fire ignores that reply content and creates no synthetic inbox item. This avoids triggering an undeclared Pi empty-ending continuation. Tool-call text uses the shape size; structured terminal JSON has its actual size, which must be measured separately from nominal `outputBytes`.

Admission matches the exact current native task, allowing only one well-formed appended native environment note. It reserves one model response at a time per definition, validates exact tool-step order and all returned bytes, and advances only after the HTTP response finishes. Unknown, extra, concurrent or malformed loop calls and failed/aborted accepted responses poison the plan. There is no retry/reset endpoint or fallback. The helper instance UUID separates tool identities across restarts; restarting loses disposable admission state and requires a fresh campaign with independently reconciled receipts.

Each accepted `companion-call` adds `loop:{loopId,sourceKey,occurrenceId,occurrenceIndex,stage,stageIndex,provisional:true,responseComplete}` alongside its unique `responseId` and normal native step metadata. The identity endpoint's `loopPlan.complete` reports only that the finite response plan was consumed. Identical successful origins can be a retry or a later scheduled fire; the endpoint cannot distinguish them by content. A campaign must independently join every accepted response ID to canonical assistant tape, its native run and exact cron fire/stage, reject retries/duplicates/extra or missing work, and reconcile the owned tail before passing. No occurrence counter, completion field or operator assertion qualifies the campaign.

`node --test test/performance/workload-loop.test.ts` uses the installed client and actual native fire service/ledger/runner for two fires each of held, all-source inbox, Gmail and Slack loops. A third regular fire uses a new declared key and proves a second held output, while preserving second-fire item dedup, duplicate-fire rejection, exact tool/model budgets, identical-origin unique receipts, finite admission and aborted HTTP response poisoning. This bounded in-memory/loopback check does not prove durable tape joins, scheduler timing, shared-runtime behavior or production pressure parity.

Native shapes can replace existing operation slots with fixed child operations: `{kind:"session-open",name,shape,model}` or `{kind:"session-followup",openOperation,shape}`. The referenced shape is the child's wire-model/tool/terminal envelope; open's `model` is the explicitly bound native application model and the harness is fixed to Pi. Each child shape has one declaring operation, terminal `reply`, no child operations of its own, at most 16,000 output bytes and at least 32 nonrepeating terminal bytes. A parent admits at most ten child operations, each in its own sequential tool batch, and declares `sessionTitle` equal to the native syscalls' captured caller title: `binding.session.title?.trim() || "this conversation"` when `forTurn` is built. A later durable title readback is insufficient because fallback or asynchronous title generation may change it. Bind the actual rehearsed stage, including the native fallback or an exact configured title-utility result; later stages may require a different fixed shape/title binding. Title changes require a new profile binding. The helper adds no calls to parent or child budgets. Follow-up inherits the open's model and targets only the UUID returned by an earlier open operation in the same current turn; forward references, title targets, prior-turn opens and automatic return-wake modeling are outside this profile.

Child tasks are fixed fixture/shape markers with nonces derived from parent nonce and operation ordinal. Child admission requires the complete installed native subagent-task or subagent-message wrapper, the exact bound parent title and at most one complete trailing environment note. The follow-up wrapper's dynamic parent UUID is syntax-checked; its actual ownership must be joined to native request/session records. Bare child markers, changed wrappers, mismatched tool identities and responsive-coordinator open responses fail. Normal cron/loop request posture has no `surfaceTools` override: native completion writes mailbox content without adding parent return runs. Profiles must retain that actual posture and separately reject unexpected return runs, rather than changing actor rollout flags to suppress work.

Exact read/exec/session result bytes may be followed by at most four native mailbox blocks per tool result, matching the installed client's single-newline flattening. Each block must equal the native final-answer renderer for an already validated owned child operation's UUID/name and deterministic terminal body; duplicates, unknown children, errors, quarantine/unscreened notices, changed base bytes and unrecognized suffixes fail. This stateless transcript check proves the declared content/ownership relation, not that a child response was delivered or persisted. Qualification still requires the independent response-ID/tape/run/mail/fire joins, exact native parent/child actor/scope/dedup identities, and reconciliation of any child/mail tail. Historical same-child follow-up or delegating-stage assignments are not inferred from this mechanism.

`node --test test/performance/workload-children.test.ts` uses the installed client, actual sessions tool/schema, native session syscalls, run stores and mailbox with owned memory stores. It drives one open, one same-child follow-up and two carrier reads for both cron and loop parents, preserving each parent's five model/four tool calls and each child's one model/zero tool calls. Native completion mail is screened and consumed without extra parent runs even with responsive rollout enabled; a responsive-parent control actually creates a return wake and its open result is rejected. This check uses controlled file bytes and explicit local completion of native queued child runs; it is not a shared-runtime worker, storage or pressure proof.

Finite ordinary recurring crons use optional `cronPlans:[{definition,directoryMembers,occurrences:[{id,shape}]}]`. Each definition is an exact retained `Cron` with one fixed `[qm-perf-cron:<fixtureId>:<cronId>]` marker in its stored action. IDs admit native 16-hex, canonical lowercase UUID, or retained `perf-cron-N` fixture values with canonical integers from 0 through 1000000. There are at most 128 definitions and 1000 declared occurrences per definition. Each occurrence selects an existing native shape; callers expand a bounded cycle explicitly. The helper renders the actual native cron task through an isolated memory scheduler, including title, bound initial last-fire note and directory-derived mention roster. This template-only call has synthetic authority and refuses delivery; it does not validate live authorization. Relay messages, one-shots, raw `!run`/`!scratch` and loop-linked crons are not admitted by this branch.

The current fixed tool shapes never edit cron notes. Bind the original note exactly (including absence) and prove it stays unchanged in native before/after evidence. Changing notes are not modeled; any changed note, roster, standing task or wrapper fails exact admission. One complete trailing native environment note is allowed using the same validation as finite loop tasks. A definition has one admitted continuation chain; duplicate, skipped, overlapping or exhausted requests fail and poison the finite cron plan. The state advances only after successful HTTP completion, and an aborted accepted response poisons it. Existing direct web/Slack/child and loop admission remain separate.

Each accepted call retains `cron:{cronId,occurrenceId,occurrenceIndex,provisional:true,responseComplete}` with its unique response ID and native step/budget fields. `cronPlan.complete` on the identity endpoint means only that every declared response was consumed successfully. A never-offered suffix is explicitly unconsumed; it adds no observed work. Identical successful origins can still be a retry or the next native fire. Actual per-definition serialization, native schedule/claim identity, unchanged definitions and one-to-one response-ID/tape/run/fire completeness must be proved independently; neither the helper counter nor a terminal response establishes them.

`node --test test/performance/workload-cron.test.ts` drives two real scheduled `tick` fires of the same memory cron through the installed streaming client with distinct 2M/1T and 3M/3T shapes, native fire keys/thread hashes, an unchanged stored note and actual mention roster. It retains five unique response IDs and an explicitly unoffered third occurrence. Negative checks reject changed tasks/notes/rosters, malformed suffixes, duplicate continuations, concurrent requests, exhaustion and an aborted accepted HTTP response. This proves bounded source/protocol behavior, not durable storage, live worker timing, pressure or production recurrence parity.

Finite loop shapes alone may declare `recovery:"empty-ending-once"` or `recovery:"overloaded-retry-once"`. Such a shape has exactly `modelCalls - 2` positive tool batches, the same exact summed tool budget, terminal `reply`, and no child operations. Direct native turns and ordinary cron plans reject these modes. They are explicit modeled mechanisms for an extra main call, not evidence of the cause of any historical production request.

`empty-ending-once` sends one empty completed response after the last tool batch. It admits only the installed Pi `EMPTY_ENDING_NOTE` as the next and sole new user message, with the same preceding request apart from the native ephemeral cache-boundary move. The next response is the normal terminal reply. `overloaded-retry-once` sends an identified message start followed by one fixed SSE `overloaded_error` on the first call. It admits exactly one retry with identical serialized request bytes, then runs the declared tool batches and terminal reply. Neither intermediate outcome advances the stage or occurrence. An incomplete/aborted response, changed retry, unknown error, skipped call, duplicate ending note or exhausted budget fails; there is no recovery reset or extra retry allowance.

Recovery receipts retain the main-call ordinal in `native.step`, tool-batch ordinal in `native.toolStep`, declared `native.recovery` and `native.outcome` (`reply`, `empty-ending`, or `overloaded-error`). The one planned error also records `native.plannedErrorSha256`, the digest of its exact SSE error JSON. A completed declared error has top-level `error:null` because the helper delivered its configured outcome; it is still an error assistant message in canonical Pi tape and is never counted as a successful assistant answer. All unknown helper/transport errors remain failures. Qualification must bind that exact planned outcome and response ID to the native error tape row and subsequent same-run retry, in addition to the ordinary run/fire bijection. Compaction summaries remain separately observed utility requests and never satisfy the main-call budget.

The loop tests additionally run the actual native fire service and Pi harness through the owned loopback companion. They prove default sync terminates at its declared byte/model/tool budget, the exact native empty-ending note and installed SDK retry occur once when declared, every main response ID reaches canonical tape, and the planned error’s body/request digests match. These tests use memory stores and fixed synthetic file results; durable campaign joins, external model capacity and production timing remain separate prerequisites.

A standalone bootstrap shape may use one `sandbox-create` operation with an exact synthetic `perf-NNNNN@example.invalid` owner and a unique `qm-perf-bootstrap-` name. It requires exactly two model calls, one tool call, one batch, terminal `reply`, and no recovery. Only the exact native fixture marker with the optional native environment suffix is admitted; cron, loop and child wrappers cannot create resources. The helper emits the installed `sandbox` management action with fixed `sprites` backend and validates its actual returned UUID, personal owner, creator, backing scope, name, nonlegacy ready state and machine identifier before the terminal reply. It never sets a default.

The bootstrap test uses the installed streaming client, actual agent tool, tool context, resource manager and router with memory stores and a controlled provisioning backend. It proves non-admin ownership, rejection of foreign ownership and reuse of the same backing resource through native provisioning. It does not prove remote provisioning, durable persistence or replay safety. An operator must retain one native turn intent and acknowledged resource ID per actor, independently join the tool result to the native durable resource, and leave lost acknowledgments unresolved; never repeat creation or adopt a resource by its name. Bootstrap turns and their utility calls belong in explicit preparation lineage outside measured campaigns.
