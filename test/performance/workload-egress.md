# Native egress connection proof

`workload-egress.ts` makes exactly one allowed and one denied HTTP CONNECT through the actual QM Envoy proxy. The allowed tunnel carries a verified TLS request to the synthetic fixture responder. The denied hostname must return a native 403 before opening an upstream tunnel. This is a bounded functionality proof, not an arrival-rate or latency benchmark.

Use the existing `deploy/egress-proxy/Dockerfile`, Envoy configuration, `egress-authz-main.ts`, and native audit relay. The driver never calls `/v1/egress-audit` or writes SQL: only the native authorization decision service produces those events. Configure its relay to the isolated core with the fixture source signer. Disable any synthetic egress-ingestion workload while this proof runs.

Prepare an isolated Docker network and a dedicated responder profile using `workload-credential-responder.ts`. The target must be `qm-perf-egress-<campaign UUID>.test`, resolving through real container DNS to a non-loopback fixture address. Its short-lived egress capability allows exactly that hostname, denies other private destinations, and uses the existing explicit private-network allowance for that host. Native loopback and metadata restrictions stay unchanged. Give the responder a normally trusted certificate covering its hostname and its loopback control endpoint. Keep responder control and data tokens distinct and synthetic. Publish the proxy and responder control ports only to loopback.

Before traffic, the driver checks the `qm_perf_*` database marker, signed owned transcript sentinel, responder identity/profile hash, zero previous events for the unique campaign hostnames, and a fresh launcher attestation of the running containers, network, proxy image, authz source, and Envoy config. Secrets come only from named environment variables. The checked-in code contains no deployment bindings or production data.

```sh
node test/performance/workload-egress.ts --profile /private/egress.json --fixture /private/fixture.json --deployment /private/deployment.json --output /private/egress-proof.jsonl
```

The supplied deployment attestation must be generated by a reviewed launcher that actually checks its named fixture resources; the JSON alone is not independent proof of infrastructure. Inspect and retain the real proxy logs as a separate completion gate. Any audit-relay failure, recovered drop count, or unexpected container exit fails the launcher result.

A pass requires the actual CONNECT statuses (200 then 403), successful TLS validation and fixture response identity, exactly one upstream responder arrival and zero unexpected arrivals, and exactly two native durable egress rows: one `allowed=true/verdict=ok` for the target and one `allowed=false/verdict=not_allowlisted` for the denied hostname. The driver waits for persistence, then observes another 12.1 seconds covering the native relay's ten-second HTTP timeout plus two-second batch period before its final count. Late duplicate rows fail. Per-connection evidence retains status, latency, and byte counts without bodies or tokens. A failing probe retains its evidence; it does not delete audit history or retry the whole campaign against the same hostnames.

This exercises Envoy CONNECT, capability verification, policy and DNS/IP checks, actual TLS traffic, the native batched source-signed relay, and core durable egress storage. It does not establish remote sandbox network enforcement, Sprites provisioning, upstream distribution, production proxy resource parity, or production traffic rates. Qualification is always false. No core configuration change is required; the fixture launcher owns and cleans up only its uniquely named network and containers.

The focused transport test uses an ephemeral TLS server and minimal tunnel peer to verify the driver protocol, trusted versus untrusted certificates, and preservation of denied CONNECT status. Native authorization and proxy configuration have their existing focused tests. The real Envoy/relay/database proof still requires the reviewed isolated live run.

```sh
node --test test/performance/workload-egress.test.ts test/egress-authz.test.ts test/egress-proxy-config.test.ts
```
