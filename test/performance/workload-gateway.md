# Model gateway and screening protocol fixture

`createGatewayFixture` provides a normally trusted HTTPS destination for the native model gateway signer and security-screen client. It uses only synthetic credentials and a fixed loopback or explicitly named fixture-internal model upstream. It has no AWS credential discovery, STS call, external forwarding, or production key. Its receipts are always unqualified.

Gateway requests require the configured API key, exact host/method/path, fresh SigV4 date, fixed region/service/credentials, and an independently recomputed body signature using the installed AWS SDK. Unknown models, unsigned payloads, changed bodies and malformed signatures fail closed. Model listing and metadata support native catalog discovery. Message forwarding translates the configured model alias and streams the companion response with backpressure; signing credentials are never forwarded.

The pinned AWS proxy copies incoming headers after signing, so the API key is authenticated separately over TLS; the verifier requires signed host/date/session-token headers and verifies every header actually named in `SignedHeaders`. This follows the observed native binary and the [upstream proxy implementation](https://github.com/awslabs/aws-sigv4-proxy/blob/master/handler/proxy_client.go), rather than requiring an additional signature on headers the proxy does not sign.

Security requests require their own synthetic token, native hook/chunk coordinates and an explicitly admitted synthetic text digest. Known allow/block digests return controlled classifier scores; all other text rejects. Delay is an explicit fixture input. Receipts retain byte hashes, coordinates, outcomes, completion/abort state and elapsed time, never request text or credential values. Disconnects cancel screening delays; cancelled responses cannot count as completed screenings. A throwing receipt sink is fatal: the owning supervisor must mark that process failed and clean up its owned services. Missing receipts are never successful evidence.

The focused test runs actual TLS requests through the native catalog and screening clients, including chunk coverage and rejection cases. A separate operator-owned isolated Docker proof is required for the pinned signer binary itself; no core overlay is performed by this helper. Keep its image/config/source hashes, native receipts, resource limits and exact owned cleanup with the campaign evidence.

This fixture does not reproduce external inference, STS, API Gateway or classifier capacity. Those waits and limits still require measured calibration or explicit finite sensitivity bounds. Native Pi runs, screening audit outcomes and two-core ownership must also be proven by the campaign; a passing protocol test alone cannot qualify performance.
