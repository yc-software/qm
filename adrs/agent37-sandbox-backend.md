# Agent37 as an agent-computer backend

Vishnu from Agent37 here. You asked whether we could host qm. The honest answer is that the part of qm that wants hosting is the agent computer, so this is a fifth sandbox backend, next to Sprites, smolmachines, Porter and AWS.

Agent37 rents isolated Linux machines over a small REST API: create, exec, start, stop, delete. Each one keeps its disk across stop and start, which is the lifecycle your Sprites and smolmachines backends already assume, so the mapping is direct: one Agent37 instance per qm scope, created on first use, named after the scope so an operator can recognise it in their Agent37 dashboard, deleted when qm tears the scope down.

What the PR adds

- `SANDBOX_BACKEND=agent37` with `AGENT37_API_KEY`. Optional knobs: `AGENT37_API_BASE_URL`, `AGENT37_NAME_PREFIX` (at most four characters, so every generated instance name stays within our 60-character limit), `AGENT37_TEMPLATE`, `AGENT37_CPUS`, `AGENT37_MEMORY_GB`, `AGENT37_DISK_GB`, `AGENT37_IDLE_TIMEOUT_SEC`, `AGENT37_EGRESS_PROXY_URL`, and the shared `SANDBOX_TIMEOUT_SEC`. Instances come in three fixed shapes, 2 vCPU / 4 GB, 4 / 8 and 8 / 16, with disk ranges of 2-12, 2-20 and 2-40 GB; the backend refuses any other combination at startup rather than letting our API refuse it at the first create.
- `src/sandbox/agent37-sandbox.ts`, modeled on the smolmachines backend. Provision creates the instance and waits for it to run. Run is our exec endpoint. Teardown with destroy deletes the instance. Files move over the instance's own files endpoints (`PUT` and `GET /v1/files/content` on `https://{id}.agent37.app`, authenticated with the same key as `X-Agent37-Key`), which stream any size with no output cap, so a file or an export archive is one request rather than a series of base64 exec chunks. Process sessions, home export, ro layers and blob staging come from the shared exec helpers unchanged.
- Exec on our side waits up to 780 seconds, a wake from sleep included, then answers `502 provisioning_failed` while the command keeps running inside the instance; each stream is capped at 512 KB. The backend runs commands of up to 600 seconds synchronously, which leaves room for the two-minute wake from cold storage under the cap, runs longer commands detached and polls them, and never retries an exec that may still be running. Larger output is spooled to disk and read back through the files endpoint, so the agent never sees a truncated result.
- Every error is branched on the `error.code` in the body, never on the HTTP status or the message text: `try_again` (a sleep checkpoint still being written), `capacity_unavailable` (a wake or start that found no host), `invalid_request` on an instance that is still `waking`, and the instance-URL codes for a container that is not up all mean "bring the instance to `running`, then retry once"; `no_capacity` on create is waited out; `instance_limit_reached` on create is reported as a clear error, since only deleting instances or topping up clears it.
- Auto sleep is on. Agent37 checkpoints an idle computer after `idle_timeout_seconds` (our default is 900, configurable from 300 to 86400 through `AGENT37_IDLE_TIMEOUT_SEC`) and bills disk alone while it sleeps; a command sent to a sleeping computer wakes it first, and every command counts as activity on the Agent37 side, so a long command is never frozen mid-flight. A command sent to a stopped instance (an operator stop, a past-due park) starts it first, then runs; while a sleep checkpoint is still in flight the API answers `409 try_again` and the backend retries until it clears.
- Instances are created with `user` and `metadata` tags naming the qm prefix and scope (or scratch key), and the backend finds a scope's instance by those tags rather than by name, so an operator may rename an instance in the dashboard. An instance that carries only the old name-based label is adopted once and tagged.
- Templates are pinned to a published release (`agent37-codex@<tag>`), so a create is reproducible and a new upstream release only reaches qm when the pin moves. `AGENT37_TEMPLATE` accepts any template name with or without a pin.
- Recovery uses our backups: every instance's `/home/node` is backed up nightly into three rotating slots, and the backend requests an on-demand backup (one per instance per 15 minutes) after every turn that touched the home. `computerStatus` reports the newest backup as the recovery point and never wakes a sleeping instance to probe it; `restartComputer` wakes the instance if needed and recreates its container through `POST /restart`.
- Profile: `writablePersistence: "resident_disk"`, `processSessions: true`, `egressEnforcement: "none"`. Our sandboxes reach the public internet and nothing private, but there is no per-domain allowlist, so the backend declares none rather than pretend.

What it does not do

- No idle reaping and no snapshot to the workspace. The instance sleeps on idle and is deleted only on destroy; the disk is the machine's own and survives stop and start, and delete takes the backups with it.
- No image plumbing. The default uses a pinned release of Agent37's `agent37-codex` system template. Any other Agent37 template can be named with `AGENT37_TEMPLATE`.
- No restore from qm. A backup can be restored from the Agent37 dashboard or API (`POST /v1/instances/{id}/restore`); qm reports the restore point but does not roll an instance back on its own.
- No new CLI target. `qm init` still deploys the core to Docker, Fly or AWS; this only changes where the computers live.

Tests run against an in-process fake of our API, so CI needs no Agent37 account. We would rather this live upstream than in a fork, and we will keep it green as the sandbox contract moves.
