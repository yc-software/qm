# Archiving projects

A project has no end-of-life today. `src/projects/project-store.ts` keeps one record per project (id, org, name, owner, `memberIds`, channel-derived `channelMemberIds`, an optional linked Slack channel, timestamps) in the `projects` artifact map, and everything else hangs off its scope, `group:web-project-<id>`: sessions (`listByScope`), the agent computer (sandbox resources and the scope's default sandbox, keyed by `ownerScopeId`), skills (`scopeId`), keychain grants (`audienceScopeId`), file artifacts, crons, webhooks, monitors and loops (all `TriggerBase.ownerScopeId`), deployments and memory. Access runs through the same membership: `canReadScope`, `canWriteScope` and `canManageScope` ask the project store whether a principal is a current member, the owner alone can rename or remove members, any member can add members or link a channel, and changes are audited as `project.create`, `project.rename`, `project.member.add` / `.remove` and `project.slack_channel.link` / `.unlink`. The inbox is personal: it is built from the loops a person picks and can administer, so a project only shows up there through loops owned by its scope.

What's missing is any way to retire one. `/v1/projects` has list, create, rename, members and slack-channel routes, but no archive and no delete, and nothing in core removes a project record. The only implicit "hide" is accidental: when the owner stops being an active internal member, the project drops out of `listForMember`, `members()` returns nothing and membership fails closed, while its crons, loops and computer carry on underneath. Other objects already have a retire step that this can borrow from: sessions have a per-participant `archived` view flag, crons have `archived` (which also disables them), skills have an `archived` status, loops have an `archived` state, and sandbox resources go to `retired` through `destroyScope`. So a finished project today keeps a warm computer, keeps firing its schedules and keeps showing up in every member's sidebar, and the only cleanup is doing each of those by hand.

Options I looked at:

- A. Status quo, plus docs on how to wind a project down by hand (disable crons and loops, retire the computer, remove members). Zero code, but easy to get half right, and nothing marks the project as finished.
- B. Hide only: an `archivedAt` on the project that filters it out of default lists. Cheap, but a hidden project that still runs schedules and holds a computer is worse than a visible one.
- C. Hard delete: remove the project and cascade to sessions, files, skills, grants, triggers and the computer. Saves the most, but it is irreversible, it touches history other members rely on, and it needs retention and legal rules QM doesn't have yet.
- D. Archive as a lifecycle state: the project becomes read-only and hidden from default lists, its active parts (computer, schedules, integrations) are stopped or paused, and its data is kept, so unarchive puts it back. Delete stays a separate, later step.

I'd go with D, and leave C for a follow-up that only applies to projects already archived, the same "archive first, delete as a deliberate second step" shape crons are moving towards.

What archive means:

- State. Add `archivedAt`, `archivedBy` and an optional `archiveReason` to `Project`, plus a small `lifecycle` field (`active`, `archiving`, `archived`, `restoring`) so a half-finished archive or restore is visible and can be resumed. Archived projects are excluded from `listForMember` and from the contexts list by default, shown under an "Archived" filter, and still returned by search and by direct link to current members, labelled as archived.
- Read-only. `canWriteScope` returns false for an archived project's scope, which covers new turns, file writes, skill edits and grant changes in one place. Reads (`canReadScope`) are unchanged, so members can still open sessions, files and history. Roster changes, rename and channel linking are refused until unarchive.
- Running sessions. Archive is refused with a clear error while any session in the scope has a queued or running run, listing those sessions. The caller can stop them first (the existing abort path), or pass an explicit `stopRunning` flag that aborts them and records that it did. No silent kills. Pending approvals in the scope are expired with an "archived" note.
- Agent computer. For each sandbox owned by the scope: checkpoint, export the home through the existing home snapshot path, then destroy the backing machine (`destroyScope`) so it stops costing anything. The resource is marked archived rather than retired, so unarchive provisions a fresh one and hydrates the home from the snapshot. Backends with no durable home export (for example Sprites without `SPRITES_SNAPSHOT_S3_BUCKET`, where destroy deletes the sprite and every checkpoint) need a choice: refuse to destroy and just stop or sleep the machine, or destroy only after an explicit confirmation that the disk will not come back. I'd default to refusing.
- Schedules and integrations. Crons, loops, webhooks and monitors owned by the scope are paused, not deleted, and each pause records `pausedByArchive` so unarchive resumes only what archive paused and leaves anything a person had already disabled alone. Loops owned by an archived project drop out of the inbox loop picker, and their open items show as archived rather than actionable. Webhook deliveries to an archived project get a clear 410-style response rather than being queued. A linked Slack channel stays linked but stops routing new messages to the project, and the channel roster sync skips archived projects.
- Skills and credentials. Project-scoped skills keep their status and content but are not resolved for any turn while the project is archived (no turns can start anyway, this just keeps them out of cross-scope listings). Keychain grants whose audience is the scope stay on record but are inactive, so nothing can materialize them. Deployments owned by the scope are left as they are in v1 and flagged in the archive confirmation, since stopping a live deployment is a bigger call than archiving a workspace.
- Files and memory. Kept as they are, readable by members, not writable.
- Permissions. The project owner or an org admin can archive and unarchive. Members can't, since archive affects everyone's access to shared work. If the owner is no longer an active member, an org admin can archive or unarchive and optionally reassign the owner as part of unarchive.
- Audit. `project.archive` and `project.unarchive` with actor, reason and a summary of what was paused, stopped and snapshotted, plus per-item entries for anything that failed and needs attention.
- API and UI. `POST /v1/projects/:id/archive` (with optional `reason` and `stopRunning`), `POST /v1/projects/:id/unarchive`, and `GET /v1/projects?include=archived`. Both mutations are idempotent and resumable from the `lifecycle` state. In the web UI: an Archive action in project settings with a confirmation that lists running sessions, computers, schedules and deployments it will touch; an archived banner and disabled composer on archived project pages; and an Archived filter in the sidebar and project list. Admin gets the same actions in its project view.

Migration is additive: existing projects read as `active` with no `archivedAt`, so nothing changes until someone archives one. Retention in v1 is "kept until deleted". Home snapshots of archived projects are the one thing that costs money over time, so they should follow whatever lifecycle the snapshot bucket already has, and the archive confirmation should say so.

Archive versus delete: archive is reversible, keeps every session, file, skill and grant, and only stops things that cost money or act on their own. Delete, when it comes, should require the project to be archived first, remove the record and cascade, and be org-admin only, ideally after a grace period.

Consequences. Finished projects stop costing compute and stop acting on schedules without anyone losing history. Members lose write access to an archived project's files and sessions until someone unarchives it, which is the point but will surprise people who expected "hidden". Restoring is not instant: unarchive provisions and hydrates a new computer, home only, so caches, `node_modules`, virtualenvs and anything outside the home are rebuilt on first use. Every scope-keyed subsystem has to respect one more state, which is why I'd keep the check in the scope helpers and the trigger runners rather than in each route.

Out of scope: hard delete and its cascade; archiving channel or personal scopes; changing how session-level archive works for participants; automatic archive of idle projects.

Open calls if the direction looks right: whether archive should block on running sessions by default or stop them by default; whether backends without a durable home export should refuse, sleep, or destroy with confirmation; whether live deployments owned by the scope should be stopped, left alone or block archive; whether project members (not just the owner) should be allowed to unarchive; whether archived projects should auto-delete after a configurable period or only ever by hand; and whether a linked Slack channel should be unlinked on archive or just muted. Happy for you to implement once you're aligned.
