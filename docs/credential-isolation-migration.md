# Execution isolation migration

Existing provider machines are refused unless their physical generation already has a durable supervisor trust record. Docker home volumes created for supervised execution carry a provider-side provenance label, allowing new containers to reuse those volumes; older unlabeled home volumes require migration. A matching scope name, guest file, or recovered machine identifier does not establish trust. Newly allocated machines are eligible for supervisor bootstrap; dependency and namespace checks must still succeed before execution.

Portable home archives restore only regular files and directories beneath `workspace/`. Home startup files, installed tools, credentials, symlinks, hardlinks, and device nodes are not restored. The original archive is retained in the same snapshot store under the scope key suffixed with `/pre-supervisor-home`. Operators can recover other files from that archive into a reviewed workspace migration; do not restore an old home over the trusted supervisor environment.

Modal native checkpoint recovery requires a current supervisor provenance marker in the durable provider record. Older checkpoints are refused pending workspace-only migration. E2B never creates or restores native memory snapshots: new guests use kill-on-expiry, save portable workspace archives, and stay warm until their timeout instead of pausing. This preserves workspace recovery while giving up suspended process recovery and some idle-cost savings. The existing checkpoint reference is retained. Native snapshot expiry still applies; refusing recovery does not extend a provider retention window. Existing workspaces must be exported or migrated before their provider checkpoint expires.

For resident machines, preserve the original disk or export its workspace before allocating the replacement. Never mark an existing unmanaged guest trusted by writing a marker or inserting its identity into the trust store. Stop unrestricted processes before copying workspace data into a newly allocated supervised machine.

Provider images require Python 3, bubblewrap, util-linux, and libseccomp. Custom images and provider-owned templates must supply these dependencies or pass the trusted bootstrap installer. Local Docker additionally needs the namespace capabilities configured by the local adapter; AWS images require the image build's additional OS capabilities. Execution still fails closed if the guest kernel or provider blocks the required boundary.

Porter supervised execution currently fails closed. Its sandbox execution API does not expose stdin or a private binary file upload API; its volume upload API alone cannot cover scratch sandboxes. Credential request bodies are never substituted into command arguments as a fallback. Other adapters stage request bytes through native file uploads or process stdin, inside root-only directories.
