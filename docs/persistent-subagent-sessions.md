# Persistent subagent sessions

A delegated task runs in a durable session with its own transcript and a mutable parent. The `subagents` tool opens children, reads their transcripts, and sends attributed messages. Subagents have no sidebar entry. The separate `sessions` tool is offered only on web UI turns and works with the user-visible conversations in the sidebar: it lists and reads them, sends them private notes, and, on a turn a person is attending, starts a new clean session or forks the current one. It refuses subagents; use the `subagents` tool for those. Parentage is organization data: it survives restarts and can be changed independently of the original delegation.

## Lifecycle

`subagents.open` accepts a task, title, model, thinking level, and optional `noComputer` flag. `noComputer: true` removes computer access entirely: no shell, filesystem, browser, or computer-backed integrations. Only memory/history, session coordination, runtime inspection, and permitted read-only connectors remain. Leave it unset for tasks that need a computer to read email, files, or code; express any no-write constraint in the task.

Reusing a request key recovers the same child and initial run after a lost receipt; using that key for different work is rejected. Children inherit the caller's scope and audience. The existing internal `readOnly` restriction remains durable: `noComputer: false` cannot lift a caller's restriction or an existing child's restriction. Work a Slack bot starts keeps the bot's restrictions the same way: its children, the parent turns their mail wakes, the swarm workers it spawns, the crons, loops and monitors it schedules, the turns that resume when its credential requests are answered or its secret drops are redeemed, and the wakes of the background jobs it watches all run as bot work. A bot's message never joins or stops a person's running turn: it queues as the bot's own turn, and a bot cannot interrupt a person's task or a person's work queued on a bot's task. A bot's stop command stops only bot work. A bot cannot direct a person's swarm, and its turn never counts as the live person that human-consent checks require, such as a loop's ship gates or registering a webhook.

`subagents.send_message` sends attributed text to a parent, child, sibling, or other accessible session. Targets accept IDs, child/sibling titles, or `parent`. By default it wakes the recipient: an idle attached child starts a turn on it, and a busy one gets it as its next turn, behind the active one. `wake: false` instead adds it to the recipient's durable inbox without starting a turn: a running recipient sees it at its next tool boundary, an idle one only when something else wakes it. A top-level conversation's wake starts a turn in another idle top-level conversation in the same context (`sessions.send_message` wakes unless `wake: false`, which sends routine FYI mail); that turn runs on the recipient's own stored context, never the sender's, and a busy recipient reads the message at its next tool boundary or is woken when its turn ends. Such a waking message is framed to the recipient as a task handed over by another conversation, which it may do now, defer, or decline by messaging the sender with `wake: false`; replies and status reports between conversations go `wake: false` so they wake no one. A wake that may not start a turn (a top-level conversation that is not the sender's own parent when the sender is a subagent, a read-only sender, a notebook-only sender such as the nightly memory tidy when the target session isn't notebook-only, a sender on a private turn, or a ninth peer wake in a row) falls back to the inbox and the result says so. The result names which happened. Stable call IDs deduplicate retries. `subagents.wait` waits up to 60 seconds for mail. `send_message` with `interrupt: true` aborts active child work, except that a notebook-only sender cannot interrupt a session that isn't notebook-only. Messages are external data, not human authorization. Each message is screened independently of its carrier tool and persisted at the receiving session's scope. Quarantined messages remain recoverable for approval; denying the approval consumes the message. Read-only and automated authorization restrictions still apply to assigned work.

Read access checks scope, current participant access, and audience visibility. Sending and adoption require current scope access. A wider target audience cannot receive a narrower source's contents.

## Parent changes and completion

Subagents appear as clickable, draggable inline chips in their parent conversation’s collapsible tool rows, outside the sidebar session list. Dragging a chip into the sidebar detaches it and makes it a top-level session. The web UI does not offer reparenting onto other sessions. A child transcript links back to its current parent. The underlying parentage API rejects cycles, unauthorized changes, and cross-scope moves.

A terminal child run produces a deduplicated internal result for its current parent. When the delegating actor is internal, a Slack or spine parent also receives a durable, deduplicated completion wake so it can report the result after ending its dispatch turn. Other parents retain passive mailbox delivery without a new run. The immutable delegating run supplies the actor, authorization, and delivery destination; the current parent request supplies the audience. A freshly adopted parent without runtime context leaves completion pending until that context exists. Detached children produce no automatic parent return.

Terminal receipts live in the run store. A paginated sweep retries pending returns after restart and continues past blocked entries. Completion receipts are acknowledged only after durable inbox insertion and any required completion wake succeed. Inbox messages are consumed after their content is persisted to the recipient transcript; an acknowledgement failure can cause redelivery. Silent completions use a generic notice rather than borrowing text from a later child run.

## Storage and scope

The session migration adds parent and spawn metadata. The run migration adds terminal-return acknowledgements and an index restricted to unreturned terminal child runs. Signal replay uses the existing signal acknowledgement columns.

Coordinator turns use durable session delegation and disable provider-native subagent tools.

## Swarms

Swarm workers continue to coordinate through the swarm API, which owns their computer assignment, membership, and execution budgets. Session tools cannot spawn or send from swarm turns, send to swarm workers, or adopt a child under a swarm worker. Ordinary human turns in a swarm root remain ordinary session turns. All session-generated work remains automated; a session turn carries only the authority its delegation chain proves, never that of an earlier task. For internal participants, an attached child and its completion continuation can retain the original live requester’s sharing and author authority through verified durable run provenance. Current audience and sharing policy still apply; read-only, private-message, swarm, detached, and unrelated automated work cannot borrow that authority.

## Access and delegation

Every internal actor is offered the subagents and sessions tools. External actors are not.

Slack and spine turns by internal actors run as responsive coordinators. Coordinators cannot use command execution, background process tools, credential execution, or provider-native delegation. They dispatch substantial work through `subagents.open`, end promptly, and receive completion wakes. Child sessions retain command tools. Web conversations without spine tools, swarm workers, and external actors keep the ordinary toolset and passive completion handling.

Messages use the existing durable artifact store under `session_mailbox`; no process-local queue owns delivery.
