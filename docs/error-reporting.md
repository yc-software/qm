# Backend error reporting

Set `SENTRY_DSN` in each backend service's deployment environment to enable Sentry. Leave it unset to disable reporting. Core (including in-process Slack), workers, web servers, and portal/auth servers report to the configured project. This does not add browser instrumentation.

Use a separate project for deployments with different operators or data boundaries. Configure `SENTRY_ENVIRONMENT` (for example, `production` or `staging`) and `SENTRY_DEPLOYMENT` (a non-sensitive deployment identifier). `SENTRY_RELEASE` overrides the image's `GIT_SHA`. Backend images built by the AWS CLI receive the source revision automatically. A combined web/admin process uses service `web`; a combined portal/auth process uses service `portal`.

Reporting captures uncaught exceptions, unhandled promise rejections, HTTP handler and authentication delivery failures, and the core's operator error records. Recorded failures carry `error_code` and a matching grouping fingerprint. Recorded exceptions preserve their original stack; records without an exception carry the recording call's stack. Repeated capture of the same error object is deduplicated by the SDK. Ordinary console logs and expected failures outside these boundaries are not reported.

Only error events are enabled by default. Profiling, logs and replay are disabled. Sampled performance tracing, including request instrumentation, is described below. Events are sent unredacted: error messages, cause chains (as linked exceptions), stacks, and the failure's context (the `detail` passed to `reportFailure`, or the operator error record's category, code, message, scope and session) all reach Sentry so issues can be debugged there directly. Each recorded failure's log line also carries its Sentry event id (`[sentry=<id>]`).

The SDK preserves existing fatal-error drain handlers. When no rejection handler exists it flushes and exits unsuccessfully. Core's explicit shutdown paths and web startup failures allow up to two seconds for pending error delivery. Delivery is best effort and never a substitute for application logs or infrastructure health alarms.

After deployment, verify a synthetic backend failure reaches the intended project with the expected release, environment, deployment and service. Check that its message and stack are readable. Test alerts against that event before relying on notifications. Disable reporting by removing `SENTRY_DSN` and redeploying; retain the prior immutable application candidate for code rollback.

## Optional performance tracing

Set `SENTRY_TRACES_SAMPLE_RATE` (a fraction between 0 and 1; unset, 0, or an invalid value keeps tracing off) on a backend service that already has `SENTRY_DSN` to sample traces. Start with `0.1`. With a sample rate set, the SDK's automatic instrumentation records incoming and outgoing HTTP requests (including `fetch`) and Postgres queries. A query run through the core's pool is one span: the transaction control the pool issues around it (`BEGIN`, per-query settings, `COMMIT`, `ROLLBACK`) is not recorded. A connection checkout from the core's pools is a `pg-pool.connect` span only when it waited at least a millisecond or failed. Health checks, server-sent event streams (`GET …/events` or `Accept: text/event-stream`) and the SDK's default 401–404 and redirect responses are not traced.

Spans are streamed: each is sent within a few seconds of finishing, and at shutdown, instead of being held until its request or run ends. A trace has no per-run span limit, and a run that is stopped keeps the spans that had finished.

Each sampled request becomes an `http.server` root span. The core names it by the registered route template, such as `GET /v1/sessions/:id`. Unregistered paths and every other service's requests are named `METHOD /*`, and deployment subdomain proxying is named `/deployment-proxy/*`. Errors captured during a request carry the same name. Each run attempt a worker processes becomes a `queue.process` root span named `run`, with `messaging.message.id` (the run id), `messaging.message.retry.count`, `messaging.message.receive.latency` (queue wait in milliseconds), `qm.surface`, `qm.origin`, `time_to_model_request` and `time_to_first_text` attributes (the last two are milliseconds from the attempt's start to its first model request and to the first streamed text delta of the reply). A run that was stopped, handed back at shutdown or requeued carries `qm.cancelled`. A run started by a person is always sampled; other roots follow `SENTRY_TRACES_SAMPLE_RATE` or the trace they continue. Its children are the attempt's Postgres and HTTP spans (each model request is an `http.client` span) and these named spans: the turn setup phases `turn.memory_snapshot`, `turn.memory_recall`, `turn.skills`, `turn.credentials`, `turn.decision` and `turn.dispatch` (dispatch until the first model request); `model.first_token` from each model request until the first streamed event of its reply; `step.gap` from a reply that calls tools until the next model request, with one `step.tool` child per tool call named by the tool, so its self time is the platform time of the step; `step.persist` around each transcript write; and `sandbox.provision`. Span names are reduced to their operation except `step.tool`, which keeps the tool name.

Trace context is propagated only to QM's own services: the origins named by `CORE_API_URL` and `AUTH_BROKER_UPSTREAM`. A run records the `sentry-trace` value of the request that queued it in its stored request (`trace`), so its worker span joins that trace. The run inherits the request's sampling decision, sampled or not, so it is never sampled again. Swarm dispatches never record one: a swarm fans out to many workers that would otherwise pile into the dispatching request's trace, so each swarm run starts its own trace and is found by its run id. Runs queued without trace context start their own trace. Browser timing is not linked to backend traces.

For requests without an upstream trace, the first traced service (normally the portal) makes the sampling decision and downstream services follow it. Incoming `sentry-trace` and `baggage` headers are honored as the SDK does by default, so a client that sends its own trace headers to a traced public endpoint can force its requests to be sampled. That costs Sentry quota. Upstream trace metadata is not exported: each envelope's trace header is rebuilt from the trace id of what it carries and this service's public key, release and environment. Sentry may sample again what it receives (dynamic sampling), so a run sampled here can be missing there or stored in part. A run stores only the `sentry-trace` value. With tracing on, error envelopes get the same rebuilt trace header; error event bodies are unchanged.

Spans are scrubbed before sending. Only traces rooted in a request (`http.server`) or a run (`queue.process`) are sampled, so other work is never a trace of its own; a span that starts after its request or run ended is sent inside that trace. Span attributes are reduced to an allowlist (Sentry's own bookkeeping, method, status, route, URL scheme, protocol, database system and name, the run's `messaging.*` attributes and timings, `qm.surface`, `qm.origin`, `qm.cancelled`, the service as `service.name`, and the deployment). A span's status message is kept only when it is one of Sentry's span status names (`unavailable`, `not_found`, …), which is what HTTP spans carry; any other text, such as a database driver's error, becomes `internal_error`. URLs, query strings, hosts, headers, cookies, request bodies, SQL text and database error text are dropped. Database spans are named by their SQL verb (`SELECT`, `UPDATE`, …; anything else is `query`), which is also all that is sent as their query text, outgoing HTTP spans by method and origin, and any other span by its operation. Error events keep the unredacted policy above.

Browser timing uses `SENTRY_BROWSER_TRACES_SAMPLE_RATE` on the web server together with `SENTRY_BROWSER_DSN`; see the web-ui README.

Browser Sentry ignores plain network `TypeError` failures (`Failed to fetch`, `NetworkError when attempting to fetch resource.`, `Load failed`) and `AbortError` cancellations; HTTP 4xx/5xx failures still report.

## Published apps

Published-app failures become operator error records in the app owner's scope, so they reach the admin errors view and Sentry: `deploy:app_start_failed` (publish failed, including an app that only answered 5xx on `/` for the readiness window), `deploy:app_restarted` (the supervisor restarted the app since the last visit-time check), and `deploy:app_down` (the app and its supervisor are gone). Each record names the deployment and carries up to 4 KB of the app's recent output, with the app's env values and known secret patterns masked. Every app host (AWS, Porter, Fly, Docker) runs the app under the same supervisor and probes, so the app image must provide `sh`; with `curl` or `wget` in the image the readiness check also rejects an app that only answers 5xx, and without either it waits only for the port to listen.
