# Background work: crons, webhooks, monitors and loops

_Verified against `main` at bd371980c (2026-11-24): statements were read in the code at c6056de14 and re-read where later commits changed it, unless marked **[interpretation]**._

## In one paragraph

Background work is every agent turn that starts without a person typing a message. Four things can start one. A **cron** comes due on a schedule. A **webhook** receives an HTTP request from an outside system. A **monitor** (a "job watch") sees new output from a long-running command on a sandbox computer. A **loop** has items waiting in its work queue. Each is a stored record with an owner (the person it runs as), a home scope (where it lives; see [scopes](./scopes.md)) and usually a destination (where its output goes). One occasion of a record going off is a **fire**. Every agent turn a fire starts passes through one function, `runTrigger`, which checks that the owner still belongs in the home scope, makes sure the same fire cannot run twice, starts an ordinary turn as the owner, and hands the reply to the delivery queue. The turn itself is the same as a typed one ([turns](./turns.md)). This area adds three things around it: the clockwork that decides when to fire (a scheduler on a pg-boss job queue, two HTTP receivers, a poller), the bookkeeping (a fire log, cursors, a loop's work ledger), and the rule for which core instance does the work when several run at once.

## One cron fire, traced end to end

The example: Ada at Acme tells the agent in her web conversation, "every weekday at 9:00 check the build dashboard, and only tell me if something is red." The agent makes a cron with a task, a script and her conversation as the destination. Side notes show where other paths diverge.

1. **Create.** The `cron` tool (`cronTools` in `src/agent/agent-tools/cron.ts`) calls `createCron` on the control service (`createControlService` in `src/api/control-service.ts`). It picks the destination from the destinations listed in the turn's capability token (`resolveCapabilityDestination`), then saves through `createCron` in `src/api/app-messaging.ts`. Because the cron has a script, `trialBeforeSave` (`src/cron/script.ts`) first runs the script once for real and refuses the cron unless it exits 0 or 1. `CronStore.create` (`src/cron/cron-store.ts`) writes one JSON row to the `crons` table: owner Ada, home scope `personal:<Ada>`, the schedule, `action` (the task text), `script`, `destination` and the computed `nextFireAt`. The id is a hash of the content, so creating the same cron twice returns the first one.
   - _A person in the web UI_ uses `src/api/routes/crons.ts`. That path rejects a `script` (`CRON_SCRIPT_TOOL_ONLY`), because only the tool path runs the trial.
2. **Queue the next slot.** The store wrapper in `src/wiring.ts` calls `Scheduler.notifyChanged`. `enqueueNext` in `src/cron/scheduler.ts` sends one job to the pg-boss queue `cron-fire` (`createPgBossCronQueue` in `src/cron/job-queue.ts`). The job starts at `nextFireAt` and has a singleton key made of tenant, cron id and slot, so the same slot is queued once.
3. **9:00, claim the slot.** pg-boss gives the job to one worker. `fireJob` rereads the cron, checks that the job's slot is still the cron's next slot, takes the advisory lock `cron-lifecycle:<id>`, and calls `CronStore.claimSlot`. That one update moves `nextFireAt` forward and sets `lastFiredAt`. A stale or duplicate job now finds a different slot and does nothing.
4. **Build the fire.** `fireJob` names the fire `cron:<id>:<slot>` (the fire key) and `fireEnabled` gives it a new conversation, `cron:<id>:fire:<hash>`. Every fire is a fresh conversation with no memory of earlier fires. `renderCronFireInput` wraps the task in a `[Cron runtime context]` block that tells the agent the cron id, the note left by the last fire, and how to keep state between fires.
5. **Admit.** `runTrigger` (`src/triggers/run-trigger.ts`) refuses if Ada is no longer an internal person, checks that she is still a member of the home scope and can still see the destination, and then runs the rest inside `IdempotencyStore.once(fireKey, …)` (`src/idempotency/idempotency-store.ts`). Its first act is to write a `cron_fires` row with status `running`.
6. **Start the turn.** `runTrigger` calls `App.turn` with Ada as the actor, surface `cron`, the fire's conversation, `origin: { kind: "automation", fire: true, destination }` and the fire key as the run's idempotency key. From here it is an ordinary queued run ([turns](./turns.md)).
7. **Script first.** In the orchestrator (`src/core/orchestrator.ts`), a cron turn with a script calls `runCronScript` before any model call. Exit 0 means the script handled the fire: the turn ends `silent` and no model runs. Today the dashboard is red, so the script exits 1. `runCronScript` returns an escalation block that holds the script's output, fenced as data and passed through the security screen ([security](./security.md)). The orchestrator appends it to the turn input and the agent runs with Ada's authority (see `src/cron/authority.ts` below).
8. **Deliver.** The turn returns `ok` with a reply. `runTrigger` hands it to `reachEnqueue` (`src/reach/reach.ts`) with the fire key as the delivery's idempotency key and a provenance record naming the cron, the fire and the session. Delivery posts it to Ada's conversation ([surfaces](./surfaces.md)).
   - _Slack versus web_: only the stored `destination` differs (`type` `slack`, `web`, `principal` or `group`). The fire does not know which surface it reports to.
9. **Record.** `fireEnabled` updates the `cron_fires` row with the final status, a note (the script verdict, then any outcome note), the reply cut to 2,000 characters (ending `...` when it was longer) and the session id. `fireJob` then queues the job for the next slot.

What happens when it goes wrong. A failed fire sends one warning to the destination; later failures in the same streak go only to the fire log. If Ada has left the private channel or group the cron lives in, the cron is deleted. If she is no longer internal, it is disabled. If the process dies mid-fire, the scheduler's repair pass (`redriveHandedOffFires`) fires the same key again after a minute, and the run queue's dedupe key attaches it to the run that already exists. A fire still `running` after `RUN_MAX_AGE_MS` (24 hours by default) is closed as failed.

Where other kinds of fire diverge:

- **Exact-text cron** (`message` instead of `action`): no turn. `runTrigger` enqueues the text for delivery directly.
- **Run now.** `Scheduler.runNow` fires in the process that received the request, with key `cron:<id>:manual:<uuid>`. It is refused while another fire of that cron is running.
- **Inbound webhook.** `POST /v1/webhooks/incoming/:id` (`src/api/routes/webhooks.ts`) reaches `createWebhookReceiver` in `src/webhooks/webhook-receiver.ts`. It verifies the signature, answers handshakes, applies filters, drops duplicates by `webhook:<id>:<deliveryId>`, stores the event in `webhook_history`, starts `runTrigger` without waiting for it, and answers 202. Each delivery gets its own conversation. The turn's input is an envelope (`buildWebhookWakeEnvelope` in `src/wake/wake-envelope.ts`) that holds the stored task as standing orders and the payload as external data, re-serialized as indented JSON when it parses and cut to its head so that it fits 16,000 characters once escaped, which is also what the security screen reads.
- **Job watch.** The `background` tool's `watch` action (`src/agent/agent-tools/computer.ts`) calls the turn's monitor broker (`createMonitorBroker` in `src/monitors/monitor-broker.ts`), which, for a job still running, writes a `monitors` row or updates the one this conversation already holds for that job. `createMonitorPoller` (`src/monitors/monitor-poller.ts`) reads the job's new output every 10 seconds and fires into the same conversation that armed the watch, not a new one. When the watch has a destination, the agent posts its own update with surface tools and `runTrigger` does not enqueue the reply.
- **Gmail-push loop item.** Google posts to `/v1/loop-ingress/gmail` (`src/api/routes/loop-ingress.ts`). `receive` in `src/loops/ingress.ts` verifies Google's token, writes a `loop_ingress_deliveries` row for every enabled Gmail source watching that mailbox, in any tenant, and answers 202. Within seconds the scheduler's maintenance pass calls `maintain`, which reads Gmail history from the saved cursor, upserts items into `loop_items`, and fires the loop with discovery turned off.
- **Many tenants.** A queued job carries its `tenantId` and each handler binds that tenant before touching a store. Sweeps walk tenants with `claimThenBind`. The two public inbound routes find the tenant from the webhook or ingress id ([storage](./storage.md)).

## The parts

### `src/triggers`: how a fire becomes a turn

**Job.** `runTrigger` takes a `TriggerSpec` (owner, home scope, input text, fire key, surface, destination) and returns a `TriggerOutcome`. Every turn this area starts reaches `App.turn` through it.

**Key idea.** Authorization is checked again at every fire, never only at creation. An owner who is no longer internal stops the fire, and a cron, webhook or monitor caller disables the record (a loop stage fails the loop's fire instead). An owner who is no longer in the home scope gets no turn. An owner who can no longer see the destination still gets the turn, but the reply is withheld and the fire is logged `refused`.

**Surprising.** (1) Besides crons, webhooks, monitors and loop stages, three resume flows fire through here: `fireAskResolution` and `fireDropResolution` in `src/triggers/keychain-ask.ts` resume a paused task after a credential owner answers a request or a secret arrives ([credentials](./credentials.md)), and `createApprovalContinuation` in `src/triggers/approval-continuation.ts` runs a fire's request again with the decision once its approval card is answered. (2) Behaviour branches on surface strings. `cron`, `loop` and `keychain-ask` are "scheduled": they report `ownerLeft` when the owner is no longer a member of a private channel or group home, and for a `cron` fire the scheduler then deletes the cron. `monitor` alone delivers through surface tools. (3) A turn that pauses for an approval is logged as `pending_approval` with the note `is waiting on an approval card sent to its owner: …` and delivers nothing; the approval card is the [security](./security.md) area's job. (4) `src/triggers/edit-notice.ts` messages a cron's owner when someone else edits it. (5) `src/triggers/trigger-store.ts` holds data migrations for several tables, not only shared store helpers.

### `src/cron`: store, scheduler, queue, fire log, scripts

**Job.** Keep crons, decide when each is due, fire each slot once, and record what happened.

**Key idea.** The cron row is the truth and the queue is derived from it. Each enabled cron has a pending pg-boss job for its next slot, and a job whose slot no longer matches the row does nothing. Jobs are queued when a cron changes and when a fire completes. A repair pass (`reconcile`, every minute) re-queues any slot due within two minutes, so a lost job costs at most that.

**Surprising.** (1) There are two firing paths. `fireJob` (pg-boss) is the normal one. If the queue cannot start, the scheduler logs a misconfiguration and falls back to `tick`, which scans every cron once a second under the leader lease. (2) Any instance whose scheduler is started works the queue. The leader lease `cron:scheduler:tick` covers only the repair and maintenance loop, not the fires. (3) That maintenance loop also carries unrelated chores through its `sweepAsks` hook: expiring credential requests, loop ingress maintenance and the loops' stale-fire check are wired there in `src/wiring.ts`. (4) Crons live as JSON rows in a generic key-value table, but fires live in `cron_fires` with typed columns. The fire log keeps the newest 100 fires per cron; older ones are pruned once they are 90 days old. (5) A missed slot is owed, not skipped. Pausing a cron leaves `nextFireAt` alone, so re-enabling it fires the stale slot at once. A calendar slot then advances from its scheduled time and an interval slot from the actual fire time, so a calendar cron fires once for every slot it missed and an interval cron fires once. (6) `everyMs` of a day or more is rejected and intervals under a minute are refused: daily work must use `{cron, timezone}`.

### `src/cron/authority.ts`: whose authority a fire carries

**Job.** Copy a record's `owner`, home scope and `botActor` mark into the fire's `TriggerSpec` (`cronTriggerAuthority`, the file's only function). What that authority covers is decided by the code named below.

**Key idea.** The contract is in the master spec: every turn acts with the authority of the person whose instructions it carries, and an audience that includes anyone external removes that authority where the turn's token is minted ([master spec](../SPEC.md)). The record of whose words a task is: whoever rewrites a shared cron's task becomes its owner (`cronTaskRewrite` in `src/api/control-service.ts`, which also drops the script; an org admin's rewrite, and any rewrite of a cron that runs as its scope, keeps the owner), and only its owner or an org admin can change a webhook's task (`editWebhook`).

**Surprising.** The master's Background work paragraph says a fire acts with the authority of the person whose instructions it carries, and that the audience narrows it once, where the token is minted. At this commit a fire carries its owner's authority through the same capability claim a typed turn gets, and a step that needs sign-off raises an approval card. What the code does today:

- A fire is a person's when its origin is `automation` and it is not bot work (`botActor`), a swarm wake or a system actor: `isPersonFire` in `src/sessions/session-syscalls.ts`. When everyone in the conversation is internal, the orchestrator mints the same `personAuthority` capability claim a typed turn gets and opens the owner's keychain on the same terms (`ownerAuthorityTurn`). The `cron` tool's description lists what that covers: the owner's credentials, connections and, for an org admin, admin authority. No record marks who wrote a task; a trigger's owner must be the person who creates it (`assertNoEscalation` in `src/triggers/trigger-store.ts`).
- `carriesPersonAuthority` (`src/api/artifact-share.ts`) reads only that claim and `botActor`, so it is true inside a person's fire when everyone in the conversation is internal (the orchestrator sets the claim only then). Steps that need sign-off raise an approval card: the control service's `createWebhook` (after refusing a caller that fails `carriesPersonAuthority`: "registering a webhook needs its owner's own authority"), sharing an app (refused without that authority, then a card), and loop policy changes in `src/api/routes/loops.ts` (`requireSignOff`). There an agent's request gets 202 `approval_required` with a card for that exact request (`actionApproved` in `src/api/action-approval.ts`), or 403 `approval_unavailable` when it is not tied to a run; creating a loop with a chosen destination, changing a loop's destination, triage or inbox sources, previewing triage and revoking a ship grant pass without a card when the token passes `carriesPersonAuthority`, and a signed-in person passes unless impersonating. `updateWebhook` has no such step: it applies `editWebhook`'s owner rule only.
- Only a loop's owner can instruct its agent on an item (`ownerInstructs` in `src/api/routes/loop-items.ts`), because the item turn runs with the owner's authority. `run-trigger.ts` passes `automated: true` to `turnModelOptions`, which only picks default effort and speed.

### `src/webhooks`

**Job.** Authenticate an inbound HTTP request and turn it into one fire.

**Key idea.** A verifier per scheme (`src/webhooks/verifiers.ts`) answers three questions: is the request authentic, is it a handshake, and what is its delivery id. The delivery id is the dedupe key.

**Surprising.** (1) The 202 does not wait for the turn to be queued, and nothing reads `webhook_history` to re-drive an event. If the process stops in between, recovery depends on the sender retrying. (2) For most schemes the delivery id is a hash of the body, so two identical bodies count as one event for 14 days (the `idempotency` retention). (3) A fire whose owner is no longer internal disables the webhook; an owner who has only left the home scope gets no turn and the webhook stays enabled. (4) A webhook created through the web route is always personal and has no destination; only the `webhook` tool (`src/agent/agent-tools/control.ts`) can attach one.

### `src/monitors`

**Job.** Wake the conversation that started a background job when the job says something worth hearing.

**Key idea.** A poller, not a push. One process holds the lease `monitor:poller:tick`, reads each watched job's output from its saved cursor, and fires on new output (filtered by the watch's pattern), on exit, on expiry, when the job is gone, and as a "still running" heartbeat after a quiet period.

**Surprising.** (1) A watch ends itself: after an exit, expiry or loss fire the monitor is disabled (so is one whose fire fails authorization or whose poll raises `SandboxAccessError`), and a disabled monitor is deleted seven days after the latest of its expiry, last fire and creation. (2) Output fires are spaced at least 60 seconds apart and capped at 20 fires per pass. (3) Patterns are literal alternatives with optional `^` and `$` anchors, not regular expressions (`compileMonitorPattern`). (4) Heartbeat fires tell the agent to finish silently unless something changed. (5) The poller is not stopped by the deployment drain described below; only its lease keeps it to one process.

### `src/loops`

**Job.** Run standing work over a queue of items and hold anything outward-facing until a person, or a standing grant, ships it.

**Key idea.** Two engines sit behind one `LoopFireService.fire` (`src/loops/loop-fire.ts`). A general loop runs staged agent turns through `runLoopFire` in `src/loops/runner.ts`: intake (list candidate items), optional triage, work (one turn per item), judge (a fresh turn decides whether the success condition is met), then ship. Each stage is a `runTrigger` call with surface `loop`. An inbox loop's fire skips those stages except triage. `createInboxPass` in `src/loops/verdict/pass.ts` reads each tracked conversation from Gmail or Slack with the owner's connector token, asks one model call for a verdict and, for `needs_reply`, a second for a draft in the owner's voice; the fire then runs the triage turn when triage is on.

**Surprising.** (1) A loop has no clock of its own. Its schedule is a cron with `loopId`, and `boundLoopCron` (`src/loops/authority.ts`) refuses to fire unless the loop's cron is the one firing, names the loop in `loopId`, and agrees with it on owner and home scope. (2) Stage results come back as fenced JSON inside the agent's reply and are parsed out of the text (`parseIntake`, `parseOutputs`, `parseVerdict`). Much of `loop-fire.ts` is prompt text. (3) An output whose ship action the loop did not declare parks the item and quarantines the loop. (4) By default (a loop's `governor` settings override the numbers) the governor quarantines after three failed fires in a row and throttles when more than half of at least four reviewed outputs were returned; a person must clear a quarantine. (5) Item and decision claims are leases stored on the item row (10 and 5 minutes). (6) There is no loop agent tool. Agents use the `/v1/loops` routes with their capability token. (7) An inbox loop's stored `playbook` is a placeholder; `inboxPlaybook` builds the real text. Inbox ledgers are pruned to 500 items and 30 days. (8) Realtime nudges for inbox loops go through a hidden `conversation` ingress source (`src/loops/inbox-realtime.ts`). They only refresh existing items and carry no message content. (9) The inbox pass reopens a sent or dismissed item when someone other than the owner writes after the last look and the verdict is `needs_reply`. Two other paths bring one back: a newer event for its conversation re-queues it (`mergeIngest` in `src/loops/item-ledger.ts`), and the `reopen` action restores a dismissed or failed one by hand.

**Ingestion** (`src/loops/ingress.ts`, `src/loops/gmail-push.ts`). `receive` authenticates an event and stores a delivery row before answering 202. `process` later moves deliveries into the ledger and fires the loop with discovery off. Failed deliveries retry with backoff from one minute up to an hour; completed receipts are kept 30 days. A duplicate event reuses its item. A newer event for the same conversation supersedes held drafts, but waits while an output is shipping or awaiting confirmation. A paused loop keeps its deliveries; a disabled source rejects new ones. Returned items are worked again even when no new event arrives. For Gmail the first watch starts at the mailbox's current history id (nothing is imported from before), the watch is renewed daily without moving the saved cursor, history is also reconciled every ten minutes, an expired cursor falls back to a full Inbox resync, and the cursor advances only after every item is stored. Disabling a Gmail source never stops the mailbox-wide watch, because another loop may share it. Slack sources have no history reconciliation.

### API: administration, sharing, routes and tools

**Job.** Decide who may change a record, and expose create, edit, run and list to people and agents.

**Key idea.** Cron and webhook routes have two callers and two code paths. A request with a capability token (an agent) goes through `createControlService`. A request from a signed-in person goes straight to the `App` methods in `src/api/app-messaging.ts`. Loop routes take both callers through one path (`actingPrincipal` in `src/api/routes/loops.ts`). The permission predicates are shared: `canAdministerCron` (`src/api/cron-administration.ts`), `canAdministerLoop` (`src/api/loop-administration.ts`) and `canAdministerWebhook` (`src/api/control-service.ts`).

**Surprising.** (1) Who may administer a cron depends on its home scope: its owner; any current member, for a cron owned by a shared scope; a persona manager; the creator; a holder of a write grant ([artifacts](./artifacts.md)); or an org admin. (2) Sharing a cron with a person makes a linked copy that runs as the recipient (`shareCron` in `src/api/app-cron-share.ts`). It starts paused unless the sharer is an org admin, and a cron with a script cannot be shared. (3) A cron's `runtime` override is allowed only on an agent-task cron, not on a loop or exact-text cron (`assertCronRuntime` in `src/cron/runtime.ts`). (4) `src/api/routes/inbox.ts` and `src/api/routes/loop-items.ts` create a person's two default inbox loops on first use (`ensureDefaultInboxLoops`). (5) On a held item, an action its source adapter implements (such as `send`) runs directly with the owner's connector token (`src/loops/sources`) and no agent turn (a bot actor's turn is refused these); the kinds `edit`, `dismiss`, `prioritize`, `ungroup`, `reply` and `reopen` only change the ledger; any other kind runs one (`itemAction`).

### Which core instance runs background work: `src/runs/drain.ts`, `src/runs/instance-registry.ts`

**Job.** When several core processes share one database, keep each background duty in one place and move it cleanly during a release ([deployments](./deployments.md)). A blue-green release depends on layer 2 below.

**Key idea.** Three layers.

1. **The process switch.** With `BACKGROUND_WORK_ENABLED` off, `runtime.start` in `src/wiring.ts` returns early: no run worker, scheduler, monitor poller or sweepers, and `src/start.ts` opens no Slack connection for it ([surfaces](./surfaces.md)). The process still serves the API and the inbound routes, and other processes claim the runs it queues.
2. **The newest deployment wins.** Each process with background work on writes a heartbeat row under its deployment key. `createDrainController` checks every 10 seconds. If a deployment with a different key started later and is alive, this process stands down: it stops claiming runs, stops the cron scheduler and closes its Slack connections, while in-flight turns finish. A newer deployment waits until no older one reports itself running. A stood-down deployment resumes when the newer one retires its heartbeat or stops beating for 30 seconds.
3. **One process per job.** Among processes that are active, pg-boss gives each cron job to one worker, and `LeaderLease.hold(key, …)` lets one process run each periodic job (scheduler repair, monitor polling, retention sweeps).

**Surprising.** (1) Processes that share a deployment key are peers: all of them fire crons. (2) The stand-down covers run claims, the scheduler and Slack only. The monitor poller keeps running on an older deployment and is kept single only by its lease; the same holds for the other sweepers that take one. (3) A deployment's start time is its first process's start, remembered for an hour after its last heartbeat, so a replaced process does not make its deployment look newer. (4) With neither `BACKGROUND_DEPLOYMENT_ID` nor `GIT_SHA` set, the registry is a no-op and a process never stands down. (5) The leases themselves, and what breaks them, are in [storage](./storage.md).

## Optional and per-deployment

Crons, webhooks and general loop machinery are wired in every deployment.

## Where the complexity lives

**Things that multiply each other.** Kinds of fire (cron task, cron exact text, cron script, loop-backed cron, webhook, monitor, loop stage turns, credential resume, secret-drop resume, approval continuation) × kinds of home scope (personal, channel, group, project group, persona) × two delivery styles (core enqueues the reply; the agent posts for itself). All of it meets in `runTrigger`, which branches on surface strings rather than on a typed kind.

**Parallel mechanisms doing one job.**

| Job                         | Mechanisms                                                                                                                                                                         |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Run one fire once           | pg-boss singleton key; `claimSlot`; the `cron-lifecycle` advisory lock; an exclusive `cron_fires` insert for manual runs; `IdempotencyStore.once`; the run queue's dedupe key      |
| Fire due crons              | pg-boss `fireJob`; the interval `tick` fallback                                                                                                                                    |
| Only one process does this  | deployment heartbeats with the drain controller; leader leases; advisory locks (`cron-lifecycle`, `loop-lifecycle`, `loop-ingress`, `loop-intake`); pg-boss job ownership          |
| Receive a signed HTTP event | `src/webhooks` (seven schemes, a turn per event, no durable receipt queue); loop ingress (two of those verifiers, an item per event, its own durable queue with retry and backoff) |
| Work a queue on a schedule  | crons; loops, which add their own store, ledger, output store, grants, governor and runner yet borrow a cron for the clock and the authority check                                 |
| Keep a loop current         | staged agent turns (general loops); the inbox pass, direct model calls with no agent turn (inbox loops)                                                                            |

The master's Wall of shame already records two of these. Overengineering: "the loops subsystem should have just re-used the crons machinery". Non-durability: "webhook work already in flight"; the process-local `inflight` set it names is still in `IdempotencyStore.once`, which writes its durable row only after the work returns. The Hand-rolling lens records hand-built queues beside pg-boss in other areas. The same shape is here: pg-boss carries cron fires and Slack delivery jobs (`src/slack/delivery-jobs.ts`), while loop ingress keeps its own attempt counter and backoff.

**Abstractions with one implementation.** `CronJobQueue` (pg-boss only; it is optional in `SchedulerDeps`, which is what keeps the tick path alive) and `CronFireStore` (Postgres only).

**Transitional code.** Migrations in `src/cron/fire-store.ts` that copy and then drop a `cron_fire_log` table. Migrations for crons, webhooks, loops and monitors that live in `src/triggers/trigger-store.ts`, `src/cron/cron-store.ts` and `src/wiring.ts`.

## Contracts

**Inbound webhook.** `POST /v1/webhooks/incoming/:id`, public. Verification by the webhook's scheme:

| Scheme              | The request must carry                                                                                                                                                    | Delivery id                     |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| `hmac-sha256`       | `X-Signature`: hex HMAC-SHA256 of the raw body with the secret (an optional `sha256=` prefix is accepted)                                                                 | SHA-256 of the body             |
| `github`            | `X-Hub-Signature-256: sha256=<hex HMAC of body>`. `X-GitHub-Event: ping` is answered `pong`.                                                                              | SHA-256 of the body             |
| `slack`             | `X-Slack-Signature: v0=<hex HMAC of "v0:<timestamp>:<body>">` and `X-Slack-Request-Timestamp` within 5 minutes. A `url_verification` body is answered with its challenge. | body `event_id`, else body hash |
| `stripe`            | `Stripe-Signature: t=<timestamp>,v1=<hex HMAC of "<timestamp>.<body>">`, within 5 minutes                                                                                 | body `id`, else body hash       |
| `linear`            | `Linear-Signature`: hex HMAC of the body, and body `webhookTimestamp` within 60 seconds                                                                                   | SHA-256 of the body             |
| `token`             | `Authorization: Bearer <secret>` or `?token=<secret>`                                                                                                                     | SHA-256 of the body             |
| `standard-webhooks` | `webhook-id`, `webhook-timestamp`, `webhook-signature` per the Standard Webhooks library                                                                                  | `webhook-id`, else body hash    |

Responses: 202 `{"ok":true}` accepted (the turn has not run yet); 200 with text `skipped` (filters did not match), `duplicate`, or the handshake body; 401 verification failed; 404 unknown or disabled; 413 body too large. A form-encoded body with a `payload` field is parsed as JSON. Filters are `[{path, in}]`: every dotted `path` must resolve to a value whose string form is in `in`. The secret is shown once at creation and listed as `***` afterwards.

**Loop ingress.** `POST /v1/loop-ingress/:id`, public, JSON body of at most 64,000 bytes. A `webhook` source checks `X-Signature` as `hmac-sha256` above; its secret is generated and returned once. The whole JSON object is untrusted input to the playbook; an optional `title` becomes the item summary. A `slack` source checks the Slack signature with the app's signing secret and accepts only `message` events with text, from a person, without a subtype, in the configured workspace (`T…`) and channels (`C…`, `D…`, `G…`). Replies share their thread's item; a direct message uses the channel id as its key. This is the HTTP Events API and is separate from the deployment's own Slack connection. Responses: 202 `Accepted`; 200 `Skipped` or the challenge; 400 not JSON, or a Slack event with a bad timestamp; 401 `Invalid signature`; 404 unknown, disabled, or owner not enabled; 413 too large.

**Gmail push.** `POST /v1/loop-ingress/gmail`, public. The request must carry `Authorization: Bearer <JWT>` signed by Google (RS256, issuer `accounts.google.com` or `https://accounts.google.com`), with audience equal to `GMAIL_PUBSUB_AUDIENCE`, `email` equal to `GMAIL_PUBSUB_SERVICE_ACCOUNT`, and `email_verified` true. The body is the wrapped Pub/Sub message whose base64 `message.data` decodes to `{emailAddress, historyId}`. `GMAIL_PUBSUB_TOPIC` is the topic name passed to Gmail's watch call, on labels `INBOX` and `SENT`. Gmail sources are allowed only on a personal loop and use the owner's personal Gmail connection. **[interpretation: the Google-side setup is not in this repo, which only checks the token above and passes the topic name to the watch call]** On the Google side this needs a Pub/Sub topic that Gmail may publish to, and an authenticated push subscription to this route with that audience and service account.

**Through the portal.** The portal forwards the webhook path and both ingress paths to core without a sign-in (`plugins/portal/src/index.ts`). It passes only `Authorization` and the headers listed in `FORWARD_WEBHOOK_HEADERS` (`plugins/portal/src/proxy.ts`), so a new scheme's signature header must be added there.

**Cron script.** At a fire, exit 0 means handled and no agent turn runs. Any other exit, a timeout or a failure to start wakes the agent with the output. When a script is set, its trial run must exit 0 or 1 or the change is refused. A script runs through the fire turn's own `execute` path with the credential handles and sandbox named in it, so it can use only what that turn could.

**Schedule.** `{cron, timezone}`: a five-field expression and an IANA timezone. `{everyMs}`: from 60,000 up to, but not including, 24 hours; first fire one interval from now unless `firstFireAt` is also given. `{firstFireAt}`: epoch milliseconds, at most five minutes in the past; fires once and the cron is then disabled.
