# Agent turns

_Verified against `main` at d1de9e2d2 (2026-11-24). Statements were read in the code at that commit unless marked **[interpretation]**._

## In one paragraph

A turn is one unit of agent work on one conversation: a message comes in, the model thinks and calls tools, and everything that happened is written down. QM turns a message from any source (the web app, Slack, a cron timer) into a _run_, a row in the `runs` table in Postgres that works as a queue. A worker claims the run. That claim is the conversation's only turn lock: a conversation has at most one running run, and every item the turn appends to the log first checks that its claim still holds. The worker rebuilds the model's view of the conversation from the conversation's permanent log (the `items` table), assembles a prompt and a set of tools, and hands both to Pi, the vendored agent loop that talks to the model. Each model step, tool call and tool result is appended to the log as it happens. What a worker holds in memory is not durable: the Pi session is rebuilt from the log at the start of every segment, and the live text stream's partial text is lost with the process. When the loop ends the reply is already in the log, and the run row is marked done with a small result. If the worker dies midway, its claim expires, another worker claims the same run, reads the log, and carries on from what was recorded.

## One message, traced end to end

Ada at Acme opens the web app, types "summarize this PDF" and attaches `q3.pdf`. Side notes show where a Slack mention, a cron fire and a deployment with many tenants differ.

1. **Upload and HTTP intake.** The browser uploads the file first and receives a blob id (see [web-clients](./web-clients.md)). It then sends `POST /v1/web/turn`. `webTurn` (registered in `webTurnRoutes`, `src/api/routes/web-turns.ts`) builds a `TurnRequest` (`src/types.ts`): surface `web`, the signed-in person as actor, origin `{ kind: "human" }`, the thread ref `web:<person>:default` (or the one the client names), the attachment's blob id, and the client's idempotency key prefixed with the person. It passes the request to `postTurn` in `src/api/routes/turns.ts`, which drops the fields only core may set and calls `turn` with `async: true`.

2. **Admission.** `turn`, built by `createTurnMethods` in `src/api/app-turn.ts`, decides whether this message may start work, and what kind. It resolves the actor to a principal and refuses anyone who is not internal (see [scopes](./scopes.md)), checks write access to the conversation and that the requested model is allowed, and builds the request that will be stored. If a run already carries this idempotency key, it returns that run. It asks `routeIncoming` in `src/wake/route-incoming.ts` what the message is to any live run in the thread: a new turn, a steer into the live run, a stop, or nothing. No run is live, so `enqueue` inserts a `pending` row into `runs` and the HTTP call returns `202 { status: "queued", runId }`. Nothing has been written to `items` yet.
   - _Typed mid-turn:_ had a run been live, the same call would have sent it a `steer` signal instead of enqueueing (step 7). The text `stop` on its own aborts the live run and its subagents.
   - _Slack mention:_ the Slack adapter builds the same `TurnRequest` with surface `slack` and a `redeliveryKey`, so a redelivered Slack event does not start a second run. For a channel or group conversation (not an external-audience request and not an approval decision), `turn` wraps the text of a `human`-origin message in a wake envelope (`buildWakeEnvelope` in `src/wake/wake-envelope.ts`) and sets `surfaceTools`: the agent answers by calling the surface's tool, which carries the surface's name rather than `surface` (`surfaceName`, default `slack`, in `surfaceTool`, `src/agent/agent-tools/surface.ts`), and the run's result is `silent`. See [surfaces](./surfaces.md).
   - _Cron fire:_ `runTrigger` in `src/triggers/run-trigger.ts` runs the fire inside `once` (`src/idempotency/idempotency-store.ts`), which skips a fire key that already completed. Inside it calls the same `turn` with origin `{ kind: "automation", fire: true }` and without `async`, so the call waits for the run to finish (`awaitRun` in `src/api/app-helpers.ts`), for at most the deployment's turn wall clock (the run's maximum age when that is 0) plus 60 seconds. See [background-work](./background-work.md).

3. **Claim.** `createWorker` in `src/runs/worker.ts` keeps a fixed number of slots. The insert sent a `qm_run_available` notification; a worker with a free slot calls `claim` on the store built by `createPostgresRunStore` in `src/runs/postgres-run-store.ts`. One SQL statement picks pending runs by priority, then age. It skips locked rows, runs still inside their retry delay, and any conversation that already has a running run, an earlier pending one, or a pending one still inside its retry delay. It sets `status = 'running'`, a fresh `lease_token`, `lease_expires_at`, and `attempts + 1`. A unique index allows one running run per conversation. `processRun` starts a heartbeat that keeps extending the expiry, and calls `handleTurn` with the run id, attempt number and lease token.
   - _Priority:_ `runPriority` in `src/runs/run-store.ts` gives priority 0 to a run whose origin is `human`, `direct` or a live `ambient` message, 1 to a delegated run whose delegating run has priority 0 or 1, and 2 to everything else: swarm runs, automation, other `ambient` runs, and delegated runs whose delegating run has priority 2 or cannot be found. `createRunPreemption` asks a priority-2 run to give up its slot when a person's run is waiting, at most three times per run (`MAX_PREEMPTIONS`); the run stops at its next model request and is requeued.
   - _Many tenants:_ the claim goes through a database function that sees every tenant's rows; `processRun` then binds the run's tenant with `withTenant` before anything else reads or writes. See [storage](./storage.md).

4. **Preparation.** `handleTurn`, on the object built by `createOrchestrator` in `src/core/orchestrator.ts`, does everything that must happen before the model is called. It checks the audience and spend limits (`src/core/orchestrator/admit.ts`), resolves the scope and its policies ([scopes](./scopes.md)), screens the untrusted parts of what came in unless the deployment's screening mode is `off` ([security](./security.md)), and finds or creates the `sessions` row with `getOrCreateByThread`. What is screened (`buildInboundScreen` in `src/core/orchestrator/security-screen.ts`): the conversation header, place metadata, overheard messages, attachment metadata, text attachments under the size cap, inbound file notes, the sender's display name on an ambient turn, and the turn's text when it came from another session, is an automated run's `screenData`, or arrived on the `monitor` or `webhook` surface. The words a person typed for their own turn are not screened (`wordsToScreen` in `src/core/orchestrator/intake.ts`). It builds the prompt blocks ([context](./context.md)), the credential catalog and capability tokens ([credentials](./credentials.md)), the sandbox handles ([sandboxes](./sandboxes.md)) and the tool context (`createToolContext` in `src/tools/primitives.ts`). It also builds a `SessionWriter` holding the session id, the run id and the lease token. Every item the turn appends later goes through it.

5. **The attachment.** `materializeInbound` in `src/core/attachments.ts` reads the blob and registers `q3.pdf` as a file artifact ([artifacts](./artifacts.md)). `loadDocumentInputs` in `src/core/documents.ts` loads the bytes back from the artifact store, checks authorization and the content hash, and keeps the document if it fits the turn's limits. The document's content is never written to the log: the user item records only the attachment's metadata and artifact id. On each model request, `withDocumentInputs` in `src/agent/document-inputs.ts` adds the document to the last user message, as a native file block when the model route accepts PDFs, otherwise as extracted text.

6. **History and the user message.** `getContextWindow` in `src/sessions/session-items.ts` returns the items whose `seq` is above the `through_seq` of the latest `ContextCompaction` item that has summary text, or every item when there is none. `handleTurn` calls `runTurn` on the agent made by `createAgent` in `src/agent/agent-run.ts`. `reconstructMessagesFromHistory` in `src/agent/replay.ts` turns the items back into the provider's message list, and Pi's `createAgentSession` starts a fresh in-memory session seeded with them. `openTurnPrompt` in `src/agent/turn-open.ts` appends Ada's text as a `UserMessage` item. That append stores the item's `seq` on the run as `turn_user_seq`, which is how a later attempt finds this turn in the log.

7. **The model loop.** Pi sends the request, streams the answer and runs the tool calls. `createStepRecorder` in `src/agent/step-recorder.ts` writes each model response as `Reasoning`, narration `AgentMessage` and `ToolCall` items, and each tool result as a `ToolResult` item. Each of these items records its step in `body.wire.message` (step id, API, provider, model, stop reason); a block's other fields go in the item's columns and `body`, and `body.wire` adds only what those cannot reproduce, so replay can rebuild the provider's blocks. Every write goes through `appendMany` in `src/sessions/session-items.ts`: one transaction takes a per-session advisory lock, checks that the run still holds its claim, and inserts. A failed write aborts the turn. While the loop runs, `startSignalPoll` in `src/runs/run-signal-store.ts` delivers signals: a `steer` is pushed into the live Pi session and recorded as a `SteeringMessage` item (a steer the security screen withholds is recorded instead as an `Error` item with code `steer_withheld` and without its text), and an `abort` stops the session. Text deltas go to `publish` in `src/runs/turn-stream.ts` and reach the browser through `GET /v1/runs/:id/events` (`src/api/routes/run-events.ts`).

8. **Settle.** When Pi stops, `runTurn` appends the reply as an `AgentMessage` item. `selectTurnResult` in `src/core/orchestrator/settle.ts` picks the result: `ok` with the reply (and any pending approvals), `silent`, `pending_approval`, or `refused` when a step needs approval and the turn's actor is a bot or a system actor, so nobody can approve it. `processRun` calls `complete`, which stores the result on the run and sets `status = 'done'`. The browser's event stream sees the run finish, and the web app renders the conversation from `items`.
   - _A tool needed approval:_ the tool does not run. It returns a result that ends the Pi loop, the pending approval is stored, and the run completes with `pending_approval`. The person's decision arrives as another `TurnRequest` carrying `approval`. If the approval stored the call, the decision is a denial or an approval for this one call (scope `once`), and that same person's run in the conversation is still `running` with an unexpired lease, is not a session turn, and has origin `human`, `direct`, live `ambient` or an automation fire, the decision is delivered to it as a steer. Otherwise it starts a new run, which executes the stored call before prompting the model (`replayApprovedCalls` in `src/agent/turn-open.ts`). The policy is in [security](./security.md).

9. **The worker dies midway.** Say the process is killed after the model called `execute` and before a result was written. No heartbeat arrives, so `lease_expires_at` passes. `createReaper` in `src/runs/reaper.ts` sweeps on a timer, and `turn` pokes it whenever a person sends a message. `reapExpired` first replaces the run's lease token, so a late write from the old worker is refused, then sets the run back to `pending`. Another worker claims it, and `attempts` is now 2. `handleTurn` loads the turn that starts at `turn_user_seq`. If that turn already has a reply, `replayRecordedAnswer` in `src/core/orchestrator/turn-replay.ts` returns it without calling the model. Otherwise `reconcile` in `src/core/turn-resume.ts` looks for tool calls that have no result. A single such call that the model marked `retrySafe`, and whose arguments were recorded for a re-run (at most 4,000 characters of JSON), is run again. Any other gets a `ToolResult` item marked `interrupted`. Then the model continues from the log, and Ada's message is not appended a second time. A run that keeps losing its claim is failed after `MAX_CLAIMS` claims. A run that keeps throwing is failed after `MAX_ATTEMPTS` errors, and `handleTurn` writes an `Error` item on the last attempt.

## The parts

### `src/api/app-turn.ts`, `src/api/start-session.ts` and the routes

**Job.** Admission. `turn` accepts or refuses a request, deduplicates it, routes it relative to live work, and enqueues a run. The same file answers questions about runs (`getRun`, `activeRunForThread`) and handles signals, edits and withdrawals of queued runs. `src/api/routes/turns.ts` and `src/api/routes/web-turns.ts` are thin HTTP shells. `startSession` creates or forks a session and sends its first message through `turn`.

**Key idea.** `turn` only decides and enqueues. It never calls the model and never writes to `items`.

**Surprising.** `turn` returns `queued` when called with `async`; without it, the call blocks until the run finishes, throws if that takes longer than the deployment's turn wall clock (the run's maximum age when that is 0) plus 60 seconds, and returns `queued` if the process is shutting down. A message can be consumed without starting a run: steered into the live run, treated as a stop, or recognised as a duplicate. An approval decision is a `TurnRequest` too.

### `src/wake`

**Job.** `routeIncoming` decides what an incoming message does when its conversation already has a live run: start its own turn, steer into the live one, stop it, or be dropped as empty. `buildWakeEnvelope` and its siblings render the text of event-driven turns. `createWakeSweep` pokes the reaper for engaged conversations that have no live run.

**Key idea.** `routeIncoming` is a pure function of the message, the live turn and the sender's `midTurn` preference. A person's message that is exactly `stop` (after an optional mention of the agent, with an optional `.` or `!`) is a halt (`isHalt`).

**Surprising.** A message steers the live run only when both use the same model account; otherwise it queues as its own turn. A bot's message never stops a person's work. `createEngagedRegistry` keeps its list in process memory.

### `src/idempotency`

**Job.** `once(key, fn)` runs `fn` at most once per key. Scheduled and event fires use it through `runTrigger`. **Key idea.** The key is written only after `fn` succeeds. **Surprising.** It is not the dedup for typed messages: those use `runs.idempotency_key`. The in-flight guard is a process-local set, so the durable check covers only fires that already committed; the master's Non-durability lens records the webhook case.

### `src/runs`

**Job.** The queue: enqueue, claim, heartbeat, complete, fail, requeue, reap. Also signals to live runs, the live text stream, and stopping claims when a newer build is live (`src/runs/drain.ts`).

**Key idea.** One `UPDATE` claims a run, and the rule "one running run per conversation" lives in that statement and in a unique index. The claim's token is the fence: `complete`, `fail`, `heartbeat` and every item append the turn makes name it, and the reaper swaps it before requeueing.

**Surprising.** `runs.session_id` holds the thread ref, not `sessions.id`. `attempts` counts every claim; `error_attempts` counts only thrown failures; `handbacks` counts voluntary releases (shutdown, preemption, a held turn) and is subtracted before `MAX_CLAIMS` applies. On shutdown a worker hands its runs back rather than failing them. Three heartbeats in a row that find the claim gone cancel the turn in the process that lost it; a heartbeat that throws resets the count. The turn stream is process memory relayed over `NOTIFY`; a crash loses the partial text, and the recorded items remain.

### `src/core/orchestrator.ts` and `src/core/orchestrator/`

**Job.** `handleTurn` runs one attempt of one turn: prepare, load history, call the agent, settle. The directory holds the pieces it calls: `admit.ts`, `intake.ts`, `security-screen.ts`, `approvals.ts`, `credential-catalog.ts`, `capability-tokens.ts`, `sandboxes.ts`, `turn-prompt.ts`, `prompt-blocks.ts`, `compaction.ts`, `settle.ts`, `turn-replay.ts`.

**Key idea.** The orchestrator owns every write to the log during a turn. The agent receives an `emit` callback; each item the agent produces goes through it to the session store with the run's claim.

**Surprising.** `handleTurn` is one very long closure, and the session row is found or created well into it, after admission, resolution and screening. After the result is returned, title generation, memory capture and sandbox release keep running. A turn can contain several agent segments: the `runtime` and `context` tools end a segment and `handleTurn` starts another on the new model or the trimmed history, up to eight times. Compaction has three entry points: before the turn when history exceeds 90% of the budget, in the background after the turn above 70%, and a trim without a summary when the summary call fails, when there is nothing to summarize, when the agent has no `compactHistory` or the scope is a managed group, or when the agent calls the `context` tool.

### `src/core` — resume, errors, attachments, documents

**Job.** `src/core/turn-resume.ts` reads a partial turn from the log and decides how to continue. `src/core/turn-error.ts` defines the error classes that decide retry. `src/core/attachments.ts` and `src/core/documents.ts` take files in.

**Key idea.** Resume reads only the log and the run row (`turn_user_seq`, `last_stop`).

**Surprising.** `NonRetryableTurnError` and non-retryable provider errors fail the run at once, except a spent model budget (`model_budget`), which `handleTurn` returns as a `refused` result after `handleModelBudgetCap` has worded the refusal and queued a once-a-day notice to the organization's admins ([models](./models.md)). `HeldTurnError` requeues it after a delay without counting an error. A file is a document by its extension, or by its MIME type when the extension says nothing. Images take a separate path: PNG, JPEG, GIF and WebP files up to 5 MB go to the model as image blocks. A document is included only in the turn it arrives in, including uploads steered in mid-turn; a note in that turn says so and names the artifact id for later turns. A resumed attempt reloads the turn's documents from the artifact store. At most ten documents and 8 MB per turn, newest first, within half of the history token budget; a PDF counts 3,000 tokens per page. What does not fit becomes a note telling the agent how to fetch the file. Text extraction runs in a worker thread with a ten-second deadline and memory and decompression limits, capped at 200,000 characters per document and 100,000 characters across the fallback text. Legacy `doc`, `xls`, `ppt`, Pages and Keynote files have no local parser, and a scanned PDF has no extractable text: both need a route with native file input. If the provider rejects a request that carries inline documents, the turn retries once with the documents replaced by notes. When screening is enforced, a document too long to screen in full is withheld, and one that cannot be screened as text is flagged as unscreened in the turn's notes.

### `src/agent`

**Job.** Drive Pi for one segment (`runTurn` in `src/agent/agent-run.ts`), rebuild messages from items (`src/agent/replay.ts`), record steps (`src/agent/step-recorder.ts`), and offer one-shot model calls for titles, summaries, the ambient "should I respond" check and judging (`ModelUtilities` in `src/agent/agent.ts`). Model choice is in [models](./models.md).

**Key idea.** There is no long-lived model-side session. Every segment starts a fresh in-memory Pi session from the log.

**Surprising.** Pi comes from two vendored packages, `@earendil-works/pi-coding-agent` and `@earendil-works/pi-ai`, installed from release tarballs of this repository. `runTurn` can prompt the model again without a new user message, for five reasons: a provider refusal, an unavailable model, a spent model budget, or an auth or account failure (retry on the fallback model; a transient provider error is not one of these), a rejected document, an open goal, an empty final message, and a reply check that retracts or prods. Item writes are queued on one promise chain so they land in order.

### `src/agent/agent-tools/`, `src/agent/agent-tools.ts` and `src/tools`

**Job.** `createAgentTools` assembles the tools the model sees. `createToolContext` in `src/tools/primitives.ts` implements what they do. Subagent tools are in [delegation](./delegation.md).

**Key idea.** Two layers joined by `ToolContextRef`: tool definitions hold schema and wording, the tool context holds authority.

**Surprising.** Every tool is wrapped, from the inside out, by `withToolApprovalGate`, `withToolSpan`, `withRuntimeBarrier` and, except for client-side tools, `withRetrySafety` (`src/agent/agent-tools/wrappers.ts`); `execute`, `background` and `sandbox` get `validateSandboxTool` innermost. `withRetrySafety` adds an optional `retrySafe` argument to the schema of each tool it wraps whose schema is an object without that field; resume reads it. The tool list is not fixed: read-only, ephemeral, app-edit and delegate turns each filter it. Several tools call core's own HTTP API with the turn's capability token (`src/tools/self-api.ts`, `src/tools/admin.ts`) rather than calling functions in process.

### `src/agent/goal.ts` and `src/agent/agent-tools/goal.ts`

**Job.** Keep a session working toward a stated objective. `enforceGoal` re-prompts the model while the goal is active or its floor is unmet. A governor model reviews progress every three rounds or thirty minutes and may pause the goal, but only when its previous verdict was `step_back`: a first `pause` is recorded as `step_back`.

**Key idea.** The goal is a row, so it survives the turn; each turn banks its active time and tokens into it.

**Surprising.** A goal extends the turn's wall-clock cap until the floor is met. Only the governor's agreement completes a goal.

### `src/sessions`

**Job.** The log and the session rows: append, read, context window, participants, pins, goals, search, spend rollups, model request captures. `forkSession` in `src/api/app-sessions.ts` copies a viewer's visible items into a new session and stamps `forked_from_session_id` and `fork_boundary_seq`.

**Key idea.** `items` is append-only. Triggers refuse updates and truncation, and a row can be deleted only by deleting its session; two one-time migrations in `src/sessions/session-schema.ts` switch the triggers off to delete stopped placeholders and to backfill call ids. Corrections are new items: `Retraction`, `Stop`, `ContextCompaction`.

**Surprising.** Code reads and writes `Item` directly; there is no second transcript shape. Compaction deletes nothing: it appends a summary with `through_seq`, and readers start after it. A session holds at most one `ToolCall` and one `ToolResult` per call id, enforced by an index and raised as `DuplicateCallError`. Much of the directory is delegation (`session-syscalls.ts`, `subagent-mail.ts` and neighbours); see [delegation](./delegation.md). There is no session lock table: `session_leases` is created by the base schema and dropped by a later migration.

### Failure reporting — `src/util/errors.ts`, `src/admin/error-log.ts`, `plugins/chassis/src/error-reporting.ts`

**Job.** Record failures where an operator will see them. `reportFailure` logs a failure and, if reporting is configured, sends it to Sentry. `ErrorLog.record` writes an `error_events` row for the admin errors view and reports the same event. Uncaught exceptions and unhandled rejections are reported too; an unhandled rejection flushes for up to two seconds and exits with failure only when reporting's handler is the sole listener; `core` and `worker` register their own (`shutdownOnUncaught` in `src/util/process-guard.ts`), which shuts the process down instead. Published-app failures use the same record (`deploy:app_start_failed`, `deploy:app_restarted`, `deploy:app_down`; see [artifacts](./artifacts.md)).

**Key idea.** One error object is reported once: `markErrorReported` tags it, and later reporters skip it.

**Surprising.** Unless the error is one QM raised on purpose or a classified provider error, a failed turn shows the person one generic sentence; the detail is in `error_events`. Provider decisions (a refusal, an account problem, a spent budget) are recorded but not sent to Sentry. Sentry events are not redacted: messages, cause chains, stacks and the record's fields are sent as they are. Only errors and, when enabled, traces are sent; traces are scrubbed down to an allowlist. Four services initialise reporting: `core`, `worker`, `portal` and `auth`.

## Where the complexity lives

**Things that multiply each other.**

- _Request fields × origins × surfaces._ `TurnRequest` has dozens of optional fields and `handleTurn` reads most of them, branching on origin kind, `surfaceTools`, `botActor`, `approval`, `swarm`, `ephemeral`, `privateSessionMessage` and more. The master's God files lens records the orchestrator.
- _How a run stopped × how it resumes._ Four stop kinds (`shutdown`, `parked`, `lease_expired`, `error`), four counters, four limits (`MAX_ATTEMPTS`, `MAX_CLAIMS`, `MAX_PREEMPTIONS`, `RUN_MAX_AGE_MS`), and five resume outcomes (replay the recorded reply, run again from the user message, continue, re-run one call, mark calls interrupted).
- _Re-prompts inside one segment._ Fallback model, document retry, goal continuation, empty-ending nudge and reply check can each follow another, and a runtime change wraps all of them in a new segment.
- _Mid-turn routing._ `routeIncoming` combines origin, who started the live run, model account, bot flags and the sender's preference. `turn` adds approval decisions, redelivery keys and steering of queued runs on top.

**Parallel mechanisms doing one job.**

| Job                                | Mechanisms                                                                                                                                                                                                    |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| "This already started work"        | `runs.idempotency_key`; `redeliveryKey` checked against runs and signals; `run_signals.dedupe_key`; the `idempotency` table; the one-call-per-kind index on `items`                                           |
| "Only one of us does this"         | the run claim; the per-append advisory transaction lock; leader leases for the reaper and the wake sweep; named advisory locks (`session-tree-admission`, `run-signal-replay:<runId>`); `instance_heartbeats` |

| Rebuilding an assistant message    | the step recorded in `body.wire.message`; `legacyAssistant` in `src/agent/replay.ts` for items without one                                                                                                    |

**Abstractions with one implementation.** `RunStore`, `RunSignalStore`, `RunActivityStore` and `SessionStore` each have one Postgres implementation, yet callers still guard optional members such as `subscribeAvailable` and `deps.signals`. `Agent` has one implementation, `createAgent` (wrapped by `withResolvedRuntime` in `src/wiring.ts`), and every `ModelUtilities` method is optional.

**Transitional code.** `handleTurn` derives `personFireTurn`, `speakerTurn` and `personAuthorityTurn` from the origin. The earlier attended/unattended split (`triggeredTurn`, `liveTurn`, `liveAuthorTurn`) is gone; its request keys (`triggered`, `liveActor`) are read only by migrations (`src/surfaces/origin-migration.ts`, `src/surfaces/published-upgrade.ts`, `src/sessions/session-schema.ts`). `src/sessions/legacy-history-migrations.ts` and `src/sessions/published-upgrade.ts` carry older databases onto `items`; the master's Historylessness lens records the history.

## Contracts

**Submitting a turn.** `POST /v1/turns` takes a `TurnRequest` as JSON. `surface`, `text`, `actor.externalId` and `conversation` are required. `?async=1` or `"async": true` returns as soon as the run is queued. The response is `202` when the status is `queued`, `403` when it is `refused`, and `200` for every other status (`ok`, `silent`, `pending_approval`, `failed`, `react`). The route drops `surfaceOrigin`, `spawned`, `cronScript`, `infrequentCron`, `redeliveryKey` and `gatewayContext.hostIds`, and rejects an `idempotencyKey` that starts with `slack:`.

**Signalling a run.** `POST /v1/runs/:id/signal` takes `{ kind }` with `abort` (optional `tree`), `steer` (`text`, optional `ts`, `request`, `queuedRunId`, `remark`) or `client_result` (`callId`, `result`). It answers `200` when accepted, `404` when the run is not visible, `400` for an invalid `kind`, `request` or `client_result` body, missing text or a request for another conversation, `403` when the caller's portal identity does not match the actor in `request`, and `409` with `{ accepted: false, reason }` otherwise.

**Run event stream.** `GET /v1/runs/:id/events` is a server-sent event stream. Each `data:` line is JSON with a `type`: `RUN_STARTED`; `TOOL_CALL_START` (`toolCallId`, `toolCallName`, `args`); `TOOL_CALL_RESULT` (`toolCallId`, `content`, `isError`); `CUSTOM` with `name` `run` (the full run view), `delta` (`offset`, `delta`, `startOffset`) or `reasoning` (`step`, `index`, `offset`, `delta`); and `RUN_FINISHED`. Event ids are `tool:<callId>:start`, `tool:<callId>:result`, `text:<offset>` and `done`.

**Document blocks by model route** (`nativeDocumentFormat` in `src/agent/document-inputs.ts`). Text fallback reads UTF-8 text and code, CSV, TSV, IIF, PDF, DOCX, XLSX, PPTX, ODT, ODS, ODP and RTF. Every extracted result says that images and charts are not included, and says so when no text could be extracted or the text was cut. Any other accepted format (DOC, XLS, PPT, Pages, Keynote and the other legacy Office extensions) has no text fallback: where a row below says extracted text, the model is told the document could not be included.

| Route                                                                           | Sent as a native file                                                                                                                                  | Everything else                                                |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------- |
| OpenAI Responses (OpenAI, or a gateway model marked for files)                  | PDF on vision models; every other accepted format except ODS, ODP and RTF (Word, Excel, PowerPoint, Pages, Keynote, ODT, CSV, TSV, IIF, text and code) | ODS, ODP, RTF, and PDF on non-vision models, as extracted text |
| Anthropic Messages (Anthropic or the QM gateway)                                | PDF on vision models; text files as plain-text document blocks                                                                                         | extracted text                                                 |
| OpenAI Chat Completions (OpenAI, or a gateway model with a document capability) | PDF on vision models                                                                                                                                   | extracted text                                                 |
| OpenRouter Chat Completions                                                     | PDF on vision models whose id starts with `anthropic/`, `google/` or `openai/`, with the `file-parser` plugin set to its native engine                 | extracted text                                                 |
| Gemini and Vertex                                                               | PDF on vision models                                                                                                                                   | extracted text                                                 |

**Traces sent to Sentry.** With tracing on, each HTTP request is an `http.server` root span named by its route template (unregistered paths are `METHOD /*`). Each run attempt is a `queue.process` root span named `run`, with `messaging.message.id` (the run id), `messaging.message.retry.count`, `messaging.message.receive.latency` (queue wait in ms), `qm.surface`, `qm.origin`, `qm.tenant`, `time_to_model_request`, `time_to_first_text`, and `qm.cancelled` when the attempt was stopped, handed back or requeued. Runs with origin `human` are always sampled; other roots follow the sample rate or inherit the decision of the trace they continue, including one named by a caller's `sentry-trace` header. Spans are sent as they finish, so a stopped run keeps the spans it completed. A run stores the `sentry-trace` value of the request that queued it in `runs.request.trace`, so its span joins that trace; swarm runs never store one. Child spans are `turn.memory_snapshot`, `turn.memory_recall`, `turn.skills`, `turn.credentials`, `turn.decision`, `turn.dispatch`, `model.first_token`, `step.gap`, `step.tool` (named by the tool), `step.persist` and `sandbox.provision`. Database spans are named by SQL verb and outgoing HTTP spans by method and origin; URLs, headers, bodies, SQL text and database error text are dropped. Health checks and event streams are not traced. Trace context is sent only to the origins in `CORE_API_URL` and `AUTH_BROKER_UPSTREAM`. A recorded failure carries an `error_code` tag and a matching fingerprint, and its log line carries `[sentry=<event id>]`.
