# Credentials and connectors

_Verified against `main` at eb148f69d (2026-11-24). Statements were read in the code at that commit unless marked **[interpretation]**._

## In one paragraph

A credential is anything that lets a command or an API call act as someone: an API key, a saved command-line login, an OAuth token. QM keeps them encrypted in one Postgres-backed store, the _keychain_, and gives the agent names for them, never values. At the start of a turn core works out which credentials this conversation may use and lists their _handles_ in the prompt. The agent asks for one by naming its handle in the `credentials` argument of the `execute` tool, and core delivers it to that one command. The safest delivery is _brokered_: the command gets a short-lived token, sends its HTTP request to core, and core adds the real key on the way out. The weaker deliveries put a value on the computer for the length of one command, as an environment variable or as login files. A person's OAuth connection to a built-in provider (a _connector_) is delivered the same way, as a variable holding a fresh access token. Two routes never reach the computer at all: MCP servers an admin registered and third-party _app connections_ (Composio). Core calls both itself. Every call from a sandbox back to core is authorized by a _capability token_: a signed, expiring statement of who the turn acts for and where. Only the keychain and capability tokens are part of every working deployment; everything else here is off until an operator, an admin or a person sets it up.

## One credential request, traced end to end

Ada at Acme writes in her own web conversation: "List the open issues in acme/api that mention rate limits, then search the web for how others fixed it." Ada has saved a GitHub token in her keychain (service `github`, environment variable `GITHUB_TOKEN`) through a secret drop, so the token never passed through chat. Acme's admin has stored an org credential `web-search`, brokered, pinned to `api.search.example`, and granted it to the whole org.

1. **Build the catalog.** Inside `handleTurn` (`src/core/orchestrator.ts`), `createCredentialCatalog` (`src/core/orchestrator/credential-catalog.ts`) decides whether Ada's own credentials are usable here (`ownCredentialsAllowed`: yes in her personal scope). Four functions then fill the catalog: `registerKeychainCredentials`, `registerConnectorCredentials`, `registerServiceCredentials`, `registerBrokeredTools`. Each entry is a `CommandCredential`: a handle plus a `resolve()` that fetches the value later. Nothing is decrypted yet.
2. **Mint the turn's tokens.** `mintTurnCapabilities` (`src/core/orchestrator/capability-tokens.ts`) signs capability tokens with `mintCapabilityToken` (`src/auth/capability-token.ts`). Up to three go into the computer's standing environment: `AGENT_API_TOKEN` for the agent API, `AGENT_OAUTH_CONSENT_TOKEN` and `MODEL_GATEWAY_TOKEN`. Every command sees these without asking. One more, for the egress proxy, is handed to the sandbox for its outbound proxy ([security](./security.md)).
3. **Tell the model.** `addConversationBlocks` (`src/core/orchestrator/turn-prompt.ts`) calls `renderKeychainManifest` (`src/credentials/keychain.ts`), which writes the `## Credentials` prompt block: one line per handle, grouped by owner, for example `github:1a2b…` with "env `GITHUB_TOKEN`" and `web-search` with "proxy api.search.example". No value enters the prompt.
4. **The command asks.** The model calls `execute` with `credentials: ["github:1a2b…"]`. The tool (`computerTools` in `src/agent/agent-tools/computer.ts`) hands the handles to `execute()` inside `createToolContext` (`src/tools/primitives.ts`). `selectCredentials` re-runs the register functions, so a grant made a minute ago counts and a revoked one does not. An unknown handle fails with "credential handle is not available on this turn".
5. **Materialize for one command.** `stageCredentials` calls the entry's `resolve()`, which calls `materializeOwnById` on the keychain. The record is decrypted and returned as `GITHUB_TOKEN=<value>`. An audit event `keychain.materialize` is recorded. The value is added to this command's environment only, and `createExactSecretValueMasker` replaces exact copies of it in the output before the model reads it.
   - _File login instead of a variable._ A login saved as files (for example `aws`) goes through `prepareExecutionFiles` (`src/credentials/execute-files.ts`): the files are written to a private `/tmp/qm-credentials.<random>/home` on the turn's _scratch computer_ (see [sandboxes](./sandboxes.md)), `fileCredentialEnvironment` points `HOME` and the tool's own variables at it, and after the command `updateFiles` saves refreshed files back. Only the owner's executions write back.
   - _Shared conversation._ In a channel or group, or when the computer is attached to more than one scope, `placeCredential` marks every credential except a brokered one `scratchOnly`. The command is moved to the turn's scratch computer, so the value never lands on a computer other people's turns use. A background job that names such a credential gets a computer of its own.
   - _Someone else's credential._ It appears only if its owner granted it to this scope. The agent can request that with `POST /v1/keychain/asks`; the owner decides on an approval card, and `fireAskResolution` (`src/triggers/keychain-ask.ts`) wakes the asking conversation. `prepareMaterialize` checks the grant again at use and, for a one-time grant, marks it used.
   - _Slack bot turn, cron._ A turn doing a bot's work (`botActor`) never gets a person's own keychain. A scheduled turn in a shared conversation gets its owner's keychain only when the owner opened sharing to that conversation ([scopes](./scopes.md)).
   - _Native connector._ Had Acme configured GitHub OAuth and Ada connected it, the handle would be `connector:api.github.com:default` and the value would arrive as `VAULT_TOKEN_API_GITHUB_COM`, refreshed by core first if it was about to expire.
6. **A key the agent never sees.** The model runs a second command with `credentials: ["web-search"]`. For a brokered credential `resolve()` returns no secret. It mints a capability token with audience `credential-broker` whose `credentials` claim lists exactly the brokered slugs named on this command, and delivers it as `AGENT_CREDENTIAL_TOKEN`. The command posts `{credential, method, url, headers, body}` to `POST /v1/credentials/broker`. `brokerCredentialCall` (`src/api/credential-broker.ts`) checks that the slug is in the token, the credential is enabled, the URL is `https` on the pinned host, and the method and path are allowed. `credentialRequestHeaders` adds the secret header, core makes the request, and the reply comes back as `{status, contentType, body}`. Usage is written to `credential_usage`.
   - _Git._ `git clone` through the same credential uses `brokerGitHttp` (`src/api/git-http-broker.ts`), which streams Git's smart HTTP protocol.
   - _Published app._ An app gets its own long-lived broker token with a `deployment` claim; a credential switched off for apps refuses it ([artifacts](./artifacts.md)).
7. **An app connection, on a deployment that has one.** Ada asks to file the summary in her task tracker. Following the seeded `composio` skill, the agent calls `GET /v1/composio/connections` with `AGENT_API_TOKEN`. `credential()` in `src/api/routes/composio.ts` is the gate. It first checks the caller: the turn is still running (`activeRun`), the token carries `ownerConnections`, and it is not a bot turn or a published app. Then it looks for a Composio project key: first Ada's own keychain credential with env key `COMPOSIO_API_KEY`; otherwise exactly one org credential, which is a stored service credential with that env key granted to this conversation's audience or, when the org stored none, a deployment credential marked `composio: true`. With a key, core calls Composio with a user id it derives itself (`composioUserId`). `POST /v1/composio/execute` checks that the connected account is Ada's and active, and that the tool and version match, before running it. The key never reaches a computer.
8. **The same call on a deployment without one.** `credential()` finds no key and `composioUnavailable` answers 403 with the error `composio_unavailable`. Nothing else differs: the routes, the entries in `src/api/agent-api-catalog.ts` and the seeded `composio` skill ship in every build. The only signal in the prompt is an absence: the `## Connected app access` block, which `appendTurnGuidance` adds when `loadServiceCredentialGrants` reports `appConnections`, is not there.

## The parts

### `src/credentials`

**Job.** Store credentials, decide who may use them, and turn a record into variables or files for one command.

**Key idea.** One table of encrypted records holds four different things: personal variables, personal file logins, org service credentials and connector OAuth tokens. A record's id is a hash of owner, service and slot, so saving a service again replaces it in place and keeps its handle and grants.

**Surprising.** (1) `CONNECTOR_SECRET_KEY` is required: `buildApp` in `src/wiring.ts` refuses to start without it. The code still carries branches for a missing keychain (a `503 keychain_unavailable` answer, random per-process keys). (2) "Broker" names both a record `kind` and a delivery. A `kind: "broker"` record with `delivery: "env"` is an org credential that _is_ handed out as a variable. (3) A Composio key is recognized only by its env key name (`isBackendCredential`). It is stored as `delivery: "env"` and never delivered. (4) A file login never expires by date (`credExpired` skips `file`). (5) A grant has three sources: an approved ask, a redeemed secret drop in a shared conversation, and an org admin through `POST /v1/admin/keychain/grants`. (6) Write-back is a three-way merge (`mergeCredentialFiles` in `src/credentials/file-merge.ts`) that keeps whichever token cache expires later. A saved login is limited to 500 files and 8 MiB. (7) `src/credentials/resident-paths.ts` is not keychain code. It builds the script sandbox backends run to link well-known login paths in the home directory into `/tmp/agent-creds`.

### `src/connectors`

**Job.** OAuth for the eight built-in providers: build the consent URL, exchange the code, refresh the token.

**Key idea.** `PROVIDERS` is a data table (`google`, `slack`, `notion`, `linear`, `dropbox`, `github`, `x`, `zoom`) with a small adapter only where a provider deviates. A provider counts as configured when an `OAuthClientResolver` can produce a client for it.

**Surprising.** (1) Tokens are stored per API host, not per provider. One Google sign-in writes five records, and the variable name comes from the host (`envKey` in `src/credentials/connector-token.ts`). (2) Each host has three account slots: `default`, `personal`, `company`. (3) Slack and Notion tokens do not refresh (`refresh: null`). (4) Registered MCP servers with per-person sign-in appear as extra providers at run time (`setPublicOAuthClients`). (5) `src/connectors/connector-client-store.ts` also holds the encryption helpers (`encryptSecret`, `decryptSecret`, `deriveConnectorKey`) that the keychain and other stores import. (6) The directory also holds things that are not connectors: `src/connectors/background-exec-broker.ts` (background `execute` jobs), `src/connectors/emoji-upload-service.ts` with `src/connectors/browser-session-store.ts` (Slack custom emoji through a saved browser session, table `browser_sessions`), and `src/connectors/gmail-sent.ts`.

### `src/mcp`

**Job.** Turn registered MCP servers into agent tools and call them.

**Key idea.** `createMcpToolService` keeps a per-tenant snapshot of tool descriptors, refreshed every five minutes and on any change to `mcp_servers`. A server's tools appear as `<server id>_<tool>`. A server registered with `catalog: true` appears as one tool with three operations: `search`, `describe`, `invoke`.

**Surprising.** (1) Listing tools always uses the server's shared `auth`. Only the call itself uses the person's token in per-user mode, and there is no fallback to any shared or operator token. (2) An ordinary server contributes at most 64 tools; a catalog up to 5,000. (3) A server with per-person sign-in shows only a `<server id>_sign_in` tool until the person connects. (4) The agent cannot register or change a server: the `PUT` route refuses agent tokens. (5) A server can declare `apps` it serves. Those then appear in the app-connection routes even with no Composio key, and `POST /v1/composio/authorize` answers `409 connect_elsewhere` for them (`connectorApps` in `src/mcp/connector-apps.ts`).

### The brokers: `src/api/credential-broker.ts`, `src/api/git-http-broker.ts`, `src/api/connector-broker.ts`

**Job.** Make an outbound request with a secret the caller never holds.

**Key idea.** The token lists slugs, each request is checked against the record's host, methods and path prefixes, the secret is added, and the response is relayed. The connector broker is the same route with a `connector` host in place of `credential`. It serves only published apps that borrow their publisher's connectors.

**Surprising.** The default allowed method is `GET` alone. Subdomains of the pinned host match. Redirects are not followed. Only four caller headers pass. Responses are cut at 5 MB. Composio hosts are refused (`isComposioHost`). A daily cap that cannot be checked fails closed.

### Capability tokens: `src/auth/capability-token.ts`, `src/core/orchestrator/capability-tokens.ts`, `src/api/capability-destination.ts`

**Job.** Let code on a sandbox call core with the turn's authority and no more.

**Key idea.** Self-contained signed claims, one token per audience, so a leaked token opens one door. On every request `verifyCapability` (`src/api/server.ts`) re-checks live state: the actor is still an internal person, still has access to the scope, and a published app is still running.

**Surprising.** (1) "A person is at the keyboard" does not survive the turn. Once the run has ended, or the token belongs to an earlier attempt, `verifyCapability` marks the token `triggered`: it keeps the owner's authority but person-only steps refuse it. App-connection calls go further and refuse outright (`activeRun`). (2) There is no revocation list. A token ends by expiry, by the live checks, or by rotating the signing secret. (3) `exp: 0` means no expiry and is accepted for five audiences only. (4) An older `payload.signature` format is still verified (`verifyLegacyPayload` in `src/auth/signed-token.ts`). (5) `resolveCapabilityDestination` reads where a reply may be delivered from the token ([surfaces](./surfaces.md)).

### `src/core/orchestrator/credential-catalog.ts`

**Job.** Per turn, decide which handles exist and how each resolves.

**Key idea.** Authorization is checked twice: when the catalog is built, and again inside each `resolve()` at the moment of use (`authorizeOwnerCredentials`, `authorizeServiceCredential`, `prepareMaterialize`).

**Surprising.** A read-only turn gets no credentials at all. A turn from an external Slack workspace gets no keychain or connector credentials, and only the service credentials its workspace policy lists ([surfaces](./surfaces.md)). One execution may use at most one one-time grant. A command sent to another scope's computer may not carry credentials.

### App-connection routes: `src/api/routes/composio*.ts`, `slack-composio.ts`, `slack-native.ts`

**Job.** A narrow proxy to Composio bound to the caller's identity: list apps, start consent, list connections, list tools, run a tool, send one raw request, upload media to X.

**Key idea.** `credential()` is the single gate, and core derives the Composio user id from the organization and the person. A request body cannot name another user.

**Surprising.** (1) The prompt block and the skills that work over app connections key on the _org_ credential only. A personal key makes the routes work for that person without adding the block. (2) `POST /v1/composio/proxy` reaches only the API hosts listed in `APP_CONNECTION_ROUTES` (`src/connectors/app-connection-routes.ts`). (3) A background job loses access when its turn ends. (4) Linking a person's Slack account has two implementations: the native connector (`src/api/routes/slack-native.ts`) is tried first, Composio (`src/api/routes/slack-composio.ts`) otherwise. (5) `execute` needs a concrete tool version; `latest` and Composio's own `COMPOSIO_` tools are refused.

### Other routes: `src/api/routes/keychain.ts`, `secret-drop.ts`, `connectors.ts`, `credentials.ts`, `admin/mcp-servers.ts`

**Job.** The HTTP surface for the above: save, list and delete credentials; asks and approvals; secret drops; OAuth start, callback, status and revoke; the broker; MCP registration.

**Key idea.** Routes the agent may call take a capability token. Routes where a human decides (approving an ask, redeeming a drop or consent link) take a request signed by a trusted web surface and compare the signed-in person with the record's owner ([web-clients](./web-clients.md)).

**Surprising.** A turn doing a bot's work may save a new login but not replace an existing one. Consent links can be minted only for oneself.

## Where the complexity lives

**Things that multiply each other.** What the credential is (variable, files, brokered, connector token) times who is asking (owner in their own scope, owner who opened sharing, grantee, bot turn, scheduled turn, external Slack, published app) times where the command runs (conversation computer, scratch computer, job computer). Each register function and each `scratchOnly` rule is one slice of that grid. OAuth has its own grid: three sources for a client (stored row, environment pair, public MCP client) times three account slots times several hosts per provider.

**Parallel mechanisms doing one job.**

- Three ways to act in a third-party app as a person: a native connector token, an MCP server with per-user credentials, an app connection. `CONNECTOR_SKILLS` in `src/core/orchestrator/turn-helpers.ts` is a hand-kept map of which seeded skill works under which.
- Two grant systems: `keychain_grants` for personal records and `service-cred` rows in `grants` for org records. The admin `service-credentials` resource (`src/api/routes/admin-resources.ts`) writes a credential and its grants as two separate stores and carries its own rollback.
- Three one-time-link stores with the same mint, peek and redeem shape: `consent_links`, `secret_drops`, `oauth_flows`. OAuth state also has a second form, a signed blob (`sealOAuthState`), used when no flow store is wired.
- Two token wire formats and two payload encodings, all readable at once.

**Kept but unused.** `materializeStanding` and `grantConnectorToScope` on `Keychain` have no caller outside tests. The `egressRule` field on every entry of `PROVIDERS` is never read. The optional-keychain branches cannot be reached through `buildApp`.

**Transitional.** `SecretKey` carries a `legacy` key and `fallbacks` so records encrypted under earlier key derivations still open. `decryptToEnv` still emits a variable for a legacy stored username. Two migrations registered in `src/wiring.ts` delete records left by retired mechanisms. ## Contracts

**Capability token.** Sent as the `x-agent-capability` header. It is a compact JWS signed with HS256; the `kid` header identifies the signing secret. The payload is the claims object, or `{"encoding":"deflate-raw","claims":"<base64url>"}` when compression is on and the claims exceed 4096 bytes; inflated claims are limited to 1 MiB. `exp` is in milliseconds. Verifiers read both encodings whatever the switch says, so turn compression on only after every process that verifies tokens (core, workers, a separately deployed egress proxy) runs a version that reads it. A changed lifetime applies to new tokens only.

| Audience                           | Delivered as                                                             | Lifetime                                              |
| ---------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------- |
| `control-plane`                    | `AGENT_API_TOKEN`                                                        | sandbox lifetime                                      |
| `oauth-consent`                    | `AGENT_OAUTH_CONSENT_TOKEN`                                              | sandbox lifetime                                      |
| `credential-broker`                | `AGENT_CREDENTIAL_TOKEN`, only on a command that names a brokered slug   | sandbox lifetime; about ten years for a published app |
| `sandbox-model`                    | `MODEL_GATEWAY_TOKEN`                                                    | sandbox lifetime                                      |
| `egress-proxy`                     | handed to the sandbox for its outbound proxy ([security](./security.md)) | sandbox lifetime                                      |
| `browser-model`                    | `BROWSE_LAB_MODEL_TOKEN`                                                 | one hour                                              |
| `secret-drop`, `memory-brain-drop` | in the drop link                                                         | 7 days                                                |
| `blob-transfer`                    | minted per file transfer ([artifacts](./artifacts.md))                   | minutes                                               |

**Broker.** `POST /v1/credentials/broker` with `AGENT_CREDENTIAL_TOKEN`. Body: `credential` (slug), `url` (absolute `https`), optional `method` (default `GET`), `headers` (only `accept`, `accept-language`, `content-type`, `user-agent` pass), `body` (string). Success is HTTP 200 with `{status, contentType?, body, truncated?}`, where `status` is the upstream status. Refusals carry an `error` code, among them `not_entitled`, `credential_unavailable`, `host_not_allowed`, `method_not_allowed`, `path_not_allowed`, `daily_cap_reached` (429) and `upstream_unreachable` (502). Git remotes use `GET` and `POST` on `/v1/credentials/git/<slug>/<upstream path>` with the same token.

**Published apps and the broker.** When core has a signing secret and an API base URL, `appEnv` in `src/wiring.ts` gives each app version it starts `AGENT_API_URL` and an `AGENT_CREDENTIAL_TOKEN` whose claims name the app (`deployment`) and its publisher. The token lists the org credentials switched on for apps at that moment, so a credential added later reaches an app the next time a version starts, and one switched off afterwards is refused on the next call with `not_available_to_deployments`. Every call acts as the publisher, whoever is viewing the app.

**Lent connectors.** `POST /v1/apps/:id/connectors` with `{"connectors": ["<host>", …]}` sets the connected-app hosts an app may call as its publisher; `[]` withdraws them. Only the publisher may call it (`setAppConnectors` in `src/deploy/deploy-service.ts`). Each host must be in `CONNECTOR_HOSTS`. A public app cannot borrow, a borrowing app cannot be made public, and an app outside its publisher's own library cannot borrow. The loan is withdrawn when anyone but the publisher changes the running version or the app leaves the publisher's library, and while it stands only the publisher can share the app. The app calls the broker with `connector` (the host) in place of `credential`. `brokerConnectorCall` in `src/api/connector-broker.ts` requires plain `https` to exactly that host, uses the publisher's personal connection, else their default, else their company one (`tokenFor`), and refuses with `not_entitled`, `connector_not_lent`, `host_not_allowed`, `scheme_not_allowed` or `connector_unavailable` (409). Audit actions: `connector.broker.use`, `connector.broker.denied` and `connector.broker.error` per call, and `deploy_connectors` per loan change.

**`BROKER_CREDENTIALS`.** A JSON array read once at startup. Any unknown field, missing secret, duplicate slug or invalid value stops core with an error that names the entry and never the secret.

| Field                 | Required               | Meaning                                                                                                                                                                      |
| --------------------- | ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `slug`                | yes                    | Lowercase kebab-case name the agent uses. Unique.                                                                                                                            |
| `secretEnv`           | yes                    | Name of the environment variable that holds the secret. The secret itself never goes in the array.                                                                           |
| `host`                | yes, unless `composio` | Bare hostname requests are pinned to. Subdomains match.                                                                                                                      |
| `displayName`         | no                     | Label; defaults to the slug.                                                                                                                                                 |
| `injection`           | no                     | `header` and `scheme` for the secret (default `Authorization: Bearer <secret>`; `scheme: ""` sends it raw). `headers` adds fixed non-secret headers callers cannot override. |
| `allowedMethods`      | no                     | Default `GET`.                                                                                                                                                               |
| `allowedPathPrefixes` | no                     | Default any path.                                                                                                                                                            |
| `maxRequestsPerDay`   | no                     | Cap per UTC day across all core processes. Over it: `429 daily_cap_reached`.                                                                                                 |
| `composio`            | no                     | `true`, with no broker field, makes the entry the deployment's Composio key.                                                                                                 |

A deployment credential is broker-only. It is available to every conversation whose whole audience belongs to the org, and admins cannot narrow that. Published apps, decision providers and skill-pack Git auth cannot use it. Its slug is reserved: a stored credential with the same slug is ignored and cannot be created, edited or deleted. The Composio entry is the exception. It is a default, not a reservation: a stored credential with the same slug, or any enabled stored Composio key, takes its place, and a disabled stored credential with the same slug turns app connections off.

**MCP registration.** `PUT /v1/admin/mcp-servers/:id`, by an org admin or owner. Agent tokens are refused. Fields: `name`, `url`, `auth` (`none`, `bearer` with `bearerToken`, `client-credentials` with `clientId` and `clientSecret`, or `oauth-user`), `credentialScope` (`shared` or `per-user`), `credentialHost` and `credentialAccountType` for per-user, `approval` (`annotations`, `all`, `none`), `catalog`, `attestActor`, `attestAudience` (`personal` or `any`), `apps`, `readOnly`, `enabled`.

- A new registration with no `auth` is probed. If the server publishes OAuth protected-resource metadata it becomes `oauth-user`, otherwise `none`. With no `clientId`, core registers a public PKCE client through the server's registration endpoint.
- `approval: "annotations"` pauses calls to tools marked destructive and not read-only. An approval is bound to the call's exact arguments ([security](./security.md)).
- `attestActor` sends the person's id in the `x-qm-actor` header. It requires `catalog`, shared credentials and `bearer` or `client-credentials` auth. `attestAudience: "personal"` limits it to the person's own conversation.
- Per-user mode requires `https` and sends the person's token for `credentialHost` to the server. A turn doing a bot's work is never offered a server that acts as the person.
- Core refuses server, discovery and token endpoints that resolve to private addresses, and refuses redirects. `PRIVATE_NETWORK_ALLOWED_ORIGINS` lists exact origins (scheme, host, port; comma-separated) that may be private. Loopback, link-local and cloud metadata addresses are never allowed, and the list does not open sandbox egress.

**Saving a token from outside.** `POST /v1/connectors/token`, signed by a trusted source, with `host`, `principalId`, `accessToken` and optional `refreshToken` and `expiresAt` (milliseconds). Core can refresh only tokens of providers it knows.

**Saving a login.** `POST /v1/keychain/credentials` with `service` and one of `secret`, `fields[]` or `files[]` (home-relative `path`, `contentBase64`, optional `mode`). The seeded `interactive-login` skill uploads files this way with `skills-seed/interactive-login/scripts/save-login.mjs`.

**Composio callback.** For identity-verified consent, the Composio project's verifier URL is `https://<web origin>/api/composio/callback`, which the web surface forwards to `GET /v1/composio/callback` with the `session_uri`. Core completes the connection as the signed-in person. An agent token cannot. Verification is a setting of the whole Composio project, so a project shared by several deployments cannot point its verifier at one of them. With verification on, Composio ignores the link's own callback, so core saves the return address for 20 minutes, keyed by person and connected account, and redirects there afterwards.
