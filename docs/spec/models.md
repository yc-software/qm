# Models and runtimes

_Verified against `main` at d1de9e2d2 (2026-11-24). Statements were read in the code at that commit unless marked **[interpretation]**._

## In one paragraph

Every model call QM makes goes through Pi, an agent library installed from two vendored packages, except these plain `fetch` calls: embeddings (`src/model/embeddings.ts`), voice (`src/voice/voice.ts`), the decision backend (`src/decisions/providers.ts`) and sandbox requests forwarded to a gateway (`src/api/routes/sandbox-model.ts`). Pi is the only harness in the code. Before each call QM settles three things. The _runtime_ is the model, the effort level and whether fast mode is on; it comes from layered settings, from the request down to a deployment default. The _model definition_ is the protocol, context size and prices behind a model id; it comes from a catalog merged from six sources. The _route_ is whose credential pays and which endpoint receives the request; it depends on what this deployment has configured: a provider API key, a subscription login, a model gateway, a custom provider, the person's own account, or a tenant's own gateway key. A deployment may have several of these at once. For one account, each model id resolves to one route, and each call uses exactly one. A model id that works on one deployment can have no route on another, so no code may assume that a particular model is callable. When a provider refuses, QM sorts the failure into a small set of codes, then retries on the organization's fallback runtime, leaves the retry to the run worker, or fails the turn with the provider's reason.

## One model call, traced end to end

Ada at Acme opens the web app and types "Summarize the Q3 notes". Acme is a [Package deployment](../SPEC.md#deployment-shapes) whose only model setting is `ANTHROPIC_API_KEY`. Side notes show where other deployments diverge. The turn machinery around these steps is in [turns](./turns.md).

1. **The picker only offers what can run.** The web UI has already loaded `GET /v1/runtime-config`, answered by `userRuntimeConfigBody` and `runtimeConfigBody` in `src/api/runtime-config.ts`. The list starts as the catalog narrowed to models offered in the web UI, or as the `webui-models` allowlist when an admin saved one. With no allowlist or a non-empty one, the organization's default model is added, and the scope's selection unless the allowlist leaves it out. `serviceableModelIds` (`src/model/pi-models.ts`) then narrows the list to models whose provider has a credential or a gateway route. At Acme that leaves the Anthropic models. Ada keeps the default.
2. **Admission checks the model.** `createTurnMethods` in `src/api/app-turn.ts` calls `turnModelRefusal`. For a web turn on company access it resolves the runtime once and, when nothing can serve it, refuses before anything is queued: "that model isn't available on this deployment (its provider isn't configured)".
   - _Slack and other surfaces_ skip this check: `turnModelRefusal` returns before it unless the surface is `web`, and `runTurn` does not test the route with `servable`. **[interpretation]** How a missing route then fails is decided inside Pi, whose source is not in this repo.
   - _Cron, webhook, loop:_ if the trigger names a model, `requestedRuntimeError` validates it. Unattended turns default to effort `xhigh` and fast mode off (`turnModelOptions` in `src/agent/runtime-choice.ts`, and the `cron` branch of `resolveRuntimeChoice`); for crons and loops with a saved `cron` purpose runtime, neither default is applied. A cron that fires at most daily is the exception: it skips the `cron` purpose runtime and the `xhigh` default, and resolves like a chat in the organization's scope with fast mode off.
3. **Whose account.** In the orchestrator, `resolveTurnRuntimeAuth` in `src/core/orchestrator/turn-runtime.ts` reads Ada's _model account_. It is `company`, so the organization's credentials apply.
   - _A person's own account:_ when the account is personal, `loadPersonalModelAuth` in `src/core/individual-auth-routing.ts` loads Ada's own API key or subscription token and picks a model her account can serve. Only turns a person typed use it. Crons, subagents and turns from a surface that marks its audience `external` (Slack external access, generic-chat guests) always use company credentials. If her account yields no usable credential for the turn, the turn fails with a reconnect message; if a web turn names a model that her account's routing replaced with another, it fails with "Your connected AI account cannot serve this model."; it never falls back to company access.
4. **The runtime is resolved.** `withResolvedRuntime` wraps the agent and calls `resolveRuntimeChoice` (both in `src/agent/runtime-choice.ts`). If the turn has a purpose (`cron` or `subagent`) and the organization saved a runtime for that purpose, that runtime is used, and only fields the request names override it. Otherwise the model is the first of: the request's model, the model this conversation last ran on, the scope's saved selection, the organization's saved selection, the deployment default. Ada's turn falls through to the deployment default, `claude-opus-5` (`DEFAULT_AGENT_MODEL_ID`). She chose no effort, so `runTurn` uses `defaultInteractiveThinkingLevel`: `low` for Anthropic models. Fast mode stays off because the organization's interactive fast-mode switch is off.
   - If the chosen model has become unavailable (retired from the gateway, deleted, or no longer verified), this step throws a non-retryable error that names the model and the reason. Nothing is sent. The model the conversation last ran on is the exception: when it is unavailable it is skipped and the next layer decides.
   - A decision rule can reroute the turn here: `routeTurnRuntime` in `src/decisions/hooks.ts`.
5. **The route is resolved.** `createAgent` in `src/agent/agent-run.ts` builds `runTurn`, which asks `createModelRoutes(...).session` in `src/model/model-route.ts`. That turns the id into a Pi `Model` with `getRequiredModel`, gathers the organization's keys, and asks `companyGateway` whether a gateway serves this id. Acme gets `{ anthropic: <key> }`, no gateway, billing `org_key`.
   - _Model gateway_ (`MODEL_GATEWAY_URL` set): models discovered from the gateway are named `gateway/<upstream-id>` and always go to the gateway. A plain id listed in `MODEL_GATEWAY_MODELS` also goes to the gateway until an admin saves the organization's own key for that provider; from then on it uses that key. Billing is `model_gateway`.
   - _Subscription login:_ with `CLAUDE_AUTH_CREDENTIAL`, the Anthropic key is a subscription token read from a named keychain credential, unless the organization also has an Anthropic API key (environment or admin-saved), which replaces it (`resolveCompanyProviderKeys` in `src/wiring.ts`). With `CODEX_AUTH_CREDENTIAL`, `companyModelId` rewrites OpenAI ids to `codex/<id>`, served on a ChatGPT subscription.
   - _A tenant's own gateway key_ ([Multi-tenant deployment](../SPEC.md#deployment-shapes)): the gateway is the same, but `gatewayKey` in `src/model/provider-endpoints.ts` sends `modelGatewayKey` from that tenant's row in `tenants` instead of the deployment's key.
   - _Custom provider:_ the id looks like `custom/<provider>/<model>` and uses that provider's saved key and base URL.
6. **Pi gets a runtime that holds only this turn's keys.** `buildModelRuntime` in `src/model/model-runtime.ts` creates a Pi `ModelRuntime` over an in-memory credential store and wraps its `stream` methods. The wrapper decides at send time. For a gateway route it swaps in the gateway's base URL, key header and `x-qm-*` headers, and rewrites the model id to the upstream id. For a direct route it rewrites only ids that differ upstream (`codex/…`, Ultrafast, custom).
7. **The call.** `createAgentSession` (Pi) starts a fresh in-memory session with Pi's built-in tools switched off and QM's tools attached. `applyTurnEffort` sets the thinking level. A payload hook then edits the request body: `applyFastSpeed` (`src/model/model-runtime.ts`), `applyReasoningMode` (`src/agent/turn-effort.ts`), then `withDocumentInputs`, `guardOutputBudget` and `trimPayloadToByteBudget` (9,000,000 bytes on a gateway route). Pi posts to the Anthropic Messages API and streams the reply.
8. **Usage is priced and recorded.** `piUsageToCallUsage` prices each call from the model's price card, at the tier the provider says it served. `recordCapturedRequests` in `src/agent/turn-stream.ts` writes one row per call to `session_llm_requests` while request capture is on. If a budget is configured, the orchestrator also adds an estimate to `budget_spend`.
9. **The provider refuses.** Suppose Anthropic returns a refusal. `providerTurnError` in `src/model/provider-error.ts` maps the structured error to a code. For the codes in `FALLBACK_CODES` (`refusal`, `model_unavailable`, `model_budget`, `auth`, `account`), `runTurn` asks `routes.fallback` for the organization's fallback runtime. Acme saved none, so the turn fails with the provider's reason. Where an admin has saved one on a different model with a usable route, and the turn's wall-clock limit leaves room for another prompt (`roomToReprompt`), the same Pi session switches model, drops the failed reply and continues with `refusalFallbackNote`, which tells the model to say that it switched and why.
   - `rate_limit` and `transient` stay retryable, as does `unknown` when the failure has no HTTP status and no stop reason, and the run worker retries the turn (see [turns](./turns.md)).
   - `context_too_long` or `bad_request` on a request that carried inline documents is retried once with the documents replaced by stubs.
   - `model_budget` (provider error type `budget_exceeded`) with no fallback ends as a refused turn, not a failed one.
   - A gateway model that disappears mid-turn raises `GatewayModelUnavailableError`. Its `type` is `model_unavailable`, a fallback code.

## The parts

### Pi: `package.json` and `vendor/pi-ai`

**Job.** Pi supplies the agent loop and the provider protocols. `@earendil-works/pi-coding-agent` gives `createAgentSession` and `ModelRuntime`. `@earendil-works/pi-ai` gives the `Model` type, a bundled model catalog, the Anthropic and OpenAI wire protocols and cost arithmetic. **Key idea.** QM hands Pi a model object, one turn's keys and QM's own tools. Pi keeps no state between turns. **Surprising.** Both packages install from tarballs attached to releases of `yc-software/qm`, not from npm. `vendor/pi-ai` holds no source: only three patches, two build scripts and a README. The patches keep the provider's structured error, the served tier and a `fetch` option, and the rest of this area depends on all three. The web UI under `plugins/web-ui` pins older stock Pi packages of its own (see [web-clients](./web-clients.md)). One migration in `src/wiring.ts`, `runtime/0002-drop-harness-choice`, removes a stored harness choice that no longer exists.

### `src/model`: the catalog

**Job.** Answer "what is this model id?". `resolveModel` in `pi-models.ts` tries, in order: gateway models, the built-in registry and Pi's bundled catalog, overlays, custom providers, OpenRouter's public catalog. **Key idea.** Capabilities come from data: `thinkingLevelsFor`, `modelSupportsFastMode`, `contextTokenBudgetForModel`. A name test does exist in `nativeDocumentFormat` (`src/agent/document-inputs.ts`), which matches OpenRouter ids beginning `anthropic/`, `google/` or `openai/`. Embedding models are resolved separately by `resolveEmbeddingModel`; memory uses them (see [context](./context.md)). **Surprising.** (1) _Supported_ and _serviceable_ are different tests. `modelSupported` says the id is in the catalog. `modelServiceable` says this deployment has a credential or gateway route for it. Code that checks only the first offers models that cannot run. (2) Overlays and custom providers are held per tenant. The gateway catalog (`gateway-models.ts`), the OpenRouter catalog and provider base URLs are held once per process. (3) Gateway discovery (`createGatewayCatalog` in `gateway-catalog.ts`) always uses the deployment's key, even when a tenant's requests use the tenant's own key. (4) An overlay with a stale verification is hidden from pickers but stays in saved selections, which then fail with a reason instead of silently changing model; a conversation's last model is skipped instead.

### `src/model`: routes and transport

**Job.** `model-route.ts` picks keys, gateway and billing for a model id. `model-runtime.ts` builds the Pi runtime, rewrites requests and prices usage. `provider-endpoints.ts` holds gateway headers and base URLs. `provider-error.ts` classifies failures. **Key idea.** `createModelRoutes` is where turns, compaction, titles, the sandbox endpoint and the browser endpoint all decide gateway versus own key versus personal key. Model verification and voice choose their credential on their own. **Surprising.** (1) Only a key _saved by an admin_ moves a plain model id off the gateway. A key in the environment does not change routing. (2) Deleting an admin-saved key leaves a disabled row, and `resolve` in `model-credential-store.ts` then ignores the environment key for that provider too. (3) With `CODEX_AUTH_CREDENTIAL` set, OpenAI models are served on the subscription even if an OpenAI API key is also present; Ultrafast ids and overlays are the exceptions. (4) Requests made with a Claude subscription token carry a `claude-cli` user agent (`claudeSubscriptionHeaders`). (5) Calls to custom providers go through `publicFetch`, which refuses private network addresses unless the origin is listed in `PRIVATE_NETWORK_ALLOWED_ORIGINS` (see [security](./security.md)). (6) Personal-account calls skip the organization's base-URL overrides and never use the gateway.

### `src/model`: credentials, logins and admin checks

**Job.** Store organization keys (`createModelCredentialStore`) and custom providers (`createCustomProviderStore`), store a person's own key or subscription login in the keychain (`createUserModelCredentialStore`), run the Claude and ChatGPT sign-in flows (`subscription-oauth.ts`, `codex-device-login.ts`), refresh the company ChatGPT login (`keychainCompanyChatGPTAuth`), and check a proposed model against its provider (`createModelVerifier`, `lookupModel`). **Key idea.** None of this runs during a turn except reading keys; reading the company ChatGPT token refreshes it when it is about to expire (`refreshingAuth` in `company-chatgpt-auth.ts`). **Surprising.** (1) A pending ChatGPT device login lives in one process's memory; a poll that reaches another core instance gets `unknown`. (2) Saving a provider key on a gateway deployment also moves the base model and the purpose runtimes that still use the gateway to that provider's default model (`moveGatewayDefaultsToProvider`); the admin response lists what moved. Moving back is a manual choice. (3) Verification stores a keyed fingerprint of the definition and the serving credential. Changing either makes the model unavailable until an admin verifies again, with no new provider call needed to notice.

### Runtime selection: `src/agent/runtime-choice.ts`, `src/agent/turn-effort.ts`, `src/api/runtime-config.ts`, `src/core/turn-options.ts`

**Job.** Turn request fields and saved settings into one `RuntimeChoice`, and tell clients which choices exist. **Key idea.** Precedence is hand-coded in `resolveRuntimeChoice`; `runtimeConfigBody` re-derives the same layers for the picker. **Surprising.** (1) A conversation keeps the model it last ran on. Changing the scope's or the organization's selection does not move it unless a request names a model. (2) With no `PI_MODEL`, no `MODEL_PROVIDER` and no gateway, the deployment default is `claude-opus-5` even when the only key is for OpenAI or OpenRouter; with `CODEX_AUTH_CREDENTIAL` set and neither `ANTHROPIC_API_KEY` nor `CLAUDE_AUTH_CREDENTIAL`, it is `gpt-6.1-sol` (`configuredModel` in `src/config.ts`). (3) The `cron-runtime` setting does not apply to crons that fire at most daily. (4) Several model ids are constants: `DEFAULT_AGENT_MODEL_ID`, `DEFAULT_CODEX_MODEL_ID`, `TITLE_MODEL_ID`, `NEXT_PROMPT_MODEL_ID`, `APP_EDIT_DEFAULT_RUNTIME`. Each caller copes on its own when the id has no route: titles fall back to the utility model, next-prompt suggestions return nothing, app-edit chats use the conversation's runtime. These are workarounds for hard-coded ids; new code should take its model from a purpose runtime, not add another constant. (5) `adaptive` and `default` are not thinking levels to Pi. QM turns Pi's thinking off and rewrites the request body itself.

### Runtime changes mid-task: `src/agent/runtime-control.ts`, `runtime-recovery.ts`, `runtime-types.ts`

**Job.** Back the agent's `runtime` tool: list choices, or switch model, effort or fast mode. **Key idea.** A switch is a _handoff_. The tool result ends the current Pi session and the orchestrator starts another on the new runtime, for this task only (`task`) or also saved for the scope (`scope`). **Surprising.** The handoff is stored in the tool result item, and `recoveredRuntime` reads it back so a retried run resumes on the switched runtime. A change needs a turn that carries a person's authority in an internal-audience conversation (`internalPerson`; otherwise the tool answers `authority_required`), except a cron fire changing its own task.

### Accounts: `src/core/individual-auth-routing.ts`, `src/core/orchestrator/turn-runtime.ts`, `src/api/routes/user-model-auth.ts`

**Job.** Decide whether a turn runs on company or personal credentials and load the personal ones. **Key idea.** No account silently falls back to another. **Surprising.** A personal turn pins the model its account routing chose, so the settings layers are skipped, unless a purpose runtime applies, the run is resuming a `runtime` handoff, or the `runtime` tool has already switched it. Its sandbox gets no model token (see below). Personal keys are stored in the keychain, not in `model_credentials` (see [credentials](./credentials.md)).

### Failure handling: `src/agent/turn-fallback.ts`

**Job.** The fallback code set, the notes the model sees after a switch, and error wrapping. **Key idea.** The fallback is one admin setting (`fallback-runtime`), tried at most once in a turn; there is no built-in ladder of alternates. **Surprising.** Compaction uses the same fallback.

### Model access for code: `src/api/routes/sandbox-model.ts`, `src/api/routes/browser-model.ts`, `src/model/chat-completion.ts`

**Job.** Let code in a sandbox, and the browse skill's inner agent, call models without holding a key. **Key idea.** Core is the proxy. It checks a capability token, picks the route with `createModelRoutes` and adds the key. **Surprising.** Inside a sandbox, `MODEL_GATEWAY_URL` points at core's `/v1/sandbox-model`. The variable of the same name in core's environment points at the upstream gateway. The sandbox variable is set even when no gateway exists.

### Admin and spend: `src/api/routes/admin`, `src/ratelimit`

**Job.** Admin endpoints for provider keys, the model registry, custom providers and spend reports; two spend caps. **Key idea.** Spend is derived from `session_llm_requests`, rolled up by day, scope, origin, cron and model. **Surprising.** (1) The two caps count differently. The budget (`createPostgresBudgetTracker`) adds input tokens at a flat rate (`estimateCostUsd`), not the model's price. Spend limits (`createSpendLimits`) use the priced usage. (2) A turn's usage rows are written only while request capture is on (`PI_CAPTURE_REQUESTS`, default on). With capture off, a turn's own calls add nothing to spend reports or spend limits; a one-shot call that is given a recorder (the respond-or-not check) still writes its usage row.

### Settings: `src/config.ts`

**Job.** Parse model environment variables: `modelGatewayFromEnv`, `configuredModel`, `providerKeysPresent`, `companySubscriptionAuth`. **Key idea.** Environment values are deployment-wide defaults; a key or selection an admin saves for the organization takes precedence. **Surprising.** `MODEL_PROVIDER` does two things. It narrows the default base model to that provider, and it makes that provider's key required at boot (for `openai`, not when `CODEX_AUTH_CREDENTIAL` is set). Without it, core starts with no model credential at all and an admin adds one later. The deployment directory sets it through `modelProvider` (see [deployments](./deployments.md)).

## Where the complexity lives

- **Routes multiply with protocols and accounts.** Six routes, four wire protocols (`anthropic-messages`, `openai-responses`, `openai-codex-responses`, `openai-completions`) and two account kinds. `withRequestHeaders`, `applyFastSpeed`, `applyReasoningMode` and the pricing in `piUsageToCallUsage` each branch on protocol; `withRequestHeaders` also branches on whether the call is direct.
- **Many settings answer "which runtime".** The request, the conversation's last model, the scope selection, the organization selection, an older per-scope `modelId` field still read by `getBaseModelOwnDurable`, four purpose runtimes, a per-cron runtime (see [background-work](./background-work.md)), a persona's model (see [context](./context.md)), decision rules, the `runtime` tool, and the `PI_MODEL` and `MODEL_PROVIDER` variables. The master's Wall of shame records this under _Config-matrix expansion_.
- **Six catalog sources, three kinds of state.** Built-in data, Pi's bundled data, rows per tenant (overlays, custom providers), and process memory (gateway, OpenRouter). Each has its own refresh rule and change counter (`gatewayModelsVersion`, `customProvidersVersion`).
- **Two spend caps with different arithmetic**, described above.
- **Three recoveries from one failed call.** The fallback runtime, the retry without documents, and the run worker's retry are separate mechanisms, each keyed on its own subset of the error codes. The master's Wall of shame records the fallback under _Band-aid fixes_.
- **Two OpenAI-compatible endpoints for code.** `/v1/sandbox-model` and `/v1/browser-model` share `completeChatRequest` but differ in token, limits and account handling.
- **Two ways to hold an organization key** (environment, admin row) with different effects on routing.
- **Abstractions with one implementation.** The `Agent` interface has one implementation, `createAgent`, plus the wrapper `withResolvedRuntime`. `BudgetTracker` has one, on Postgres.
- **Transitional code.** `vendor/pi-ai` exists until Pi ships the three patched fields (its README says so). `MODEL_GATEWAY_MODELS` is the only gateway routing while discovery has never succeeded, and after discovery it still sends a plain id to the gateway when the gateway lists its upstream id. The `auto` effort level is described to the agent as the legacy default.

## Contracts

**Gateway configuration.** `MODEL_GATEWAY_URL` is an http(s) URL without credentials, query or fragment; a trailing `/v1` is accepted. `MODEL_GATEWAY_API_KEY_HEADER` must be a valid header name and must not be one of the context headers below. Every local id in `MODEL_GATEWAY_MODELS` must be a known model or boot fails.

**Gateway discovery.** QM sends `GET <root>/v1/models` and `GET <root>/model_group/info` with the key header. Redirects are refused; each read is limited to 5 seconds and 2 MiB. Both return `{"data": [...]}`. A model is offered only if it is in both lists, has `mode: "chat"`, `supports_function_calling: true`, and valid `max_input_tokens`, `max_output_tokens`, `input_cost_per_token` and `output_cost_per_token`. A group with `mode: "embedding"` becomes an embedding model. Optional fields: `providers`, `supports_vision`, `supports_reasoning`, `supports_adaptive_thinking`, `supports_fast_mode`, `supported_openai_params`, `supported_reasoning_efforts`, `cache_read_input_token_cost`, `cache_creation_input_token_cost`. Prices are per token; missing cache prices use the input price. If the output limit is not below the input limit, QM substitutes a smaller one. Upstream credential and endpoint fields are ignored.

**Protocol selection.** It follows `providers`, never the model name. Only `anthropic`: Messages at `<root>/v1/messages`. Only `openai` or `azure`: Responses at `<root>/v1/responses`. Anything else: streaming chat completions. Document input is native files for `openai`/`azure`-only groups, and PDF when every provider is one of `anthropic`, `openai`, `azure`, `gemini`, `vertex_ai`. Reasoning controls follow `supports_reasoning`. For chat-completion groups that list `supported_reasoning_efforts`, other levels are marked unsupported, and Pi moves a request to the next higher supported level, or the highest lower one.

**Discovery timing.** A successful discovery replaces the catalog, even with an empty one, and is reused for five minutes. A failure is retried after thirty seconds. After a transient failure (429, 5xx, timeout, network error) the last catalog is kept for up to fifteen minutes from the last success. Any other failure, or a longer outage, removes all gateway routes until discovery recovers. Before the first success, configured aliases stay routable.

**Request context headers.** Gateway requests carry `x-qm-session-id`, `x-qm-actor`, `x-qm-scope`, `x-qm-origin` (`conversation`, `cron`, `webhook`, `monitor`, `loop`, `swarm`) and `x-qm-purpose`. A value is sent only when known and when it is 1 to 256 printable ASCII characters without spaces. `x-qm-actor` is the first 32 hex characters of an HMAC-SHA256 of the principal id, keyed with `CAPABILITY_SECRET` or, failing that, `CORE_SIGNING_SECRET`. A personal scope's person is replaced by the same hash; other scope ids are sent as they are, so a gateway should not forward client `x-` headers upstream. `GET /v1/admin/users` returns each person's hash as `gatewayActor`. Direct provider calls and discovery never carry these headers.

**Sandbox endpoint.** Turns with an all-internal audience, outside strict posture and on company access get `MODEL_GATEWAY_URL` (core's `/v1/sandbox-model`) and `MODEL_GATEWAY_TOKEN`, a capability token that authorizes model calls and nothing else. The token is accepted as `Authorization: Bearer`, `x-api-key` or `x-agent-capability`. `GET /v1/models` lists usable ids with `owned_by` set to `gateway` or `organization`. Ids the gateway serves are forwarded to the same path on the gateway, streaming included, with the model id rewritten and the end user (`user`, or `metadata.user_id` on `/v1/messages`) replaced by the actor hash. Other ids accept only non-streamed `POST /v1/chat/completions` with text, inline `data:` images and an optional `json_schema` response format; no tools. Core passes on `accept`, `content-type`, `anthropic-version` and `anthropic-beta`. Strict posture answers 403 and a spent budget 429. Gateway 401 and 403 become 502. Bodies up to 32 MiB. The gateway key's own permissions are the only limit on which gateway paths and models sandbox code can reach, so it must be an inference-only key.

**Browser endpoint.** The browse skill (`skills-seed/browse`) reads `BROWSE_LAB_BASE_URL`, `BROWSE_LAB_MODEL` and `BROWSE_LAB_MODEL_TOKEN` from the sandbox. `POST /v1/browser-model/chat/completions` takes non-streamed chat completions up to 16 MiB with a 120-second limit. The token is bound to one model and one account and lasts one hour; core reloads the account's credentials on every request. Strict posture answers 403, a personal account that no longer serves the model 409, and Claude subscription access 422.

**Model registry writes.** `PUT /v1/admin/model-registry/:model` and `POST /v1/admin/model-registry/:model/enable` require `verify: true` in the body, because verification sends a small billable request. The probe uses synthetic text and one synthetic tool, caps output at 128 tokens, has a 15-second deadline, and runs twice for fast-mode models. A failed check never saves the proposed definition, and a failed recheck of unchanged settings removes their earlier verification. `POST /v1/admin/model-registry/lookup` reads one model record from the provider (5 seconds, 64 KiB, no redirects) and never fills a missing price from another model.

**Spend export.** With `SPEND_EXPORT_TOKEN` set (at least 32 characters, different from every other environment value), `GET /v1/spend/export?from=YYYY-MM-DD&to=YYYY-MM-DD` accepts `Authorization: Bearer <token>`. The window is whole UTC days, at most 93. The reply is `{"scopeId", "window", "asOf"?, "rows", "crons"}`. Each call is audited as `spend.export`.
