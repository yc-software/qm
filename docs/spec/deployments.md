# Deployments: the deployment directory, CLI, releases and CI

_Verified against `main` at eb148f69d (2026-11-24). Statements were read in the code at that commit unless marked **[interpretation]**._

## In one paragraph

This area turns the code in this repository into a running instance, and carries each merged change to the instances that already run. One running instance is a _deployment_: one or more copies of core (the server process), a Postgres database, object storage, a sandbox provider that runs the agents' computers, and an optional egress proxy that filters what those computers may reach. All of it sits in the operator's own account. The operator describes it in a _deployment directory_: a folder they commit, holding one config file (`qm.config.jsonc`), an optional `sandbox/` folder of tools and skills, and a `.env` file of secret values that stays out of Git. The `qm` CLI in `cli/` is the only program that reads that folder. It checks the folder, works out which secrets the chosen features need, turns the config into environment variables and provider resources, starts the images, and tests the live result. Core never sees the folder. It reads environment variables once at boot (`loadConfig` in `src/config.ts`), refuses to start when a required one is missing, applies its database migrations, and serves. Images come from one of two places: digests pinned inside a published `@yc-software/qm` npm release, or a build of the source at a commit the operator chooses. A change reaches `main` through a merge queue and CI, and there this repository's part ends: no workflow here deploys anything. Each deployment takes the change on its own schedule, by upgrading its npm pin or by building a newer commit. So there is no single "production". There are as many deployments as there are operators, the four [deployment shapes](../SPEC.md#deployment-shapes) differ only in settings, credentials and rows, and nothing in this repository can list them or coordinate with them.

## One deployment, traced end to end

Ada is an operator at Acme. She sets up a [Package deployment](../SPEC.md#deployment-shapes) on AWS. Steps 1 to 9 take her from an empty repository to a passing live check. Steps 10 to 14 follow one merged pull request to each of the four shapes.

1. **Scaffold.** In an empty private repository Ada runs `npm exec --yes --package=@yc-software/qm@latest -- qm init . --org acme --target aws`. `main` in `cli/src/cli.ts` dispatches to `runInit` in `cli/src/commands/init.ts`. `runInit` looks the target up in `HOSTING_PROVIDERS` (`cli/src/backends/registry.ts`) and uses its scaffold (`awsScaffold` in `cli/src/provider-scaffold.ts`). It writes `qm.config.jsonc`; a `package.json` that pins the exact CLI version (`packageContent`); `.env.example` (`renderEnvExample`); a mode-600 `.env` with locally generated signing keys (`mintLocalSecret`); `.gitignore`; `AGENTS.md`; `deployment.md` and `.codex/skills/deploy-qm/`, copied from `cli/templates/deployment/`; Slack app manifests; a sample `sandbox/`; and, for AWS only, `infra/` with the Terraform module from `cli/templates/aws/`. It refuses to overwrite an existing config, and refuses when `.env` is tracked by Git.
   - _Other targets:_ the default target is `docker`, a local test drive. `render` also needs `--repo` and `--branch`. Changing target means a new directory, because config, files and secret rules are scaffolded as one unit.
2. **Collect secrets.** `qm setup` runs `runSetup` (`cli/src/commands/setup.ts`). It asks `computedSecrets` (`cli/src/secrets.ts`) which secrets this config needs, generates the ones it can, prompts for the rest with hidden input, and writes them to `.env`.
3. **Check the folder.** `qm check` runs `runCheckCommand`, then `runChecks` (`cli/src/commands/check.ts`). `loadConfigAt` (`cli/src/config.ts`) parses the config and rejects an unknown top-level key or a `contract` other than 1. `validateSandboxLayer` (`cli/src/sandbox-layer.ts`) checks tools and skills. `discoverPlugins` (`cli/src/plugins.ts`) finds the operator's own services. The target's `validateConfig` checks provider fields. A secret-shaped name under `env` fails with clause `config.no-secret-values`. Nothing is built. The only network calls verify credentials whose values are already in `.env`. `plan`, `up`, `doctor` and `sandbox build` run `runChecks` first.
4. **Create the infrastructure (AWS only).** `qm infra render` runs `renderTerraformVars` (`cli/src/terraform.ts`) and writes `infra/terraform.tfvars`. Ada runs Terraform herself; the CLI never applies it. `qm infra build-image` runs `buildAwsMicrovmImage` (`cli/src/commands/infra.ts`), which builds the sandbox image and records its version in the config.
   - _Other targets:_ Docker, Fly and Render have no Terraform step; `qm up` creates what it needs.
5. **Store the secrets.** `qm secrets push` runs `awsSecretsPush` (`cli/src/backends/aws.ts`) and uploads the values to Secrets Manager under `aws.secretsPrefix`. Terraform owns `DATABASE_URL`, because it created the database. Docker reads `.env` directly and uploads nothing.
6. **Check prerequisites.** `qm doctor` runs `awsDoctor`. It only reads: the caller's account, the ECS cluster and services, ECR, RDS, routing, the deploy role's trust, each required secret, and the sandbox image pin.
7. **Deploy.** `qm plan` is `qm up --dry-run`. `qm up --yes` runs `awsUp`. In order it: takes a DynamoDB lease so two deploys cannot overlap (`acquireAwsLease` in `cli/src/aws-lease.ts`); confirms the database has a current point-in-time restore point (`assertPredeployDbRestorePoint`); copies each service image from the digest in `cli/manifest.json` (`manifestRef` in `cli/src/manifest.ts`) into Acme's ECR (`publishWorkloadImage`); renders one task definition per service (`renderTaskDefinition`, with plain values from `serviceEnvironment` and secret references from `secretArns`); updates the ECS services and waits until only new tasks serve (`applyServiceTargets`, `awaitServiceTargets`); sends `sandbox/` to core (`syncAwsLayerAfterRoll`, which calls `PUT /v1/deployment-layer`); and records the result as a deployment manifest (`recordDeploymentManifest`). A failure before the record restores the previous task definitions and layer.
   - _Source checkout:_ `cli/manifest.json` in this repository holds placeholder digests at `registry.invalid`. From a checkout Ada would add `--build-from <checkout>`, and `publishWorkloadImage` builds `deploy/<service>/Dockerfile` instead of copying.
8. **Core boots.** In each new task `src/index.ts` calls `loadConfig`, then `startQm` (`src/start.ts`). `startQm` builds every store and service (`buildApp` in `src/wiring.ts`), applies database migrations (`migrateRegisteredPgSchemas`), installs the cron queue (`installCronQueue`), finds the boot tenant, which is the one organization of a single-organization database (`bindBootTenant`), waits for the deployment layer, listens for the API on `PORT`, starts the public front door on `PUBLIC_PORT` (`startFrontDoor`), and last starts background work: the cron scheduler and Slack.
9. **Prove it.** `qm check --live` runs `awsCheckLive`. It compares the live task definitions, environment, secret routing and release label with the folder, in both directions. Then it runs one real agent turn against the deployed core, as a one-off task inside the private network (`awsLiveSession`, which runs `src/deployment/postdeploy-smoke.ts`). `qm conformance` (`runConformance`) then compares the tools core resolved with `sandbox/tools`.
10. **A change merges.** Later a contributor's pull request passes CI and is queued. `cicd.yml` runs on the queue's commit. `select` in `scripts/select-ci.ts` picks the tests the changed files can reach. `reusableCi` in `scripts/reuse-ci.ts` skips them when the queue commit has the same tree as the pull request's own green run. After the push to `main`, `cicd.yml` runs again and reuses the queue's result (`mergeQueueCi`), and `full-suite.yml` runs everything. No deployment has changed yet.
11. **Package deployment (Acme).** The change reaches Acme after two human acts. First a maintainer starts `release.yml` by hand. Its preflight requires the run to be on `main`, the newest `cicd.yml` run for that commit to be green, and no open issue labelled `release-blocker`. `release-package.yml` builds and signs three images. `publish-cli.yml` writes their digests into `cli/manifest.json` and publishes the package under the npm tag `next`. The workflow then tags `v<version>` and creates a GitHub prerelease; moving `latest` is a manual command the run prints. Second, Ada raises the pinned version in Acme's `package.json` and repeats steps 3, 6, 7 and 9.
12. **Platform-hosted deployment.** On Render the deployment directory still pins the CLI, but the runtime does not come from the release. `qm up` (`createRenderBackend` in `cli/src/backends/render.ts`) resolves `render.source.branch` with `git ls-remote`, pins the build to that commit, and Render builds from Git. The change arrives at the next `qm up` after that branch contains it, released or not. Porter has no CLI target: the operator applies `porter/apps/core.yaml` and `porter/apps/egress-proxy.yaml`, which build this repository's Dockerfiles, or installs the chart in `deploy/helm` with an image tag they choose.
13. **Source-built deployment.** The operator's own pipeline, outside this repository, picks a green commit of `main` and builds it: `qm up --build-from <checkout>`, or on AWS `qm up --build-only --image-label <label> --candidate-out <file>` and then `qm up --candidate <file> --yes`. The candidate path applies migrations in a one-off task (`runAwsCandidateMigration`, which runs `src/migrate-main.ts`) before any service changes. The `notify-deployments` job in `cicd.yml` can tell such a pipeline that a commit is green.
14. **Multi-tenant deployment.** Build and rollout work as in step 11 or 13. What differs is reach: tenants are rows in `tenants`, so one rollout and one migration run change every organization at once. Per-tenant differences are not deployed. They are values in `tenants.settings`, set with `qm tenant settings set` (`runTenantCommand` in `src/tenants/operator.ts`), and each core re-reads them every 30 seconds.

## The parts

### `cli/src/cli.ts` and `cli/src/commands/` (about 700 and 2,300 lines)

**Job.** Parse `qm <command>`, load the folder, and call one command module or the target's backend.

**Key idea.** One CLI serves three people, and its help text groups them. An operator in a deployment directory gets `init`, `setup`, `check`, `doctor`, `plan`, `up`, `secrets`, `status`, `logs`, `down`, `rollback`, `sandbox build`, `ui publish`, `layer sync`, `outputs`, `admin-login`, `conformance`, `infra` and `migrate`. An operator of a database with several tenants gets `tenant` and `db`. A contributor gets `dev`.

**Surprising.** (1) `tenant`, `db` and `dev` are not in the npm package. They spawn `scripts/tenant.ts`, `scripts/db.ts` and `scripts/dev/cli.ts` from the Git root, so they work only in a source checkout. (2) `qm sandbox build` (`runSandboxBuild`) is a local validation build; no running sandbox boots its output. Tools reach sandboxes through the deployment layer. (3) `qm ui publish` (`runUiPublish`) changes the browser app without restarting core, but only where the release store is an S3 bucket the operator can write. (4) `check --json` reports by clause id, exits 1 for a failed check and 2 for a bad invocation.

### `cli/src/config.ts` (about 1,700 lines)

**Job.** Define and validate `qm.config.jsonc` (`QmConfig`, `loadConfigAt`).

**Key idea.** The file is JSON with comments. Its top-level keys are a closed set (`VALID_TOP_LEVEL_KEYS`), so a misspelled one fails. `publicUrl` is the one public address, and the CLI derives every other URL from it.

**Surprising.** (1) Strictness stops one level down. `env.<service>` is an open map of strings that every backend forwards unchanged. A misspelled or retired name under `env.core` passes `qm check` and does nothing. (2) Some names under `env.core` are read by the CLI and never by core, for example `AWS_PUBLIC_ORIGIN_URL`. (3) About 400 of the lines validate the `aws` block alone.

### `cli/src/providers.ts`, `cli/src/services.ts`, `cli/src/secrets.ts` (about 1,100 lines)

**Job.** The three catalogs the rest of the CLI reads: targets and the sandbox backends each allows (`SANDBOX_BACKEND_POLICY`); services and the environment derived for them (`orgEnv`, `brokerWiring`); and secrets (`FIRST_PARTY_SECRET_SPECS`).

**Key idea.** A secret is required because of what the config selects. Each spec carries a condition: a service is enabled, a target or sandbox backend is chosen, an `env` value is set, a model provider is named. `computedSecrets` evaluates them once, and `.env.example`, `qm setup`, `qm secrets push`, `qm doctor` and the backends all read that result.

**Surprising.** (1) `slack` and `auth` appear under `services` but are not workloads: `serviceHost` maps both to `core`. (2) The CLI names seven sandbox backends; core accepts eleven (`sandboxBackendEnvStrict` in `src/sandbox/sandbox-settings.ts`). The other four are reached only by writing `env.core.SANDBOX_BACKEND` by hand. See [sandboxes](./sandboxes.md).

### `cli/src/backends/` (about 9,000 lines; `cli/src/backends/aws.ts` about 4,600)

**Job.** One module per target, each implementing `Backend` (`cli/src/backends/types.ts`): `up`, `status`, `logs`, `down`, `rollback`, `doctor`, `secretsPush`, and optionally `checkLive` and `migrateCandidate`. `cli/src/backends/registry.ts` maps a target to its backend, scaffold, accepted `up` flags and config checks.

**Key idea.** Every target does the same three things in its own vocabulary: choose an image per service, render core's environment and secret references, and make the provider match. `docker` runs local containers and its own Postgres (`dockerUp`). `fly` renders one Fly app per service from `cli/templates/fly/` (`flyUp`). `aws` registers ECS task definitions on infrastructure that Terraform created. `render` creates services that Render builds from Git.

**Surprising.** (1) The targets are not equal. Rollback exists on AWS and Render; Docker and Fly throw "not implemented". Docker has no `checkLive`. Candidates, the migration task, the deploy lease, the recorded manifest and drift detection are AWS only. (2) Blue-green comes from the target, not from a deployment shape. The AWS Terraform module sets the ECS `BLUE_GREEN` strategy for every service except the egress proxy, and `cli/templates/fly/core.toml` sets `strategy = "bluegreen"`. (3) Render rejects `imageOverrides`: its services always build from `render.source`. (4) The master's Wall of shame names the AWS backend under God files.

### `cli/templates/`

**Job.** Files that ship in the package and that `qm init` copies: the operator workflow (`cli/templates/deployment/deployment.md`, `cli/templates/deployment/SKILL.md` and `cli/templates/deployment/references/`), the AWS Terraform module, Fly app templates and Slack manifests.

**Key idea.** These are product, not documentation. An agent in the operator's repository follows them step by step. Operator procedure belongs there; this spec says only what the code does.

**Surprising.** (1) Terraform is vendored. After `init` the copy in `infra/` belongs to the deployment, and upgrading the CLI does not change it. `assertTerraformScaffoldSupportsConfig` refuses to deploy over a copy that is too old. (2) `cli/templates/deployment/references/porter.md` ships in the package, but `scaffoldDeploymentSkill` copies only the `fly`, `aws`, `render`, `slack` and `email` references. (3) The repository's own `.codex/skills/deploy-qm/` and root `deployment.md` are pointers to these files, not copies.

### `src/config.ts` (about 700 lines)

**Job.** `loadConfig` turns the environment into one typed `Config`, once, at boot.

**Key idea.** Fail at boot, not at first use. A bad number, an unknown choice or a missing required secret throws before the server listens.

**Surprising.** (1) An unknown variable is ignored without a word. The environment has no closed key set. (2) "Production" means `NODE_ENV=production`, which `deploy/core/Dockerfile` sets. Every image-based deployment is production to these checks, a local Docker test drive included. (3) `loadConfig` is not the only reader. `sandboxSettings` (`src/sandbox/sandbox-settings.ts`) and `deploySettings` (`src/deploy/deploy-settings.ts`) parse their own variables, the front door has its own boot checks (`bootChecks` in `plugins/portal/src/index.ts`), and about twenty files in `src` read the environment. By grep, `src` and `plugins` read about 390 distinct names. About 160 of them are named anywhere in the CLI, its templates, `deploy/`, `porter/` or the root `.env.example`.

### `src/start.ts` and `src/wiring.ts` (about 250 and 3,500 lines)

**Job.** `buildApp` in `src/wiring.ts` is the composition root: it constructs every store, service and route dependency from a `Config`. `startQm` in `src/start.ts` starts them in the fixed order of step 8.

**Key idea.** One core process is the whole product: API, run workers, scheduler, Slack, sign-in and the web UI. A deployment scales by running more copies of that process against one database.

**Surprising.** (1) Migrations run inside every core's boot, before it listens. During a rollout the new core migrates a database the old core is still serving. **[interpretation]** Each operator upgrades when they choose and may skip releases, so a migration has to work from any older schema with no step coordinated from outside. (2) Which copy does background work is decided at run time. Each core registers under a deployment key, `BACKGROUND_DEPLOYMENT_ID` or else the build's `GIT_SHA`. When a newer key is live, the older core stops claiming runs, firing crons and holding Slack connections (`createDrainController` in `src/runs/drain.ts`). See [turns](./turns.md) and [background work](./background-work.md). (3) Several missing settings only log a warning at boot: no `ADMIN_GRANTS`, an apps domain whose wildcard DNS does not resolve, a Docker app provider with no daemon. (4) `buildApp` is one function of about 2,800 lines.

### `src/deployment/` (about 1,300 lines)

**Job.** Core's side of the deployment directory: which secrets core demands (`secret-schema.ts`), the deployment layer at run time (`load-layer.ts`, `deployment-layer-store.ts`), and the live session test (`postdeploy-smoke.ts`).

**Key idea.** `CORE_SECRET_SPECS` is the code's own list of what is required and when. Each entry names a gate. The gate `production` is on in every image. Every other gate is a feature selection read from the environment: a sandbox backend, an app-hosting provider, a model provider, an OAuth client id, an email allow-list. `validateCoreSecretEnv` checks a secret only when its gate is on, and treats `changeme`, `todo`, `placeholder` and `replace-me` as missing.

**Surprising.** (1) A new entry under the `production` gate stops every existing deployment at its next upgrade. On AWS, Docker and Render the CLI names the missing secret before it changes anything (`secretArns`, `missingRequiredSecrets`). A chart-driven deployment finds out when core refuses to boot. (2) The full list of always-required settings is longer than this file. `buildApp` demands `DATABASE_URL` everywhere; `loadConfig` demands `PUBLIC_PORT` in production; `sandboxSettings` demands an explicit `SANDBOX_BACKEND` in production; the front door demands its sign-in settings. (3) Core imports CLI source. `deployment-layer.ts` re-exports `parseToolDescriptor` and `compileApproval` from `cli/src/tool-descriptor.ts`, and `deploy/core/Dockerfile` copies eight named `cli/src` files into the image. Moving one of those files breaks the core image, not the CLI. (4) The layer is stored per tenant and each core re-reads it every 30 seconds, so `qm layer sync` changes tools and skills without a restart.

### `src/feature-flags.ts` (about 130 lines)

**Job.** Per-scope switches for optional or unfinished product features. `FEATURES` names them, thirteen at this commit. `createFeatureFlagStore` reads and writes their rows.

**Key idea.** A flag is a row, not a setting. Its `enabledScopes` lists the scopes it is on for; the org scope means everyone. No row means off.

**Surprising.** Flags are not environment variables and not in `qm.config.jsonc`. No deployment template can turn one on. A feature behind a flag is off in every deployment until an admin there enables it. See [scopes](./scopes.md).

### `deploy/`, `fly/`, `local/`, `porter/`

**Job.** Build inputs. `deploy/core/Dockerfile` builds core, with the web UI inside. `deploy/egress-proxy/` builds Envoy plus an authorization process (`src/egress-authz-main.ts`). `fly/Dockerfile` builds the sandbox base image. `deploy/helm/` is a Kubernetes chart for core and the proxy. `porter/apps/` holds the Porter app files. The rest are per-provider sandbox and app-runner images (`deploy/e2b/`, `deploy/do-managed-agents/`, `deploy/porter-runner/`, `deploy/render-runner/`, `deploy/render-minio/`, `local/Dockerfile`, `porter/Dockerfile`) and `deploy/connector-sdk/`.

**Key idea.** Two images are the product: core and the egress proxy. A release signs those two and the sandbox base.

**Surprising.** (1) `deploy/layers/` holds only a README here, on purpose. A private source fork keeps its own deployment directory there, and nothing under it may come back upstream. (2) `deploy/stacks/` is test fixtures, not deployments: `cicd.yml` runs `deploy/stacks/*/test/*.test.ts` against the built package. (3) `fly/Dockerfile` has nothing to do with the Fly target. The directory name is older than its present use. (4) The Helm chart and the Porter files do not go through the CLI. The chart derives core's environment in `deploy/helm/templates/deployment.yaml`; on Porter the operator sets it by hand.

### `.github/workflows/`

**Job.** `cicd.yml` tests pull requests, merge-queue commits and pushes to `main`. `full-suite.yml` runs all of `cicd.yml` on every push to `main`. `wall-of-shame.yml` checks a pull request's review report. `release.yml` cuts a release by hand and calls `release-package.yml` (images) and `publish-cli.yml` (npm). `pgbouncer.yml`, `desk-native.yml` and `ios-native.yml` are narrower checks.

**Key idea.** Test only what a change can reach, and never test the same tree twice. `select` follows imports from the changed files to test files. `reusableCi` proves the merge-queue commit has exactly the tree a green pull-request run recorded. `mergeQueueCi` proves the commit on `main` is the one the queue tested.

**Surprising.** (1) No workflow deploys. A release publishes images, a package and a tag, and stops. (2) The release preflight asks for a green `cicd.yml` run, which on `main` may be a reused result. It does not ask for `full-suite.yml`. (3) Some changes run everything: `package.json`, the lockfile, anything under `.github/` or `vendor/`, a non-code file under `src/`, a seeded skill. (4) `Production dependency audit` is never reused, because advisories appear after a tree was tested. (5) `publish-cli.yml` runs only in the repository `yc-software/qm`. In a fork the release stops at that job.

### `scripts/`

**Job.** CI helpers (`select-ci.ts`, `reuse-ci.ts`, `wall-of-shame-check.ts`, `run-root-test-shard.mjs`, `check-published-upgrade.sh`, `smoke-core-image.sh`), the entry points the CLI spawns (`tenant.ts`, `db.ts`), provider image builders and smoke tests, and the dev instance supervisor in `scripts/dev/` (about 3,900 lines).

**Key idea.** A dev instance is a real stack, not a mock: one supervised core with real Postgres, a real model and a real sandbox, in a numbered port slot so several worktrees run side by side. `scripts/dev/supervisor/main.ts` restarts crashed children and probes health.

**Surprising.** (1) `check-published-upgrade.sh` is the one mechanical guard for databases that already exist. In the `Core Postgres tests` job it checks out the latest release tag, migrates an empty database with it, then migrates that database twice with the pull request's code. A migration that cannot follow the last release fails there. It does not cover older releases, and it does not cover required secrets. (2) `wall-of-shame-check.ts` reads its list of lenses from the headings under `## Wall of shame` in the master spec, so renaming a lens there changes what every pull request must report.

## Optional and per-deployment

## Where the complexity lives

Line counts mislead here too. The weight is in choices that multiply and in jobs done in several places.

**Things that multiply each other.** A deployment is one pick from each of five lists: four targets; eleven sandbox backends in core, seven of them named by the CLI and narrowed per target by `SANDBOX_BACKEND_POLICY`; six app-hosting providers (`DEPLOY_PROVIDER`); three sign-in routes (the built-in broker, Slack OIDC, another OIDC provider); and five image sources (the release's digests, `--build-from`, `imageOverrides`, an AWS candidate, Render's Git build). Each combination has its own required secrets and derived environment. A change tested on one combination says little about another. The master's Wall of shame records this under Config-matrix expansion and Prod-like QA.

**Environment names against the places that set them.** Core reads about 390 names and the CLI, charts and templates name about 160. The rest reach a deployment only when its operator types them. An opt-in variable that nothing sets is off in every deployment. That is the Config-matrix expansion entry about an opt-in flag no template set.

**Parallel mechanisms doing one job.**

| Job                         | Mechanism A                                                      | Mechanism B (and C)                                                                                                                                                                                                                                                                                                                 |
| --------------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Say what must be set        | `CORE_SECRET_SPECS` and `validateCoreSecretEnv`, at core's boot  | `FIRST_PARTY_SECRET_SPECS` and `computedSecrets` in the CLI; `bootChecks` in `plugins/portal/src/index.ts`; plain throws in `loadConfig`, `buildApp`, `sandboxSettings` and `deploySettings`. `test/secret-schema-drift.test.ts` and `test/secret-schema-conformance.test.ts` hold the first two together. The lens is Duplication. |
| Render core's environment   | `serviceEnvironment` for AWS                                     | The Fly `managed` and `stackKeys` lists in `cli/src/services.ts`; `dockerUp`; `cli/src/render-services.ts`; `deploy/helm/templates/deployment.yaml`; by hand on Porter                                                                                                                                                              |
| Apply migrations            | Every core, at boot                                              | The one-off `src/migrate-main.ts`, used by the AWS candidate path and by `check-published-upgrade.sh`                                                                                                                                                                                                                               |
| Ship the web UI             | Inside the core image, published at boot                         | `qm ui publish`, straight to the object store                                                                                                                                                                                                                                                                                       |
| Supply the deployment layer | The `deployment_layer` table, through `PUT /v1/deployment-layer` | A `DEPLOYMENT_LAYER` directory read at boot                                                                                                                                                                                                                                                                                         |
| Test a push to `main`       | `cicd.yml`, which reuses the queue's run                         | `full-suite.yml`, which runs everything                                                                                                                                                                                                                                                                                             |

| Roll back                   | AWS restores a recorded manifest                                 | Render rebuilds an earlier commit; Fly and Docker cannot                                                                                                                                                                                                                                                                            |

**Abstractions with one implementation.** `Backend.migrateCandidate`, the `infra` operations on a hosting provider, release candidates, the deploy lease and the deployment manifest exist for AWS only. The only `contract` value the CLI accepts is `1`. Six clause ids in the status table below appear nowhere in `cli/src` or `src`; one of them, `extension.deployment-data-proxy`, has no implementation at all.

**Transitional code that is still there.**

- `sandbox.env` and `sandbox.secretEnv`. The CLI validates them and delivers each name to core as `FLY_RESIDENT_ENV_<NAME>` (`sandboxCoreEnv`, `secretDestinations`). No file in `src` or `plugins` reads a variable with that prefix. At this commit they do not reach a sandbox.
- Retired config keys. `securityScreen: { "backend": "off" }` loads as mode `off` with a warning, and other retired screening keys fail. `sandbox.image` on a backend other than `local` is ignored with a warning.
- `assertTerraformScaffoldSupportsConfig` refuses a vendored Terraform module from before core served the public front door.
- `src/sessions/published-upgrade.ts` keeps the migration chain for a database created by release 0.1.15. `test/postgres-published-upgrade.test.ts` runs it against a saved schema.
- `packageContent` deletes a dependency named `qm-cli` from a deployment's `package.json`. **[interpretation]** That was the package's earlier name.

**How to tell whether a setting does anything.** Search `src`, `plugins` and `cli/src` for the bare name. A read takes one of three forms: `env.NAME`; a helper called with the name as a string, such as `optNum(env, "NAME", …)`; or the CLI reading `config.env.core.NAME`. A name found in none of them has no effect, whatever a deployment's config says.

## Contracts

Outside systems and operators depend on the exact formats below.

**Deployment directory layout.** `init` writes it; `check` validates it.

```text
qm.config.jsonc          the config; committed; no secret values
package.json             pins @yc-software/qm at one exact version
.env.example             computed secret names and what enables each; never values
.env                     secret values; mode 600; never committed
sandbox/tools/<id>/tool.json, sandbox/tools/<id>/<files>, sandbox/skills/<id>/SKILL.md, sandbox/Dockerfile (optional)
plugins/<name>/Dockerfile   the operator's own services
infra/                   AWS only: vendored Terraform and terraform.tfvars
slack-app-manifest.yml, slack-sso-manifest.yml (Slack OIDC only), deployment.md, AGENTS.md, .codex/skills/deploy-qm/
```

**`qm.config.jsonc`.** Required: `contract` (must be `1`; another integer fails as an unsupported major), `orgId` (a lowercase DNS label), `publicUrl` (an origin with no path), `target`, and `services` including `core`. Optional: `apiUrl`, `model`, `modelProvider` (`anthropic`, `openai`, `openrouter`), `basePort`, `plugins`, `skills`, `env`, `secretEnv`, `securityScreen`, `vms`, `imageOverrides`, `sandbox`, `botName` (at most 31 characters), `orgName` (at most 40), `appPrefix`, `region`, `flyOrg`, `imageFrom`, `deployAppPrefix`, `aws`, `render`. Any other top-level key fails. `env.<service>` holds non-secret strings. `secretEnv.<service>` maps an environment name to a secret-store name. Ports and the `SECURITY_SCREEN*` names are managed by the CLI and cannot be set in either. Target `fly` requires `region`, `flyOrg`, and S3 settings for snapshots and transfers. Target `aws` requires an `aws` block with coordinates for every service and plugin, and an HTTPS `publicUrl`. Target `render` requires a `render` block. The semver-stable programmatic surface is the export `@yc-software/qm/contract`.

**Sign-in callback.** An external identity provider must register exactly `<publicUrl>/auth/callback`.

**Deployment layer API.** `PUT /v1/deployment-layer` and `GET /v1/deployment-layer` on core. Requests are signed with `CORE_SIGNING_SECRET`: headers `x-timestamp` and `x-signature: v0=<hex HMAC-SHA256 of "v0:<timestamp>:<METHOD>\n<path>\n<body>">`. The body is `{"contract": 1, "tools": [{"path", "content", "executable"?}], "skills": [...]}`, text files only, at most 1 MB. Core validates it again, stores it, versions it by content hash, and writes one `deployment_layer.updated` audit record.

**Tool descriptor (`tool.json`).** Only `id` is required. `label` names the tool in login status. `advertise` adds it to the agent's list of installed CLIs. `hints` are added to the model's tool guidance. `auth.check` and `auth.reauth` are the commands that test and renew a login. `auth.credentialPaths` lists `$HOME`-relative `{path, kind}` entries (`file` or `directory`) to capture and restore. `auth.splitEnv` and `auth.broker` (kind `aws-role`) configure credential vending. `egress` lists hosts; it is validated and not enforced. `approvals` are rules that may require approval or deny for the tool's own binary, and can never allow. `install.binary` names the executable. `install.files` are text files beside `tool.json`, each `{from, to, mode}` with `to` under `/usr/local/bin/` or `/usr/local/lib/<id>/`. See [sandboxes](./sandboxes.md) and [security](./security.md) for what each buys at run time.

**Images and releases.** Images are `ghcr.io/yc-software/qm/<core|egress-proxy|sandbox-base>:<40-character commit sha>`, built for `linux/amd64` and signed with cosign under the identity of `release-package.yml` on `main`. `cli/manifest.json` is `{"sandboxBase": "<ref>", "services": {"core": "<ref>", "egress-proxy": "<ref>"}}`, every reference pinned by `@sha256:`. A release's version is one patch above the higher of the latest `v*` tag and the published npm version, or the version in `cli/package.json` when that is higher. It is published under the npm tag `next`. An existing tag is never moved.

**CI names.** Downstream release pipelines match these as text, so renaming one silently stops a deployment's releases. Workflow files: `cicd.yml` (named `CI/CD`), `full-suite.yml` (`Full suite`), `release.yml`, `release-package.yml`, `publish-cli.yml`, `wall-of-shame.yml`. Job names in `cicd.yml`, also listed as `CI_JOBS` and `PR_JOBS` in `scripts/reuse-ci.ts`: `Select tests`, `Core typecheck`, `Core`, `CLI`, `Lint`, `Production dependency audit`, `Core Postgres tests`, `Web UI plugin`, `Auth plugin`, `Portal plugin`, `Co-author trailers`, `Certify tested tree`. The receipt line is `QM_CI_TREE={"sha","tree","runId","attempt","pr"}`.

**Green-`main` webhook.** When configured, the `notify-deployments` job sends `POST <url>` with `content-type: application/json`, `x-github-event: push`, `x-hub-signature-256: sha256=<hex HMAC-SHA256 of the body>` and the body `{"event":"main_green","repository":"yc-software/qm","sha":"<sha>","run_id":<n>,"attempt":<n>}`. A failed delivery is a warning, not a failed run.

**Wall of shame report.** A pull request's description needs a section `## Wall of shame review report` with a line ``Reviewed commit: `<head sha>` `` and a table whose columns are lens, reviewer, verdict, score (`N/100`) and assessment. Verdicts are `Accept`, `Waived` (assessment `Waived by <name>: <what>`) or `Not relevant`. `wallOfShameProblems` reads the lens names from the `### <Lens> (…)` headings of the master spec and treats the marks `(always reviewed` and `(checked by CI` specially.

**AWS candidate and progress files.** `up --build-only` writes `{"contract": 1, "accountId", "region", "label", "images", "imageProvenance", "architectures"}`. With `QM_DEPLOY_PROGRESS_FILE` (an absolute path) and `QM_DEPLOY_PROGRESS_TOKEN` set on a candidate deploy, the CLI writes `{"phase": "monitoring", "token", "orgId", "targets"}` once every service update is submitted. The exit status still decides success.

**Web UI release store.** Under `web-ui/` in the object store: `assets/<name>` shared by all releases, `releases/<id>/<file>` with `index.html` written last, and `live.json` as `{"release": "<id>", "deployed": "<id>"}`. An id is 64 hex characters.

**Security screen proxy.** `securityScreen.classifier: "proxy"` selects an external classifier. Its wire protocol is in [security](./security.md#contracts).

**Spend and app export.** With `SPEND_EXPORT_TOKEN` set (at least 32 characters, different from every other environment value), `GET /v1/spend/export?from=YYYY-MM-DD&to=YYYY-MM-DD` and `GET /v1/apps/export?principalId=<id>` accept `Authorization: Bearer <token>`. The spend window is whole UTC days, at most 93. The spend reply is `{"scopeId", "window", "asOf"?, "rows", "crons"}`. Each call is audited as `spend.export` or `app.export`.

**Clause status.** `qm check --json` reports results under clause ids. This table is parsed by a test, which requires every ENFORCED row to name code that exists.

| Clause                            | Status         | Verifier                                                                         |
| --------------------------------- | -------------- | -------------------------------------------------------------------------------- |
| `config.v1`                       | ENFORCED       | `loadConfigAt`, `qm check`                                                       |
| `config.no-secret-values`         | ENFORCED       | `qm check`                                                                       |
| `secrets.computed-set`            | ENFORCED       | typed schema, `qm check`                                                         |
| `sandbox.descriptors`             | ENFORCED       | `validateSandboxLayer`, core PUT validation                                      |
| `sandbox.approvals-tighten`       | ENFORCED       | descriptor parsers, command-policy composition                                   |
| `runtime.layer-resolved`          | ENFORCED       | deployment-layer store/API and core PUT validation, `qm conformance` cross-check |
| `aws.rendered-task`               | ENFORCED       | `renderTaskDefinition`, AWS `plan`/`up`, digest and task-diff tests              |
| `aws.live-drift`                  | ENFORCED       | `qm check --live`, bidirectional task/environment/secret/release checks          |
| `sandbox.egress`                  | VALIDATED-ONLY | wildcard/host warnings in `qm check`; no runtime enforcement claimed             |
| `sandbox.aws-substrate`           | ENFORCED       | Lambda MicroVM image/version validation and live drift                           |
| `target.provider-registry`        | ENFORCED       | provider registry and packed-artifact tests                                      |
| `extension.deployment-data-proxy` | RESERVED       | optional env-gated org adapter; not part of contract v1                          |

RESERVED names a slot and claims no implementation. `check --json` also emits ids the table lacks: `config.secretEnv`, `plugins.resolved`, `fly.live-readiness`, `render.live-drift`, `cli.invocation` and `cli.internal`.
