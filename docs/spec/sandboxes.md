# Sandboxes

_Verified against `main` at bd371980c (2026-11-24): statements were read in the code at c6056de14 and re-read where later commits changed it, unless marked **[interpretation]**._

## In one paragraph

A sandbox is a Linux computer, separate from core, on which the agent runs shell commands. The agent's own loop runs in core (the API server); a sandbox only executes what a tool call sends it and holds working files. Core keeps one database record per sandbox, called a _sandbox resource_: the scope that owns it, the provider that hosts it (the _backend_), and its lifecycle state. A scope may select one of its sandboxes as its _default_. A command that names no sandbox goes to the default, and in a scope with no default such a command fails until the agent selects one, creating it first if the scope has none. Eleven backends implement one TypeScript interface, `Sandbox`, and a router picks the backend for each call by reading the resource record. When a turn ends, its sandboxes are _torn down_. That means something different on each provider (stopped, paused, checkpointed, or left running), and the machine is brought back at the next use. What survives depends on the provider, so durable work belongs in git or Files (see [artifacts](./artifacts.md)), never only on a sandbox disk. The agent lists, creates, selects, restarts and retires sandboxes itself with the `sandbox` tool, and it is shown a load summary so it can decide where to run; core never moves or refuses work because a machine is busy. A background job is a detached process on a sandbox, recorded in Postgres and killed by a reaper when its time limit passes. Optionally, an egress proxy stands between sandboxes and the internet and checks each connection against the turn's policy; `local`, `aws` and `superserve` never use it, and `EGRESS_PROXY_EXEMPT_BACKENDS` leaves out others.

## One command, traced end to end

The running example: Ada at Acme, in a web DM, asks the agent to run a test suite, try the build on a second machine, and leave a long job running. Acme's deployment sets `SANDBOX_BACKEND=e2b` and also holds Modal credentials. Ada's personal scope already has a default sandbox on E2B.

1. **The turn gets a pool, not a machine.** `handleTurn` (`src/core/orchestrator.ts`) calls `createTurnSandboxes` (`src/core/orchestrator/sandboxes.ts`). It builds an empty per-turn pool with three kinds of slot: the default, scratch, and one per sandbox id. Nothing is provisioned until a tool needs it. One exception: if the session's history holds a tool call other than a skill read, and the turn is bound to a sandbox or its writable scope has a default, `handleTurn` starts opening that computer in the background so the first command does not wait. It skips this for a read-only turn (`strictReadOnly`), an ephemeral session, and a cron, webhook or monitor fire.
2. **The model calls `execute`.** The tool is defined by `computerTools` (`src/agent/agent-tools/computer.ts`) and wrapped by `validateSandboxTool`, which rejects unknown fields, and fields the chosen action does not take, before anything runs. The tool calls `execute` on the tool context built by `createToolContext` (`src/tools/primitives.ts`). That function checks the command against policy (`authorizeExecution`; the rules are in [security](./security.md)), picks the computer, puts the named credentials in place for this one command ([credentials](./credentials.md)), runs it, and masks secret values in the output.
3. **Picking the computer.** Ada's command names no `sandbox_id`, so the pool's `provision` (internally `openScoped`) asks `defaultComputer` (`src/sandbox/sandbox-resources.ts`) for the default of the turn's writable scope. With no default it throws `NoDefaultSandboxError`, whose text tells the agent to get one with the `sandbox` tool. Core never creates or selects a default for a scope on its own, apart from the one-time legacy import. It does create sandboxes that are not defaults: a subagent's own sandbox, swarm computers and job computers.
   - _Scratch._ `scope: "scratch"` opens a blank machine for this turn instead (`openScratch`). A command that names a credential marked `scratchOnly` is moved there even if it asked for the default or named a `sandbox_id`, and the tool result says so.
   - _Environment._ The writable scope is normally the conversation's own scope. If that scope is attached to an environment, `resolveEnvironmentId` (`src/environments/environment-store.ts`) substitutes the environment's id, which is the id of the scope the environment was created in, so the turn uses that scope's default sandbox. A turn with an external audience skips this and keeps its own scope.
   - _Subagent or swarm._ A child session told to use its own sandbox, and a swarm member, are bound to one sandbox id and skip the default ([delegation](./delegation.md)).
   - _Slack bot turn._ A bot's turn may use only a computer it created that no person's turn has used, or a swarm's computer while the swarm's template turn is a bot's, no person has used the swarm's computers and every message in the swarm came from that bot (`botMayUseComputers`; `botMayDirect` in `src/swarms/swarm-service.ts`), and its `sandbox` tool has no `set_default`.
4. **Routing and provisioning.** `provision` on the router (`createSandboxRouter`, `src/sandbox/sandbox-routing.ts`) reads the resource record, takes the backend it names, and calls that backend's `provision` with the record's backing scope id. If that backend is not constructed the call fails ("refusing to use a substitute computer"); the router never falls back to another provider. The E2B backend (`createE2bSandbox`, `src/sandbox/e2b-sandbox.ts`) reconnects to the machine or resumes it from pause, makes sure the workspace directory exists, and returns a `SandboxHandle`. The turn then records its run id on the resource as a holder (`hold`), a person's turn marks the record `personUsed`, and `reconcileProcesses` (`src/processes/reconcile.ts`) settles background jobs that exited while no turn was looking.
   - _Multi-tenant deployment._ When the `tenants` table did not hold exactly one row at startup, `requireTenantSeparation` refuses every backend outside `TENANT_SEPARATED` (`sprites`, `modal`, `superserve`). Those three give each organization its own provider account or a hashed name prefix (`src/sandbox/tenant-sandbox-shape.ts`). With exactly one row, any backend is allowed for a call bound to that organization or to none.
   - _Platform-hosted deployment._ The platform's template fixes the backend. For the Render target the CLI's generated services set `SANDBOX_BACKEND=render` and `SANDBOX_BACKEND_POLICY` (`cli/src/providers.ts`) allows no other. The steps are the same; only the backend behind the router differs.
5. **Running.** `run` on the router wraps the command with `withLoadProbe` (`src/sandbox/load-probe.ts`), which appends one marker line of load figures to stdout. The backend runs the script under a POSIX shell with stdin closed, pagers and prompts disabled, the handle's environment exported, and the workspace as working directory. `takeLoadSample` strips the marker line; the router stores the sample in `sandbox_loads` at most once every ten seconds and returns it on the result. The tool appends `[exit N]`, plus a `[pressure]` note when IO pressure is 50% or more. On later turns `defaultSandboxLoadLine` (`src/core/orchestrator/prompt-blocks.ts`) adds one summary line to the turn environment, only when two or more runs hold the default or its IO, memory or disk is strained.
6. **A second sandbox on another provider.** The agent calls `sandbox` with `list` (the configured providers and their supported actions, the sandboxes this turn may use, and the scope's default), then `create` with `backend: "modal"`. `create` in `createSandboxResources` writes a record in state `provisioning`, calls the Modal backend's `provision`, and moves the record to `ready` or `failed`. The new machine is blank: no files are copied and the default does not change. The agent passes the new id as `sandbox_id` on `execute`; `openResource` re-checks access through `accessResource` on every call.
   - _Another scope's sandbox._ Under Open sharing posture a turn that carries a person's authority (`personAuthorityTurn` in `src/core/orchestrator.ts`; never a bot's turn or one with an external audience) may target a sandbox owned by another scope the actor can use ([scopes](./scopes.md)). `createTurnSandboxAccess` then narrows egress to what both scopes allow and hands over the owning scope's command policy. The tool context applies both command policies, accepts only one-time approvals, and refuses a command that names credentials ("command credentials cannot be copied to another scope's computer"); the machine is opened without the connector environment.
7. **A background job.** `execute` with `background: true` goes to `backgroundStart`, then to `start` in `createBackgroundBroker` (`src/connectors/background-exec-broker.ts`). The router's `startRegisteredProcess` launches the process in the guest and `register` (`src/processes/process-registry.ts`) writes a `process_sessions` row with an expiry time; if the write fails the process is killed. The call returns a process id and up to five seconds of first output. The `background` tool then polls, sends input, stops, lists and watches by that id. A job stays on the sandbox it started on, even if the default changes.
   - _Private credentials._ A background job that names a `scratchOnly` credential cannot use a scratch computer, because scratch dies with the turn. `provisionJobComputer` creates a job computer for it instead.
8. **The turn ends.** `reclaimBox` runs `releasePool`. Scratch machines are destroyed, with three attempts. For each sandbox resource it removes this run from the holders, then asks the backend for `keepWarm` if another live run still holds the sandbox or a live job runs on it, and for `homeUnchanged` if the turn opened the default but never used it. E2B then takes a provider snapshot if one is due and pauses the machine. Modal checkpoints the home directory and leaves the machine running. This is the step where providers differ most; see the backend table below.
9. **The next turn restores it.** `provision` runs again. E2B resumes the paused machine. If the provider has lost it, the backend creates a replacement from the last snapshot; with no snapshot it raises an error instead of returning a blank machine. Files come back. Whether running processes come back depends on the provider.
10. **Reaping and retiring.** `createProcessReaper` (`src/processes/process-reaper.ts`) sweeps every 30 seconds under a leader lease. It claims jobs past their expiry, sends TERM and then KILL (`createReaperKillHook`), and marks them `reaped`. When the agent is done with the Modal sandbox it calls `sandbox` with `retire`. `retire` refuses while the sandbox is the scope's default or has live jobs, then calls the backend's `destroyScope`. The record stays, in state `retired` (a job computer's record is deleted instead, by `retireJobComputer`). A retired sandbox is never restored: whatever was not published to git or Files is gone.

## The parts

Most of `src/sandbox` is the eleven backends and their provider clients.

### `src/sandbox/sandbox.ts` — the contract

**Job.** Define `Sandbox`, the handle, the profile, command results and computer status. **Key idea.** Ten members are required: `profile`, `provision`, `run`, four file reads and writes, `listDir`, `removeDir`, `teardown`. Sixteen are optional, and callers test for them. **Surprising.** A missing optional method is not a startup error. The matching `sandbox` action is simply not offered for that provider, or the call fails: with `CapabilityUnsupportedError` in the router, and with a plain `Error` (`sandbox status unavailable: <backend>`, `sandbox restart unavailable: <backend>`, `sandbox retirement unavailable: <backend>`) in `createSandboxResources`. `computerVerdict` calls a machine that exists but does not answer a shell probe `wedged`, unless its lifecycle state is `paused`, which counts as `ok`.

### `src/sandbox/sandbox-routing.ts` — the router

**Job.** Be the one `Sandbox` object the rest of core holds, in front of every constructed backend. **Key idea.** A handle carries `backend` and `resourceId`. Each call on a handle that has a resource id is forwarded to that backend inside `use` on the resource, which refuses retired sandboxes; a scratch handle has none and goes straight to the backend. Commands and file operations take no lock. Starting a background job through `startRegisteredProcess` holds the `sandbox-resource:<id>` advisory lock in shared mode across the launch and the write of the job's registry row; in the router destroy, restart, and plain teardown on backends that park (`parksOnTeardown`: `local`, `e2b`, `aws`, `do-managed-agents`) take it exclusively, as do `create`, `retire` and `retireJobComputer` in `src/sandbox/sandbox-resources.ts`, so each waits for every start in flight. **Surprising.** The router's own `profile` is the default backend's, so `sandbox.profile` describes the deployment default, not the sandbox in hand; `profileFor` answers for a scope or sandbox. The load probe is added here, so every command on a resource runs inside a wrapper, while scratch commands are not sampled. The router also records one `io_pressure_high` error per episode (opens at 75% IO pressure, clears below 40%).

### `src/sandbox/sandbox-resources.ts` — records, defaults and access

**Job.** Create, list, select, restart and retire sandbox resources; keep holders and load samples; decide who may use what. **Key idea.** `list`, `create`, `access`, `status`, `restart`, `retire` and `setDefault` check that the actor may use the owning scope; the other calls (`get`, `getMany`, `resolve`, `use`, `hold`, `release`, `notePersonUse`, the load calls and the job-computer calls) check nothing and rely on their callers. `forTurn`, which `handleTurn` uses only for a turn with an external audience, additionally admits the turn's actor in the turn's own scope while the run is still current. Selecting a default changes routing only. **Surprising.** The file also carries the bot-versus-person rules and two data migrations. `create` takes a long list of positional parameters. On first use per organization it runs a one-time import, `upgradeLegacySandboxes` (`src/sandbox/sandbox-resource-upgrade.ts`), which writes a `legacy` record in state `unverified` for every scope it knows of at that moment (scopes with sessions, environments, existing resource records, rows of the old `sandbox_routing` table, and E2B, Modal, AWS and Superserve body records), without checking that a machine exists, and selects it as that scope's default unless a default row already exists.

### The backends — `src/sandbox/e2b-sandbox.ts` and ten siblings

**Job.** Implement `Sandbox` for one provider, one file per backend name. The exception in naming is `do-managed-agents`, which lives in `src/sandbox/managed-agents-sandbox.ts`. Six providers also have a client file beside it that wraps the provider SDK or API (for example `src/sandbox/e2b-client.ts`).

**Key idea: the contract every backend meets.**

- `provision(backingScope, options)` finds or creates the machine named after the backing scope, makes the workspace directory, links resident credential paths ([credentials](./credentials.md)), installs the deployment layer's tool files after a checksum probe (on seven backends; see below), and returns a handle. Calling it again is safe. With `scratch` it returns a throwaway machine, counted by reference. With an egress token and a configured proxy, the proxy settings go into the handle's environment.
- `run` executes the command under a POSIX shell (not always bash) from the workspace, with stdin closed and a non-interactive environment, and returns stdout, stderr, exit code and `timedOut`. An abort signal kills the command's process group (not on `aws`; see below).
- File operations take paths relative to the handle's workspace root.
- `teardown` with no options releases the machine and preserves the home by the provider's own means. `keepWarm` leaves it running. `destroy` deletes machine and storage. Scratch is deleted when its last reference is released.
- Background processes are not a provider feature. All eleven backends use `createExecProcessSessions` (`src/sandbox/exec-process-session.ts`), which keeps each job's command, output, stdin pipe and exit code as files under `~/.agent-proc/<process id>/` and drives them through `run`. A job found after a reboot is marked exited with code 137.

**What actually differs.** "Actions" are the `sandbox` tool actions offered besides `create`. "Locked egress" means the provider's own network rules admit only the proxy host when `EGRESS_PROXY_URL` is set.

**Surprising.** (1) "Restart" is not one operation. Sprites restarts in place; it restores the newest checkpoint only when that restart call fails and the provider's check then reports the machine unhealthy, and otherwise raises the failure without restoring. Modal checkpoints the home and terminates the machine, and the next use restores into a fresh one. DigitalOcean rolls back to its checkpoint, or with a bucket snapshots the home and replaces the session. Render boots fresh from a filesystem snapshot, so processes end. (2) An action missing from the table fails if called: `status` on `local`, `aws` and `agent37`, `restart` on six backends. Porter cannot retire, so a background job that needs a job computer is refused there. (3) On `aws` an abort signal is checked only before the command starts; the other ten kill the running command. (4) Backends that restore homes refuse to hand back a blank machine when a saved home exists but failed to restore; they raise an error instead. (5) Modal keeps only the home: packages installed outside it last until the machine is replaced. (6) Scratch computers have no `sandbox_resources` row. (7) Only seven backends are given the deployment layer's install files. `local`, `aws`, `agent37` and `porter` are not, yet `aws`, `agent37` and `porter` still list the layer's tools in their profile, so there the tools must already be in the image.

### Shared guest helpers — `src/sandbox/exec-sandbox-base.ts` and neighbours

**Job.** The parts of a backend that are plain shell run in the guest: provisioning order and scratch counting (`src/sandbox/exec-sandbox-base.ts`), tar-based file import and export (`src/sandbox/exec-file-ops.ts`), killing an aborted command (`src/sandbox/exec-kill.ts`), home snapshots (`src/sandbox/home-snapshot.ts`), the load probe (`src/sandbox/load-probe.ts`), tool installation (`src/sandbox/layer-tool-install.ts`) and the proxy environment (`src/sandbox/sandbox-env.ts`). **Key idea.** Anything expressible as a shell script over `run` is written once here. **Surprising.** `createExecSandboxBase` is used by only three backends (`sprites`, `smolmachines`, `render`); the other eight repeat its provisioning and scratch logic. Home snapshots skip job computers, so nothing a job computer writes outlives it.

### `src/sandbox/sandbox-settings.ts` — environment to settings

**Job.** Read the backend and provider environment variables into `SandboxSettings` (the tool and job time limits, the reaper interval and the idle-sweep settings are read in `src/config.ts`), and decide which backends exist (`enabledSandboxBackends`). **Key idea.** The default backend is always constructed; any other is constructed when its credential is present. **Surprising.** "Credential" is loose. `porter` is enabled by `PORTER_DEPLOY_API_TOKEN`, the same token that app publishing uses. `superserve` is enabled by its template name, not its key. `aws` is enabled by its bucket. `local` is enabled by an image name.

### `src/sandbox/tenant-sandbox-shape.ts` — per-organization shapes

**Job.** In a multi-tenant deployment, give each organization its own Sprites token or name prefix, Modal app and environment, Superserve key and template, and default backend. **Key idea.** Wrap the deployment-wide client and choose the real one per call from the bound tenant's settings. With no per-tenant setting, names get a prefix hashed from the tenant id. **Surprising.** Whether a deployment is multi-tenant is decided by a count: core reads once at startup whether `tenants` has exactly one row. If it does, that organization gets the deployment's plain settings and may use any backend.

### `src/processes` — background job registry and reaper

**Job.** `src/processes/process-registry.ts` stores jobs. `src/processes/process-reaper.ts` kills expired ones. `src/processes/reconcile.ts` marks jobs that exited unobserved. `src/processes/job-computers.ts` retires job computers and stops a bot's jobs on computers the bot has lost. **Key idea.** The row in `process_sessions` is the truth about a job's lifetime; the files in the guest are the truth about its output. **Surprising.** The code that starts, polls and stops jobs is not here but in `src/connectors/background-exec-broker.ts`. When the same actor starts the same command again in the same scope on the same sandbox, with no credentials and nothing in the command redacted, the call reattaches to the running job instead of starting a second one.

### `src/environments/environment-store.ts` — environments

**Job.** Store environments and which scopes are attached to them. **Key idea.** An environment's id is the scope id of the scope that created it. Attaching a scope makes its turns write in that scope. **Surprising.** This is how two conversations share one computer; the sandbox code itself knows nothing about it. The routes are `GET` and `POST /v1/environments` and `POST /v1/environments/attach`.

### The tool layer — `src/agent/agent-tools/computer.ts`, `src/tools/primitives.ts`, `src/core/orchestrator/sandboxes.ts`

**Job.** The first file defines the model-facing `execute`, `sandbox` and `background` tools. The second implements them against the router with policy and credentials. The third owns the per-turn pool and the end-of-turn release. `src/agent/agent-tools/workspace.ts` defines `read` and `write`, which take the same `sandbox_id`. **Key idea.** Of the three tools, `execute` is the only one that launches a command; `background` only controls jobs that exist; `sandbox` only manages machines. **Surprising.** The tool descriptions are built from configuration (timeouts, job limits, whether the turn is a bot's), so the text the model sees differs between deployments. `status` adds its own shell probe on top of the provider's report. An ephemeral session gets only scratch: its `execute` has no `sandbox_id` or `background`.

### `src/api/routes/admin/sandbox.ts` — admin route

**Job.** Let an organization admin list, create, set the default of and retire sandboxes for any scope. **Surprising.** Sandboxes created here are marked `personUsed`, so a bot's turn cannot use them.

### Egress proxy

The proxy itself belongs to [security](./security.md). What matters here is what a backend does with it. The proxy only makes policy unavoidable where the provider's network rules also block direct traffic (the "Locked egress" column). Elsewhere a command can ignore the proxy variables. A DigitalOcean session already has a provider proxy in its environment, so core runs a small forwarder inside each session (`src/sandbox/managed-agents-egress-forward.mjs`) that chains through it, and points commands at the forwarder.

### Images — `fly/`, `local/`, `deploy/e2b`, `deploy/do-managed-agents`, `superserve/`, `porter/`

**Job.** Build what a sandbox boots from. `fly/Dockerfile` is the shared base image (coding-agent CLIs, `gh`, AWS CLI v2, a Python venv at `/opt/agent-venv`, `x-api`). `local/Dockerfile` adds the in-guest command daemon for the `local` backend. `deploy/e2b/e2b.Dockerfile`, `deploy/do-managed-agents/Dockerfile`, `superserve/templates/qm-agent.ts` and `porter/Dockerfile` build provider-specific images. **Key idea.** The profile tells the model which tools exist, so an image and its backend's tool list must agree. **Surprising.** `fly/` is named for a backend that no longer exists. Its image is what `local` boots (through `local/Dockerfile`) and what the CLI hands `render` as `RENDER_SANDBOX_IMAGE`. Sprites boot the provider's stock image; smolmachines boots the image named by `SMOLMACHINES_IMAGE` (default `codex`). With no `MODAL_IMAGE`, Modal assembles an image at first use from a pinned Node base (`src/sandbox/modal-image.ts`). The deployment layer's tools are not in these images; on seven backends core copies them in at provision ([deployments](./deployments.md)). The E2B template build can bake them into a child template when given `DEPLOYMENT_LAYER`; the checksum probe then finds them and installs nothing.

## Where the complexity lives

**Backends multiply lifecycle operations.** Eleven backends times provision, three teardown options, restore, status, restart, retire and idle sweep. The table above is the matrix, and almost every cell is its own code path. The master's Wall of shame records this under _Provider drift_, and the backend count under _Config-matrix expansion_.

**Three mechanisms bring a home back.** Provider pause and resume, a provider-native checkpoint, and the portable home snapshot. Several backends carry two (E2B native snapshot or an older portable path, chosen by the `nativePause` flag on the body record, not by a setting; DigitalOcean checkpoint or bucket, chosen by `DO_AGENTS_SNAPSHOT_S3_BUCKET`; Sprites checkpoint plus export on destroy when `SPRITES_SNAPSHOT_S3_BUCKET` is set).

**A shared base with three users.** `createExecSandboxBase` exists, but eight backends repeat its provision queue and scratch reference counting; the same counting block appears in several backend files (_Duplication_).

**Capability checks where nothing varies.** All eleven profiles set `processSessions: true` and all eleven backends implement `exportFiles`, yet `supportsProcessSessions`, `supportsAgentComputerExport` and the router's conditional spreads still guard them.

**Contract members with no production caller.** `stageIn` and `stageOut` are implemented by ten backends and forwarded by the router, and nothing calls them. `persistHomeSnapshot` is implemented by six backends and called only from tests. `writablePersistence` is set by every backend and read by none. No backend reports the `ip_port` value of `EgressEnforcement`. `DEV_IDLE_MACHINE_MS` is parsed and passed to the idle sweep, and no backend reads it.

**The park decision is made twice.** `releasePool` asks for `keepWarm` when other live runs hold the sandbox; the router's `teardown` reads the holders again for backends that park.

**Two timeouts for one command.** The tool passes its own limit (`EXEC_TIMEOUT_*`) to `run`; calls made without one fall back to `SANDBOX_TIMEOUT_SEC`; the provider's machine lifetime sits above both.

**One feature in four places.** A background job touches `src/agent/agent-tools/computer.ts` (tool), `src/tools/primitives.ts` (policy and credentials), `src/connectors/background-exec-broker.ts` (start, poll, stop) and `src/processes` (registry, reaper). **[interpretation]** The broker's location is historical rather than meaningful.

**Transitional code still present.** The legacy import and its inputs (`sandbox_routing` table, `SANDBOX_SCOPE_BACKENDS`, the `legacy` flag and `unverified` state), recorded under _Historylessness_; two data migrations inside `src/sandbox/sandbox-resources.ts`; `checkRetiredEgressProxyKeys`, which refuses to start when a per-provider proxy variable from an older release would leave that provider uncovered; and the `fly/` directory name.

**Status advice baked into a tool result.** The `status` action tells the agent to restart a `wedged` computer and then to replace it. The Wall of shame records this under _Band-aid fixes_.

## Contracts

**The `Sandbox` interface** in `src/sandbox/sandbox.ts` is the contract for a new backend, together with the behaviour listed under "The backends". A new name must also be added to `SandboxBackendName`, to the builder table in `src/wiring.ts`, and to `enabledSandboxBackends` and the name check beside it in `src/sandbox/sandbox-settings.ts`.

**What a sandbox image must contain.** Core drives the guest with shell scripts, so an image needs POSIX `sh`, `setsid`, `base64`, `mkfifo`, `tar`, `find`, `dd`, `mktemp` and `sha256sum`, and on every backend except `local` and `aws` the `timeout` command that wraps each command. The load probe also uses `awk`, `cut` and `df`, and yields no sample without them. The home directory must match the backend (table above). Every image should carry the same base toolset (the master's Provider drift lens), and the tool list in the backend's profile must be true of the image.

**Tools.** `execute(command, purpose, sandbox_id?, scope?, background?, timeout_seconds?, credentials?)`. `sandbox` actions: `list`, `create` (`backend`, `name?`, `memory_gib?`), `set_default` (`sandbox_id` or null), `status`, `restart`, `retire`. `background` actions: `poll`, `send_input`, `stop`, `list`, `watch`, `unwatch`. A field the action does not take is rejected.

**Admin API.** `GET /v1/admin/sandboxes/:scopeId` lists. `POST` to the same path takes `{ "action": "create", "backend", "name?" }`, `{ "action": "default", "sandboxId": <id or null> }` or `{ "action": "retire", "sandboxId" }`.

**Tenant settings keys.** `sandboxBackend`, `sandboxScopeBackends`, `spritesToken`, `spritesNamePrefix`, `modalAppName`, `modalEnvironment`, `modalNamePrefix`, `superserveApiKey`, `superserveTemplate`, `superserveNamePrefix`. The two backend keys accept only `sprites`, `modal` or `superserve`. `modalNamePrefix` is used only when `modalAppName` or `modalEnvironment` is also set; otherwise the hashed prefix applies.

**Deployment config.** The CLI key `sandbox.backend` accepts a subset of backends per target (`SANDBOX_BACKEND_POLICY`). `env.core.SANDBOX_BACKEND` overrides it and reaches core unchanged, which is how the other backends are selected; on the Render target the CLI rejects any value but `render` ("Render requires env.core.SANDBOX_BACKEND=render"). The rest of that file belongs to [deployments](./deployments.md).

**Egress proxy, as a sandbox sees it.** A backend sets `HTTPS_PROXY=<scheme>://x:<token>@<host>` on each command; the token is a capability token with audience `egress-proxy`. The proxy's own wire format is in [security](./security.md#contracts).

**Home snapshot objects.** `<prefix>/<tenant id>/<URL-encoded backing scope>.tar` in the configured bucket, with prefix `sprites-home`, `smolmachines-home`, `e2b-home`, `modal-home` or `managed-agents-home`. The `aws` backend uses `AWS_SANDBOX_S3_PREFIX` (default `sandbox-home`) and its own leaf name.

**Provider-side markers.** Modal machines carry the tags `qm-org`, `qm-prefix` and `qm-kind`, which the idle sweep uses to find machines no record claims. `RENDER_SANDBOX_IMAGE` must have the form `<repository>:<tag>@sha256:<digest>`.

**Load marker.** The probe appends one stdout line, `__QM_LOAD__ <io> <load1> <mem used MiB> <mem total MiB> <disk used KiB> <disk total KiB>`, with `-` for a missing value. The router removes it before the model sees the output.
