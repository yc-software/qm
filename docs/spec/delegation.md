# Delegation: subagents, peer sessions and swarms

_Verified against `main` at bd371980c (2026-11-24): statements were read in the code at c6056de14 and re-read where later commits changed it, unless marked **[interpretation]**._

## In one paragraph

Delegation is how one agent turn gets other turns to do work for it. It has three forms. A turn can open a **subagent**: a new session with its own transcript, kept out of the sidebar, that works on a written task and reports to the session that opened it, its **parent**. A turn can message another ordinary conversation in the same scope, a **peer**. Or a turn can start a **swarm**: a pool of worker sessions, each on its own blank computer, that talk through one shared message list. All three are built from the same two things: queued runs (see [turns](./turns.md)) and durable mail in Postgres. Mail, wakes, returns and swarm rows live in Postgres; what process memory holds is per-turn or sweeper bookkeeping (for example `quarantinedMessages` in `createRecorder` and the swarm sweeper's `reconciling` maps) and one cache (`memberIndex` in `src/swarms/swarm-store.ts`). Mail reaches a busy recipient when its next tool call returns. An idle recipient is **woken** when the mail carries a wake: a new run is queued in its conversation. A finished child's result is mail too, and the child's run is not marked returned until the parent has read that mail, a wake run for it has finished, or the mail was delivered owing no wake. Stopping has a scope: the Stop button stops one conversation and leaves its subagents working; a typed `stop`, or stopping the agent session in a Slack thread, stops the whole tree.

## One delegation, traced end to end

The example: Ada at Acme asks the agent in the web app to "reconcile the March and April billing exports against the ledger". The agent opens two subagents, "March" and "April". March finishes first. Ada presses Stop on her conversation while April is still working.

1. **The tool call.** The model calls the `subagents` tool with `action: "open"` and a `task`. `sessionTools` in `src/agent/agent-tools/sessions.ts` defines the tool. It holds no logic: it calls `open` on the turn's `SessionSyscalls`, an object that `createSessionSyscalls(...).forTurn(binding)` in `src/sessions/session-syscalls.ts` builds once per turn from that turn's own request.
   - _Who gets the tool:_ every turn except one whose conversation has an external audience (`handleTurn` in `src/core/orchestrator.ts` passes no syscalls there), a turn in an ephemeral session and a turn editing an app (`EPHEMERAL_OMITTED_TOOLS` and `APP_EDIT_TOOL_NAMES` in `src/agent/agent-tools.ts` filter the tool out). A swarm worker's turn has the tool, and `open` and `send_message` are refused there.
2. **Admission.** `open` first refuses a side chat that has not been opened as a session. It then takes the Postgres advisory lock `session-tree-admission` and re-checks the caller: its own run has not been stopped (`runStopped`), its session still exists in the same scope, and its actor may still act in that scope. It refuses a swarm worker, a turn started by a private session message, and an empty task.
3. **The child session.** The child's thread ref is `agent:main:subagent:` plus a hash of the parent session, the parent run and the request id. The request id defaults to the tool call id, so a retried tool call finds the same child instead of making a second one. The same id with any different `open` argument (task, name, model, isolation and the rest are fingerprinted together) is refused: `the requestId was already used for different work`. `open` creates the session in the parent's scope, sets `parent_session_id`, adds the actor and the request's `sessionParticipantIds` (the conversation's audience when that is unset) as participants, and saves `spawn_meta`: the context every later run of this child starts from (actor, conversation, audience, surface, delivery target, read-only flags, model). `sessionContextOf` builds it from the parent's request. `openRuntime` in `src/sessions/subagent-runtime.ts` picks the model. `childIsolation` in `src/sessions/child-isolation.ts` picks where commands run.
4. **The first run.** `open` queues a run in the child's thread with dedup key `subagent-open:<threadRef>`. Its text is the task inside a `<subagent-task>` envelope. Its request carries `sessionSenderId` (the parent session) and `delegatingRunId` (the parent's run). The tool returns at once with the child's session id. `runPriority` in `src/runs/run-store.ts` gives a delegated run priority 1, behind people's turns (0) and ahead of background work (2), unless its delegating run has priority 2 or cannot be found: then it gets 2.
5. **The child's turn.** It runs as any turn does ([turns](./turns.md)), with three differences. `isSessionTurn` in `src/core/turn-origin.ts` is true, so the orchestrator does not trust the origin copied into the request; it uses what `delegatedAuthorization` returns. That function walks the `delegatingRunId` chain back to a turn that is not itself a session turn, has an all-internal audience, and was started by a person, by an automation fire that is not a bot's, a swarm's or a system actor's (`isPersonFire`), or by a live ambient message outside a DM, and it checks every link. When a turn's computer is opened, `openScoped` in `src/core/orchestrator/sandboxes.ts` calls `ensureChildSandbox` (only when the isolation record names a `sandboxId`) and `prepareChildWorkdir` to prepare the child's placement. The prompt gains the text from `isolationBrief`.
6. **The parent carries on.** In the web app it may keep working and call `wait`, which polls its mailbox for at most 60 seconds, or simply end its turn.
   - _Slack and other surface-tool turns:_ `requiresDelegation` makes the turn a **coordinator**, unless it is a swarm worker's, is in a subagent thread, has an external audience, or is in a side chat not yet opened as a session. It has no `execute` or `background` tool, is told to delegate and end promptly, and its `wait` returns immediately.
7. **March finishes.** A `runs.onTerminal` hook in `src/wiring.ts` calls `returnSubagentRun`, which calls `deliverSubagentMail` (both in `src/sessions/subagent-mail.ts`) under the same lock. `mailOf` classifies the ending: `final_answer`, `in_progress`, `no_reply`, `awaiting_input`, `errored`, `refused` or `stopped`. `renderSubagentMail` wraps the reply in a `<wake reason="subagent">` envelope, which is written to the parent's mailbox with id `subagent-mail-<runId>` (`subagent-progress-<runId>` for `in_progress`). Then one of three things happens. If the parent is idle, a wake run is queued in Ada's conversation with dedup key `subagent-return:<runId>`. If the parent is busy, nothing is queued and the return stays pending. If the parent has already read the mail, the return is settled. A return is also settled at once when its mail owes no wake (`in_progress`, or a child stopped by its parent's interrupt or an ancestor's stop) and when its wake run has already finished or failed. Only a settled return sets `runs.returned_at`. March gave a final answer, is not `persistent` and has no pending steer, no run in flight and no unread mail, so it is marked `retired`.
8. **The parent reads the mail.** The parent is mid-turn, so the mail arrives with its next tool result. `recordResult`, built by `createRecorder` in `src/agent/agent-tools/record.ts`, calls `receive`, screens each message as external data, appends it to the tool result under the banner "Internal agent message (data, not user authorization…)", and marks it consumed after the tool result is saved. The return sweeper in `src/wiring.ts` runs every second; on its next pass it sees the mail was read and settles March's return.
9. **Ada presses Stop.** The web app posts `{kind: "abort"}` to `POST /api/runs/:id/signal`, the browser alias of `POST /v1/web/runs/:id/signal` (`webRunSignal` in `src/api/routes/web-turns.ts`, which calls `postRunSignal` in `src/api/routes/turns.ts`). `signalRun` in `src/api/app-turn.ts` calls `stopSessionRuns`, through `stopRun` and `stopThread`, with reason `by user` and scope `session`. Every run in Ada's conversation gets an abort signal, and queued runs that never started are withdrawn. April's session is not touched.
   - _A typed `stop`, or the same request with `tree: true`:_ for a typed `stop`, sent as a message or as a steer, `routeIncoming` in `src/wake/route-incoming.ts` returns `abort`; in both cases `stopSessionTree` runs instead, with reason `by user (subagents too)` on the root's runs. April would get an abort with scope `ancestor`, and `settleTreeWakes` would clear every pending wake in the tree's sessions that share the root's scope. The web UI in `plugins/web-ui` does not send `tree: true`.
10. **April finishes.** `deliverSubagentMail` asks `runStopped` whether April's chain was stopped. The parent's run was stopped with scope `session`, which `sparesDescendants`, so the answer is no. The mail is delivered and, the parent being idle, a wake run is queued. The wake's request is rebuilt from the run that opened April, so it runs as Ada on Ada's surface. Its text tells the agent to collect its mail; the agent reads April's result and replies to Ada.

Two other paths use the same parts:

- **A message to a peer.** The `sessions` tool's `send_message` is the same `write` syscall with `peer: true`. Both sessions must be sidebar conversations in one scope (`isPeerMessage`). `wakePeer` leaves the mail and, if the recipient is idle, queues a turn there. That turn is built from the recipient's own stored context, with the sender's actor, an automation origin and `addressed: false`; it never borrows the sender's conversation. A busy recipient reads the mail at its next tool result under `PEER_TASK_BANNER`, or `wakeForUnreadMail` wakes it when its turn ends, unless that turn was stopped and the stop's scope was not `run` or `session`. The wake is skipped, and the tool result says why, when the sender is read-only, is on a private turn, is notebook-only and the target is not, or would be the ninth wake in a chain (`SESSION_MESSAGE_DEPTH_CAP` is 8).
- **A swarm worker.** A worker is not a subagent. `POST /v1/swarm` with `action: "spawn"` (`swarmRoutes` in `src/api/routes/swarms.ts`, then `spawn` on the service from `createSwarmService`) only reserves members inside the swarm's row and answers 202. A sweeper then creates each worker's computer and session (thread ref `swarm:<rootSessionId>:<memberId>`, the root id URI-encoded) and queues one run per pending notification with dedup key `swarm:<messageId>:<memberId>`. Before the worker's turn runs, `binding` checks its request against the stored message. Each write the worker makes to the swarm is fenced by its run lease (`assertSwarmRun`).

## The parts

### `src/agent/agent-tools/sessions.ts` — the two tools

**Job.** Define `subagents` (`open`, `read`, `send_message`, `wait`) and `sessions` (`list`, `search`, `read`, `send_message`, `new`, `fork`), and turn each syscall result into a sentence for the model (`deliveryOutcome`).

**Key idea.** The tools are thin. The tool description is the model's manual for the tool (the coordinator prompt in `handleTurn` and the wake texts in `src/sessions/subagent-mail.ts` add instructions of their own), and each result states what happened: woken, queued behind a busy turn, delivered into a running turn, or left in the mailbox and why.

**Surprising.** (1) `noComputer` is stored as `readOnly`; a read-only child gets no isolation record and cannot lift the restriction for its own children. (2) `sessions` refuses subagent targets and `subagents` is the only way to reach them, but both call the same `write` and `read` syscalls. (3) `new` and `fork` are refused on a swarm worker's turn, on read-only turns and on a Slack bot's work; they create web sessions through `startSession` in `src/api/start-session.ts`. (4) `read` with no target lists only children that are not retired.

### `src/sessions/session-syscalls.ts` — open, message, read, stop

**Job.** Everything a turn may do to another session (`open`, `write`, `read`, `receive`, `acknowledge`, `list`, `search`, `start`), plus the tree helpers other modules import: `treeSessions`, `stopSessionRuns`, `stopSessionTree`, `runStopped`, `delegatedAuthorization`, `requiresDelegation`.

**Key idea.** Authority is recomputed, never carried. Every call except `acknowledge` re-reads the caller's session, scope and membership (`currentCaller`); a `receive` that finds no mail and does not wait returns before it. A child's request copies the parent's origin kind, so a child of a person's turn is stored with origin `human`; what marks it as delegated is the `sessionSenderId` and `delegatingRunId` pair. `delegatedAuthorization` then proves the chain: same actor, of type internal, same scope, no wider audience, no read-only, private-message, swarm or plain-automation link, at most 32 hops. A chain that cannot be proven leaves the turn with no person's authority (`personAuthorityTurn` is false).

**Surprising.**

1. `write` has four outcomes: `steered` (put into a running child's turn as a steer signal), `queued_turn`, `interrupted`, and `queued_message` (mailbox only). A wake that is not allowed falls back to the mailbox instead of failing. The message id is a hash of the session, the run and the tool call id, so a retried call does not send twice.
2. A subagent that is not read-only, not on a private turn, and not notebook-only unless its parent is too, can wake its own parent, at any depth. It cannot wake any other top-level conversation: that mail waits unread until something else wakes the recipient.
3. `interrupt: true` works on any subagent session the caller can resolve: a child, a sibling, or a parent that is itself a subagent. It never works on a top-level conversation, and a read-only caller cannot interrupt a writable target, nor a notebook-only caller a target that is not notebook-only. It stops the target's running run with scope `run` and withdraws its queued, unstarted session messages; one sent by another session is first copied into the target's mailbox. The interrupt's text becomes the target's next turn.
4. A stop is judged by its scope, not its reason text (`sparesDescendants`). The table below is the whole rule.
5. `spawn_meta` has two roles. For a subagent it is the fixed starting context. For a top-level conversation the orchestrator overwrites it with the context of each ordinary turn (`ownsSessionContext`), because a wake arrives with no person's request to take context from.
6. Work a Slack bot starts stays bot work: `botActor` is copied into `spawn_meta` and into every wake. A bot's turn cannot interrupt a person's task, and a message is not steered across the bot and person line; it queues as its own turn. See [surfaces](./surfaces.md).
7. `read` returns a target's items only when every member of the current conversation's audience is a participant of the target, and then only the items the actor may see.

Pending wakes there are cleared. |

### `src/sessions/subagent-mail.ts` and `src/runs/run-returns.ts` — results and wakes

**Job.** Turn a finished child run into mail for its parent, decide whether that mail wakes the parent, and keep trying until it has landed.

**Key idea.** The in-process `onTerminal` hook is only the fast path. The durable record is `runs.returned_at`: `PENDING_RETURNS` selects finished subagent runs without it, plus those whose return wake is still queued and unstarted, and a sweeper retries them every second under the advisory lock `session-return-sweep`. A failed attempt is deferred 60 seconds (`deferReturn`). The master's Non-durability lens records the same hook failing as the only path for reply delivery.

**Surprising.**

1. A wake turn's request comes from the run that delegated the work (actor, authority, delivery target) only while the parent is the conversation that run was in; otherwise it comes from the parent's stored context with the sender's actor, an automation origin and `addressed: false`. Either way the audience and `publishMembers` are taken from the parent's current stored context when it has one.
2. A child that ends its turn while its own subagents or watched background jobs are still working reports `in_progress`, which never wakes the parent; the final result follows later (`pendingWork`).
3. A stopped child wakes its parent only when the child's own run was stopped with scope `session` or with no scope, which is read as `tree`. A parent's own interrupt and an ancestor's stop deliver mail without a wake.
4. Files a child attached are delivered separately through the delivery queue with key `subagent-files:<runId>`, unless the run was stopped.
5. A reply longer than 16,000 characters is cut in the mail; the full text stays in the child's transcript.
6. Message wakes do not use `returned_at`. They use the `wake` flag on the mailbox row, recovered by `sweepUnreadMailWakes` and by `wakeForUnreadMail` when a run in the recipient's thread ends, unless that run was stopped and the stop's scope was not `run` or `session`.

### `src/sessions/session-mailbox.ts` and `src/agent/agent-tools/record.ts` — mail delivery

**Job.** Store mail (`createSessionMailbox`) and hand it to a running turn.

**Key idea.** Mail is read at tool boundaries. `recordResult` takes up to four pending messages, screens each one on its own (`session_message_<id>`, source `session-delegation`), appends them to the result text, and acknowledges them only after the result is saved. A crash before that save redelivers. Not every tool result passes through it: an `execute` call that throws and a call aborted mid-flight are saved with `logResult` directly (`src/agent/agent-tools/computer.ts`, `src/agent/agent-tools/wrappers.ts`) and carry no mail.

**Surprising.** On a web turn that speaks through the surface tool (`web_dm_spine`), mail is not read into a tool result that ends the turn, so it waits for the turn it wakes. A message the screen quarantines pauses the turn on an approval, unless the turn cannot raise approvals (`approvalUnavailable`): then the result carries a notice and the turn goes on. Denying the approval consumes the message ([security](./security.md)).

### `src/sessions/child-isolation.ts` and `src/sessions/subagent-runtime.ts` — placement and model

**Job.** Decide the child's computer and directory (`childIsolation`), create them on first use (`ensureChildSandbox`, `prepareChildWorkdir`), and choose its model (`openRuntime`).

**Key idea.** The default is to share. A child uses its parent's computer and directory unless `open` asks for `worktree` or `sandbox`. Which computer that is when nothing is recorded belongs to [sandboxes](./sandboxes.md).

**Surprising.** (1) The default flips to `worktree` when the parent itself runs in a subagent directory, so grandchildren do not share a worktree. (2) A `worktree` child gets `subagents/<slug>-<hash>` and branch `subagent/<slug>-<hash>`; if the base is not a git repository it is a plain empty directory. (3) A `sandbox` child's computer id is its session id and is created the first time one of the child's turns opens its computer (`openScoped`). (4) With no `model` given, the child inherits the parent's model only when the parent is off the scope default and that model passes validation for the child; otherwise it resolves as purpose `subagent` ([models](./models.md)).

### `src/sessions/subagent-status.ts` and `src/sessions/session-work.ts` — what is still working

**Job.** Answer "what is this child doing?" for the tools (`subagentActivity`, `renderSubagentActivity`, `liveSubagentsNote`) and "is this conversation busy?" for Slack's session status (`createSessionWork`, built once in `src/wiring.ts`).

**Key idea.** Liveness is the latest tool step, not the end of the turn. A listing shows status (`running`, `pending`, `idle`, `waiting on subagents`), the age and name of the last tool step, the last turn's outcome, and unread mail.

**Surprising.** For `createSessionWork`, a session with no run of its own still counts as busy while a descendant runs, a child's return is pending, a background job or watch it owns is live, or a delivery to its thread is pending. The tool listing's `waiting on subagents` is a different test (`pendingWork`): an unstopped descendant run, a child's mail that still owes a wake, or an armed watch on the session's own thread; background jobs are not counted.

### `src/wake` — a message meets live work

The part belongs to [turns](./turns.md). Two facts matter here. Nothing in `src/wake` queues delegation wakes; those live in `src/sessions/subagent-mail.ts`. When a conversation is idle but its subagents are running, a halt still stops the tree, and any other message starts a normal turn (`only-subagents-live`).

### `src/swarms` and `src/api/routes/swarms.ts` — swarms

**Job.** Create and run pools of worker sessions: membership, messages, budgets, pause and stop, worker computers and the shared board.

**Key idea.** Reserve first, provision later. `spawn` and `send` only edit the swarm's row, inside a transaction that also locks the caller's `runs` row and checks its lease, then answer 202. A sweeper (every 2 seconds, 16 swarms a pass, 4 at a time, 30 seconds each) does the slow work in two phases: `resources` creates computers and worker sessions and cleans up failures; `delivery` queues one run per pending notification. Provisioning is given up after three attempts, or sooner on a provisioning timeout, a passed deadline or an expired swarm, and a failed reservation still counts toward the `agents` budget.

**Surprising.**

1. A worker has no parent link, no session mailbox and no return, and its reply is not delivered to any surface. The session tools refuse on a swarm turn and refuse swarm targets. A person's ordinary turn in the root session is an ordinary turn.
2. A worker turn's request must equal what `dispatchRequest` would build for that message, or it fails with `forged swarm provenance`.
3. The roster is frozen at creation. If the participants of the root session change, swarm calls fail with `swarm roster changed`; if those of the caller's own session change, with `swarm session roster changed`.
4. A worker starts on a blank computer. It gets none of the root's files and does not copy the root's model; an unset model resolves as purpose `subagent`.
5. A worker's turn ends when it replies. A message with a `goal` keeps it working under the goal loop; while a goal is open, swarm messages reach the worker mid-turn (`createSwarmGoalInbox`). Mail sent with `wake: false` is handed over at the start of the worker's next turn (`openSwarmMailbox`).
6. `stopped` is final and reaches descendants. `paused` returns queued, unstarted runs to `pending`; a turn that starts for a paused worker is held and retried.
7. Only a Slack bot's own turns may add workers to a swarm a bot started, and such a swarm never takes a forum. The bot loses the swarm once anyone else posts a message in it or a person's turn uses one of its computers.

### `src/core/side-chat-context.ts` and `src/sessions/side-chat.ts` — side chats

**Job.** Give a side chat its rules (`SIDE_CHAT_GUIDANCE`) and give the origin conversation a view of its side chats (`sideChatContext`).

**Key idea.** A side chat is a fork with an anchor (`isSideChatAnchor`: an entry seq, a quote, an occurrence). The origin's prompt receives side-chat exchanges as untrusted reference data under a token budget that drops the oldest exchanges first, and only when every member of the current audience is a participant of both sessions.

**Surprising.** A side chat cannot open subagents until `POST /v1/sessions/:id/expand` turns it into a full session. It can still read and message existing sessions.

## Where the complexity lives

**Things that multiply each other.**

- _Stops._ Five ways to stop (the table above; `deleteEphemeralSession` in `src/api/app-sessions.ts` and `cutOffBot` in `src/swarms/swarm-service.ts` send aborts as well) × four scopes × three run states (running, queued and unstarted, queued by another session) × a bot-only variant (`botRunsOnly`). Only the tree stop walks the tree and signals descendants. A goal cancel signals one session; its descendants are fenced by `runStopped` but their current turns run on.
- _Wake eligibility._ `write` chooses between steer, new run, wake and mailbox from the target kind (child, sibling, own parent, peer, other top-level) × the sender's flags (read-only, notebook-only, private turn, bot) × `wake` and `interrupt` × chain depth. It returns six fixed "left in the mailbox" reasons, or the error text when queueing the wake throws.

**Parallel mechanisms doing one job.**

| Job                           | Mechanism A                                                 | Mechanism B                                                                                              |
| ----------------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Remember that a wake is owed  | Results: `runs.returned_at` and the `PENDING_RETURNS` sweep | Messages: the `wake` flag on the mailbox row, `sweepUnreadMailWakes`, `wakeForUnreadMail`                |
| Messages between agents       | `session_mailbox` (subagents, peers)                        | `SwarmMessage` inside the `swarms` row, with its own states, `wake: false`, dedup and mid-turn hand-over |
| Put text into a busy session  | A steer signal (`steerRunningTurn`)                         | Mail read at the next tool result; or a queued run                                                       |
| "Is this tree still working?" | `pendingWork`, `subagentActivity`, `openChildren`           | `createSessionWork`, `sessionTreeWorking`, `workingSessionThreadRefs`, `sessionTreeRuns`                 |
| Context for a wake turn       | The delegating run's stored request                         | The recipient's `spawn_meta` (`storedContext`)                                                           |
| A pool of parallel workers    | Subagents: a tree, the parent's computer by default, mail   | Swarms: a flat member list with depth, own computers, a board                                            |

**One lock for every tree.** `session-tree-admission` is a literal key with no tenant or tree in it. Every `open`, `write`, Stop-button or tree stop (`stopThread`), detach, return and unread-mail wake in the database serializes on it; a goal cancel does not take it.

**One row per swarm.** Every spawn, send, control and notification change rewrites the whole JSON document, including every message sent so far.

**Fixed numbers.** Eight peer wakes in a row, 32 authority hops, four messages per mailbox read, 16,000 characters per message, 60 seconds per `wait`, and the swarm defaults below. The master's Arbitrary limits lens covers swarm settings and subagent run caps.

**Recorded by the master.** The rule in `routeIncoming` that a person's message does not steer into a live automation turn unless they asked to steer is the case under the Category gate without census lens.

**Abstractions without a second user.** `SessionSyscallDeps.enabled`, a per-person gate, is never passed in `src/wiring.ts`. `createSwarmStore` has a write path for a missing Postgres pool; `src/wiring.ts` always passes one.

**Transitional code.**

- `privateSessionMessage` marks a read-only turn that one branch of `write` can queue. That branch needs a target that has a parent but is not a subagent thread, and `open`, the only writer of a parent link, creates only subagent threads, so the branch is unreachable for sessions created at this commit. The field is still read in a dozen files.
- The code that builds a wake turn handles a parent that is not the conversation the child's delegating run was in (`originalParent` in `parentTurn`). That branch runs with no re-parenting: for every peer wake, and for a child whose run was started by a sibling's message. `setParentSession` has two callers: `open` sets the opener, detach sets null.
- Two startup migrations backfill `sandbox_resources` rows (and, in the second, `swarms` rows) written by older releases: `durable-map/swarms/0040-stamp-computers` and `durable-map/swarms/0041-mark-forums-person-used`.

## Contracts

**Environment.** `SWARMS_ENABLED` (boolean, default `true`). `SWARM_DEFAULTS`: a JSON object of the settings below.

**Swarm settings.** Stored once on the swarm. Each is a positive integer. The root may change any except `turnMs` on a later spawn.

| Setting                                      | Default    | Meaning                                                                                                        |
| -------------------------------------------- | ---------- | -------------------------------------------------------------------------------------------------------------- |
| `agents`                                     | 32         | Members, counting the root and failed reservations. At least 2.                                                |
| `depth`                                      | 4          | Levels of workers below the root.                                                                              |
| `contextBytes`, `textBytes`                  | 8,192 each | Size of one member context and of one message text.                                                            |
| `waitMs`                                     | 10,000     | Longest wait on one read.                                                                                      |
| `spawnRequests`, `messages`, `notifications` | unset      | Lifetime budgets, reserved in the same write as the thing they count.                                          |
| `lifetimeMs`                                 | unset      | Work window from creation. After it, history stays readable and new work is refused until the root extends it. |
| `turnMs`                                     | unset      | Wall clock for one worker turn. Does not apply to a goal turn. Ceiling 2,147,483,647.                          |

**Agent swarm API.** Sent from a turn's computer with header `x-agent-capability: $AGENT_API_TOKEN`. The token must be bound to the calling session and to a run that is running under an unexpired lease. Request bodies cannot set identity. An unknown body field is a 400. Errors are `400 {error}`; a missing session binding is 403 (`session-bound authentication required`, or `session access denied`); with swarms off every route answers 503.

| Request                  | Body or query                                                                                                                             | Answer                                                                                                                                                                                                                                                                                                  |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/swarm`          | —                                                                                                                                         | `200 {id, self, peers, board?, backend, settings, expiresAt?}`                                                                                                                                                                                                                                          |
| `GET /v1/swarm?read=1`   | `after` (last seq seen), `waitMs` (at most the `waitMs` setting), `replyTo?`                                                              | `200 {messages}`: at most 32, any audience. Replies read with `replyTo` count as handed to the caller. A timeout returns an empty list.                                                                                                                                                                 |
| `POST /v1/swarm` spawn   | `{action:"spawn", requestId, text, count?, context?, contexts?, model?, effort?, fastMode?, goal?, settings?, backend?, forumSandboxId?}` | `202 {members}`. `count` is at least 1 and below `agents`. `contexts` sets the count. `backend` only on the first spawn. `settings` only from the root. `model`, `effort` and `fastMode` are stored on the new members and inherited by workers they spawn; an unknown or unavailable model is refused. |
| `POST /v1/swarm` send    | `{action:"send", requestId, text, audience, replyTo?, wake?, goal?}`                                                                      | `202 {message}` with `id` and per-swarm `seq`. `audience` is a list of member ids or `"all"`.                                                                                                                                                                                                           |
| `POST /v1/swarm` context | `{action:"context", context}`                                                                                                             | `200`: the caller's member record. Any JSON; replaces the caller's own context only.                                                                                                                                                                                                                    |
| `POST /v1/swarm` control | `{action:"control", memberId, state}`                                                                                                     | `200 {member}`. `state` is `active`, `paused` or `stopped`. An agent may control itself and its descendants. The root cannot be controlled.                                                                                                                                                             |

`requestId` is required on spawn and send, at most 128 bytes. The same id with the same payload returns the first result; with a different payload it is refused. A sender is not notified of its own message unless it sends itself a goal by id. `wake: false` stores the message as `mailbox` for each recipient and uses no notification budget. A `goal` is `{objective, floor?, token_cap?}`, goes to workers only, cannot be combined with `wake: false`, and replaces the recipient's current goal.

**Person swarm API.** `GET` and `POST /v1/sessions/:id/swarm` (browser alias `/api/sessions/:id/swarm`), as a signed-in person who can view the session. `GET` inspects. `POST` accepts `control` only; a person may control any worker.

**Stop, detach, list.** `POST /v1/runs/:id/signal` with `{kind:"abort"}` stops that conversation; with `tree: true` it stops the tree. `POST /v1/sessions/:id/detach` with `{principalId}` clears a child's parent and answers `{detached: true}`; it answers 404 when the session has no parent, or the principal cannot see it or cannot write in its scope. `GET /v1/sessions/:id/children?principalId=` lists the session's descendants that the principal is a participant of, at most 500 (`MAX_LISTED_CHILDREN`).
