# Storage: Postgres, tenancy and object storage

_Verified against `main` at d1de9e2d2 (2026-11-24). Statements were read in the code at that commit unless marked **[interpretation]**._

## In one paragraph

Everything QM must remember lives in one Postgres database. A core process holds only caches, and several core processes run against that database at once, so anything kept only in memory is lost on the next deploy and invisible to the process next door. Every organization is a _tenant_: one row in the `tenants` table. Almost every other table has a `tenant_id` column and a Postgres row-security policy that hides the rows of every tenant except the one _bound_ to the current transaction, so the same code serves one organization or many. A piece of work (a request, a Slack event, a queue job) first finds its tenant and binds it; from then on every query sent through the shared pool wrapper carries that tenant into Postgres. There is no schema file: each store defines its own list of migrations in code, and a ledger table records which have been applied. Locks, leader election and "something changed" signals between core processes are Postgres features too. Large bytes (file contents, long tool output, transfers to and from sandboxes) go to a byte store that is either a local directory or an S3 bucket.

## One webhook delivery and one schema change, traced end to end

**The request.** Acme is one of several organizations on a [multi-tenant deployment](../SPEC.md#deployment-shapes). Ada at Acme created a webhook, and an outside system now sends `POST /v1/webhooks/incoming/<id>`. Core connects to Postgres as a login that does not own the tables.

1. **The route says how its tenant is found.** `webhookRawRoutes` in `src/api/routes/webhooks.ts` declares `tenant: { by: "webhook", key: (params) => params.id }`. The `tenant` field of a `Route` (`src/api/routes/route.ts`) has three other values: absent (the tenant comes from the caller's credentials), `"optional"`, and `"none"` (the handler finds the tenant itself or needs none).
2. **Find.** `buildServer` (`src/api/server.ts`, called by `createServer`; inner function `inRequestTenant`) calls `inboundKey` and then `withInboundTenant` (`src/api/inbound-tenant.ts`), which calls `tenantFor("webhook", id)` from `tenantLookup` (`src/tenants/lookup.ts`). That runs `SELECT qm_tenant_for_webhook($1)`, a SQL function created by the `TENANT_LOOKUPS` migration. No tenant is bound yet, so core's own login cannot read `webhooks`. The function is `SECURITY DEFINER`: it runs as the tables' owner, and it returns a tenant only when exactly one tenant has that id.
3. **Bind.** `inTenant` (`src/tenants/claim.ts`) calls `withTenant` (`plugins/chassis/src/tenant.ts`), which checks that the id is a UUID, mints a `Tenant` token, and binds it in `AsyncLocalStorage` for everything the callback does. `inTenant` then awaits `loadTenant` (`src/tenants/cache.ts`), which runs every loader registered with `onTenantLoad` once per tenant per process. `loadTenantSettings` is the exception: it is registered with `TENANT_SETTINGS_REFRESH_MS`, so a request that finds its copy older than 30 seconds reloads it in the background. The token is put on the request context, where handlers read it with `tenantOf`.
   - _No tenant found:_ `withInboundTenant` binds `EMPTY_TENANT`, the all-zero UUID. Every query then matches nothing and the handler answers as it would for an unknown id.
4. **Store call.** The handler reaches `createWebhookReceiver` (`src/webhooks/webhook-receiver.ts`), which calls `webhooks.get(id)`. The webhook store is a durable map; `get` in `createPostgresMap` (`src/persistence/durable-map.ts`) runs `SELECT json FROM webhooks WHERE id = $1` through `PgPool.q`. The SQL names no tenant.
5. **Carry the tenant to Postgres.** `q` in `createPgPool` (`src/persistence/pg-pool.ts`) reads `boundTenant()`. Because a tenant is bound, it sends `BEGIN`, `SELECT set_config('qm.tenant_id', <id>, true)`, the query and `COMMIT` in one pipelined round trip. The setting lasts for that transaction only, so it cannot leak to the next borrower of the connection.
6. **Enforce.** `webhooks` carries the policy `tenant_isolation`: `USING (tenant_id = qm_bound_tenant()) WITH CHECK (tenant_id = qm_bound_tenant())` (`tenantRowSecurity` in `src/tenants/migrations.ts`). `qm_bound_tenant()` returns the setting, or raises `No tenant is bound to this query` when it is empty. Only Acme's row can come back. Inserts need no tenant in their SQL either, because `tenant_id` defaults to `qm_bound_tenant()`.

Where other paths diverge:

- **Signed-in web request, or a sandbox calling back.** Routes with no `tenant` field, and `"optional"` ones, go through `withRequestTenant` (`src/api/request-tenant.ts`), except on a published app's host name when `deployGateSecret` is set: there `inboundKey` returns the `app_host` key for every route. The tenant is the `tenant` claim of the capability token, else the portal identity header, else the browser session, else the boot tenant. With none of these the request gets a 401, or on an `"optional"` route runs with no tenant bound.
- **Slack.** `createTenantSlackRuntimes` (`src/surfaces/slack-tenants.ts`) asks `slackTenants()` every five seconds which tenants have a Slack installation and starts one Slack plugin per tenant (`startQm` puts the boot tenant first on that list); the plugin's first middleware wraps every event in `withTenant` (`startSlackPlugin` in `src/slack/index.ts`). Events relayed over HTTP arrive on a `tenant: "none"` route whose handler, `managedSlackEvent` (`src/api/routes/admin/slack-installation.ts`), looks up `slack_team` itself. See [surfaces](./surfaces.md).
- **Background work.** A sweep has no request. It calls a _claim function_ (a `SECURITY DEFINER` SQL function returning `(tenant_id, id)` pairs across tenants), and `claimThenBind` (`src/tenants/claim.ts`) runs each row's work inside `inTenant`. See [background work](./background-work.md).
- **Single-organization install.** `tenants` has one row. At start-up `bindBootTenant` (`src/tenants/boot.ts`, called from `startQm` in `src/start.ts`) asks `qm_boot_tenant()` for it once. Steps 2 to 6 still run and resolve to that row; a request that names no tenant falls back to it; start-up work runs inside `inBootTenant`. If core connects as the owner of the tables, step 6 does not filter (Postgres skips row security for a table's owner), which is harmless with one tenant.

**The schema change.** Ada adds a column recording when a participant was last notified.

1. **Define.** She appends one `PgMigrationDefinition` to the store's list: `PARTICIPANT_NOTIFIED_AT` in `SESSION_MIGRATIONS` (`src/sessions/session-schema.ts`), id `sessions/store/0069-participant-notified-at`, statements `SET LOCAL lock_timeout = '5s'` and `ALTER TABLE participants ADD COLUMN IF NOT EXISTS notified_at BIGINT`. Each array element is one SQL statement. She does not edit an earlier migration.
2. **Register.** `createPostgresSessionStore` (`src/sessions/postgres-session-store.ts`) hands the list to `createPgPool`. `definePgMigration` validates each entry and computes its checksum, and the entry joins an in-process registry keyed by database URL. `buildApp` (`src/wiring.ts`) constructs the stores, so when it returns their migrations are registered and no query has been sent. Not every migration in the codebase is among them: the maps `render_sandbox_namespace` (built only when the Render sandbox backend is enabled) and `web_push_subscriptions` and `web_push_vapid` (built only when the public URL is `https`) register only in those configurations, and the vector-memory migrations register in `registerVectorMigrations` (called by `src/migrate-main.ts`) or when the vector store is first created.
3. **Apply.** Three entry points then call `migrateRegisteredPgSchemas`: `src/migrate-main.ts` (migrate and exit), `startQm` (core) and `src/runs/worker-main.ts` (run worker). It sorts everything registered by id and passes it to `applyPgMigrations` on a one-connection pool that always uses the direct database URL.
4. **Once, one process at a time.** `applyPgMigrations` takes the Postgres advisory lock `qm:schema-migrations`, so processes starting together queue up. For each migration it reads the ledger table `qm_schema_migrations`: recorded with the same checksum, skip; recorded with a different checksum, throw; not recorded, run the statements and insert the ledger row in one transaction.
5. **Rollout with two releases live.** Release N+1 carries the migration while release N is still serving. Something applies it first: on the AWS target, when a release candidate is deployed (`qm up --candidate` or `qm migrate --candidate`), the CLI runs `src/migrate-main.ts` from the new image as a one-off task; otherwise, and on every other target, the first N+1 process to start does it in step 3 (see [deployments](./deployments.md)). Release N keeps running against the changed schema and never notices the new ledger row, because `applyPgMigrations` examines only the migrations the running code knows.
6. **Why this one is safe.** The column is nullable and release N never names it, and the lock timeout makes the `ALTER` fail after five seconds instead of queueing behind live traffic. A migration that drops or renames something release N still reads breaks N the moment it commits, and the runner has no check for that. **[interpretation]** Destructive changes therefore ship one release after the code stopped using the thing.
   - _Core runs as a non-owner login:_ step 4 may not apply anything. If a migration is pending, start-up fails with `misconfiguration: migration … has not been applied and this database login lacks migration authority`, and the owner login must run `src/migrate-main.ts` first.
   - _Databases differ:_ an empty database, one upgraded from published release v0.1.15, and one that followed `main` commit by commit each hold a different ledger. See "Schema definitions" below.

## The parts

### `src/persistence/pg-pool.ts` — connections, the tenant setting, the migration runner

**Job.** Give every store a `PgPool`: `q` and `query` for single statements, `forTenant(tenant)` for the token path, `pool()` and `sessionPool()` for raw connections, `registerMigration` and `migrate` for schema.

**Key idea.** Three kinds of pool exist per database URL per process, shared by every store through reference counting. The _query_ pool (20 connections) goes to `DATABASE_POOL_URL` when that is set. The _session_ pool (64) always connects directly and serves whatever must hold one Postgres session: advisory locks, leader leases, `LISTEN`. The _migration_ pool (1) always connects directly. The tenant reaches Postgres as a transaction-local setting, which is why it survives a transaction-mode pooler.

**Surprising.** (1) A query with no tenant bound, no timeout and no abort signal is sent bare, without a transaction. On a tenanted table it fails under an app login and returns every tenant's rows under an owner login (both observed). (2) `pool()` and `sessionPool()` return raw `pg` pools that know nothing about tenants; `withPgTransaction` is the helper that sets the tenant on a raw connection. (3) A per-query `timeoutMs` is a transaction-local `statement_timeout`, for the same pooler reason. (4) A closed `PgPool` cannot reopen. (5) The runner has special forms a migration can opt into: `prepare` (statements run first, outside the transaction, with no statement timeout; used for batched backfills), `autocommit`, concurrent-index migrations (only `CREATE INDEX CONCURRENTLY IF NOT EXISTS` statements; an invalid leftover index is dropped and rebuilt), `legacyId` (adopt a row from the older `schema_migrations` table instead of re-running), `upgradeFrom` (run only if the ledger holds the named anchor) and `expectedChecksum` (pin a released migration's text in source).

### `src/persistence/durable-map.ts` — one table per noun, one JSON document per row

**Job.** `createPostgresMap` gives a store `get`, `put`, `merge`, `update`, `all`, `select` and similar over a table of `(tenant_id, id, json)`. Most tables in a migrated database have this shape (observed on an empty database after migrating).

**Key idea.** Every write to a tenanted map bumps a per-tenant counter in `durable_map_versions` in the same transaction. `all()` and `entries()` keep a per-tenant snapshot in memory, read the counter on every call, and refetch when it has moved or the snapshot is older than 15 seconds. A `processMap` has no counter and no snapshot: its `all()` and `entries()` query every time. This is "core memory is a cache" in its smallest form: the cached copy is trusted only while a row in Postgres says it is current.

**Surprising.** (1) Creating a map registers its migrations: the table, its tenancy conversion and its claim functions. `src/wiring.ts` builds three flavours: `artifactMap` (tenanted), `inboundMap` (tenanted, plus an index on `id` alone so a lookup function can find the tenant from the id) and `processMap` (not tenanted; installation facts such as port allocations). (2) `get`, `getMany` and `select` always query; only `all` and `entries` are cached. (3) Fields passed as `indexedFields` get expression indexes on `lower(json->>'field')` and one claim function each, `claim_<table>_tenants_by_<field>`.

### `src/persistence/advisory-lock.ts` and `src/persistence/leader-lease.ts` — one holder across all core processes

**Job.** `createPostgresAdvisoryLock` gives `withLock`, `withSharedLock`, `tryWithLock` and `tryWithLocks`: mutual exclusion by string key. `createPostgresLeaderLease` gives `hold(key, fn)`: run `fn` only if nothing holds the key (another process, or this process already), and return `null` at once otherwise.

**Key idea.** Both are Postgres session-level advisory locks on session-pool connections, so a process that dies releases them with no cleanup code. The periodic sweeps (cron tick, run reaper, wake sweep, monitor poller, app reaper, memory indexer and others) are wrapped in `leaderLease.hold`, so one core process runs each at a time.

**Surprising.** (1) Keys are database-wide, not per tenant: one leader sweeps for all tenants. (2) `withLock` waits by polling every 300 ms and throws after five minutes. Nested locks in one async call chain share a connection, but taking the same exclusive key again inside itself is never granted and runs into that timeout; only `tryWithLocks` lets inner `withLock` calls on its own keys pass. (3) `hold` passes `fn` a `lost` promise that resolves if the lock's connection dies; long work must watch it. (4) Each advisory lock taken outside another pins one session connection (nested ones share it), and all of a process's leader leases share a single connection, so the session pool's size bounds the unnested advisory locks one process can hold at once. (5) Both need a direct connection. Behind a transaction pooler the unlock reports "not held", which the lease logs as a hint that `DATABASE_URL` points at a pooler.

### `src/persistence/postgres-listener.ts` and `src/persistence/postgres-notify-bus.ts` — wake-up hints between processes

**Job.** `createPostgresNotifyBus` returns an event bus whose `emit` reaches subscribers in every core process through Postgres `NOTIFY`. `subscribePostgresChannel` is the lower level.

**Key idea.** One direct connection per database URL per process does all the listening. Five channels use it: `session_state`, `run_signals`, `run_stream`, `qm_run_available` and `loop_item_events`. A notification is a hint to go and read durable state, never the state itself.

**Surprising.** (1) The default encoder silently drops payloads over 7,500 bytes. (2) After a reconnect the listener re-subscribes and then calls each subscriber's `resync`, which must re-read from tables; whatever was sent while disconnected is gone. (3) Channels are database-wide, not per tenant; session-state and loop-ledger events carry a `tenantId` field for that reason. (4) Sending goes through the query pool and so through the pooler; listening cannot.

### `src/persistence/blob-transfer.ts` and `src/persistence/s3.ts` — bytes in transit

**Job.** `BlobTransferStore` (`put`, `open`, `delete`, `sweep`) holds short-lived blobs moving between core, sandboxes and clients. `s3.ts` builds the S3 client and recognises "not found" errors.

**Key idea.** `src/wiring.ts` picks one of two interchangeable stores: `createLocalBlobTransferStore` (a directory under `DATA_DIR`) or `createS3BlobTransferStore`. Transfer blobs have no table. A sweeper deletes any that are older than six hours.

**Surprising.** (1) Local disk is a supported store, not a test double. It is one machine's disk: no code shares it between core processes. **[interpretation]** A deployment with more than one core machine therefore needs S3 or a shared volume; the deployment CLI requires S3 on the Fly target (`cli/src/backends/registry.ts`). (2) On S3, core also writes a lifecycle rule named `qm-transfer-expiry` to the bucket (one day, on the transfer prefix), keeping the bucket's other rules. If that fails, core logs it and relies on the sweeper. (3) Durable bytes (files, tool output, shared transcripts) use a second interface, `DurableByteStore`, chosen by `SNAPSHOT_STORE` rather than `TRANSFER_STORE`; see [artifacts](./artifacts.md).

### `plugins/chassis/src/tenant.ts` and `src/tenants/context.ts` — the binding and the token

**Job.** Say which tenant the current work belongs to.

**Key idea.** Two forms exist side by side, and the code is partway from the first to the second. The _binding_: `withTenant(id, fn)` stores the tenant in `AsyncLocalStorage`; `boundTenant()`, `currentTenant()` and `ambientTenant()` read it; `PgPool.q` picks it up without being told. The _token_: `withTenant` also hands its callback a `Tenant` object that nothing else can construct. A converted store takes the token as its first argument, queries through `pool.forTenant(tenant)`, and writes `tenant_id = $n` in its own SQL, so it is correct even under a login that bypasses row security. `forTenant` still sets `qm.tenant_id`, so row security keeps checking behind it.

**Surprising.** (1) `withTenant` checks only that the id is a lowercase UUID, not that the tenant exists. (2) While both forms exist, `forTenant` refuses a token whose tenant differs from the binding. Unbound work, including work inside `withoutTenant`, may use any token. (3) While a transaction opened by `withPgTransaction` or `forTenant(tenant).transaction` is running, binding a different tenant in the same call chain throws. (4) `ambientTenant()` turns the binding back into a token for callers that have none yet, as do the two bridge writers `recordAuditInBinding` (`src/audit/audit-log.ts`) and `recordErrorInBinding` (`src/admin/error-log.ts`); each use is a site still to convert.

### `src/tenants/boot.ts`, `src/tenants/claim.ts`, `src/tenants/cache.ts` — boot tenant, claim then bind, per-tenant memory

**Job.** `boot.ts` reads the boot tenant once per process. `claim.ts` lets background work find rows across tenants (`claimFunction`, `claimRows`, `claimThenBind`, `claimThenLoad`, `inTenant`). `cache.ts` holds in-process state per tenant (`perTenant`, `tenantKeyed`, `tenantListeners`, `onTenantLoad`, `loadTenant`).

**Key idea.** Code asks "one organization or many" by calling `bootTenant()`: a value means single-organization, `undefined` means multi-tenant. Background work does not read tenanted tables unbound; it claims, then binds each tenant it was handed. `perTenant` (keyed by the binding) and `tenantKeyed` (keyed by a token) are the wrappers for in-process state: each lazily creates one value per tenant, so one tenant cannot read another's cached value.

**Surprising.** (1) The boot tenant is read at start-up and never again. Inserting a second `tenants` row turns a deployment multi-tenant at each process's next restart. (2) `qm_serving_tenants()` leaves out tenants whose `settings.serving` is `false`, unless there is a boot tenant; the claim functions of durable maps and of the run store filter by it, except `claim_terminal_runs`. (3) Per-tenant maps never evict. (4) `loadTenant` runs each loader once per tenant per process. Only the settings loader re-runs, in the background, when a request arrives more than 30 seconds after the last load, so a changed setting reaches a process after its next request for that tenant.

### `src/tenants/lookup.ts`, `src/api/request-tenant.ts`, `src/api/inbound-tenant.ts` — from an inbound key to a tenant

**Job.** Turn what an unauthenticated caller presents (a webhook id, a Slack team id, a share token, an app host name) into a tenant id before any tenant is bound.

**Key idea.** One `SECURITY DEFINER` SQL function per kind of key, called through `tenantFor(key, value)`. The kinds are `slack_team`, `webhook`, `loop_ingress`, `oauth_flow`, `consent_link`, `deployment`, `share`, `secret_drop`, `slack_bridge`, `partner_chat` and `app_host`. These functions are not the only code on the request path that reads across tenants: `src/api/routes/auth-broker.ts` reads `qm_tenants_for_email` and `qm_tenants_for_principal` through the directory store, self-serve calls `qm_self_serve_tenant`, and `src/api/routes/web-events.ts` runs a claim function through `claimThenBind`.

**Surprising.** (1) Ids are unique per tenant, not globally, because primary keys are `(tenant_id, id)`. The first nine lookups return a tenant only when exactly one tenant has the key; `partner_chat` relies on a unique index instead, and `app_host` reads `app_hosts`, whose primary key is the host label, before falling back to the `deployment` lookup. (2) A public route that takes a new kind of key needs three things: a lookup function, an index on the key that does not start with `tenant_id` (`inboundIndexes`), and `tenant: { by, key }` on the route. (3) One inbound event can belong to several tenants: `gmailTenants` returns all of them and the handler fans out. (4) A capability token carries the tenant it was minted under, so a sandbox calling back lands in the right tenant with no lookup.

### `src/tenants/settings.ts`, `src/tenants/external-org.ts`, `src/tenants/app-handle.ts` — per-tenant values

**Job.** Hold what differs between organizations on one deployment: `tenants.settings`, a JSON object validated by `tenantSettingsSchema`.

**Key idea.** A value that differs per organization cannot come from env, because env is one value per deployment. Readers call `tenantSettings()` or `loadedTenantSettings()`. Those of `slackBridgeToken`, `brandName`, `modelGatewayKey` and the sandbox keys fall back to the deployment's value when the key is absent, as in `tenantSettings().slackBridgeToken ?? opts.token`. The others differ: `allowedEmails` and `orgSlug` fall back to the deployment's value only for the boot tenant; with `deploymentModelKey: false` and no `modelGatewayKey`, `gatewayKey` (`src/model/provider-endpoints.ts`) throws `this workspace has no model gateway key of its own`; `serving`, `handle` and `partnerChatAccount` are read in SQL; and no code in `src` or `plugins` reads `oidcClient`.

**Surprising.** (1) `ORG_ID` is the same for every tenant. Scope ids such as `org:<ORG_ID>` and the `org_id` columns are therefore identical across tenants; only `tenant_id` separates organizations. A database remembers the `ORG_ID` it first ran under and refuses another (`src/resolution/config-store.ts`). (2) `externalOrgId()` is the organization's name for outside systems: the tenant's `orgSlug`, else `ORG_ID` for the boot tenant, else the tenant id. At this commit only the Composio user id uses it. (3) The sandbox settings are ignored for the boot tenant (`src/sandbox/tenant-sandbox-shape.ts`); a single-organization install sets those in env. (4) `handle`, or else a cleaned `orgSlug`, prefixes the host names of the tenant's published apps. The table `app_hosts` keeps those host names unique across tenants.

### `src/tenants/migrations.ts` and the conversions around it — the tenancy schema

**Job.** `TENANCY` creates `tenants`, `qm_bound_tenant()`, `qm_boot_tenant()` and `qm_serving_tenants()`. `tenantTables` returns the migrations that make existing tables tenanted: add `tenant_id`, build tenant-first unique keys without blocking writes, swap them in, add foreign keys to `tenants`, enable row security, create the policy.

**Key idea.** Only three tables are ever created with a `tenant_id` column: `items` and `blobs` (in the session base schema and in the published-release upgrade), and `persona_versions` (on a database where `users/v2/0005-persona-versions` has not already created it). Any other store creates its table and then names it in a `tenantTables` call (durable maps do it through `durableMapTenancy`). `test/tenant-tables.test.ts` fails if any table lacks the column, tenant-first keys or the policy, unless the table is on its list of untenanted tables with a reason.

**Surprising.** (1) Rows that existed before their table became tenanted are stamped with the oldest tenant, and one is created if `tenants` is empty. An empty database also finishes its first migration run with exactly one tenant row (observed by running `src/migrate-main.ts` against an empty Postgres 16). (2) Row security is enabled, not forced, so Postgres does not apply it to the tables' owner or to a superuser. It filters only when core connects as a separate app login, which `grantAppRole` sets up; that login may read only the bound tenant's row of `tenants` and may not write it. Unconverted stores send SQL with no tenant predicate, so a multi-tenant deployment is isolated only when core uses such a login. Nothing at start-up checks this. (3) `src/tenants/retire-0116-tenancy.ts` and `src/tenants/prebuilt-indexes.ts` exist only to remove an earlier tenancy layout from databases that ran published release v0.1.16. `src/identity/user-tenancy.ts` is the same kind of conversion for `users` and `user_links`.

### `src/tenants/operator.ts`, `src/tenants/self-serve.ts`, `src/tenants/external-orgs.ts`, `scripts/tenant.ts` — creating tenants

**Job.** A tenant row beyond the first comes from one of two places: an operator runs `qm tenant create` (`runTenantCommand`), or an organization from a trusted identity provider signs in for the first time and `createSelfServe` creates one.

**Key idea.** Both need more authority than the app login has. The operator commands run with the owner login in `DATABASE_URL`. Self-serve goes through the `SECURITY DEFINER` function `qm_self_serve_tenant`, which maps `(issuer, organization id)` to a tenant in `tenant_external_orgs`.

**Surprising.** (1) Self-serve refuses on a single-organization install. (2) A self-served tenant starts with `serving: false` and `deploymentModelKey: false`. Core then calls the provisioner (see Contracts), stores the model gateway key it returns, and turns `serving` on. (3) `qm tenant members add` writes `directory_members`, and with `--admin` also `admin_grants`, directly.

### Schema definitions — `src/sessions/session-schema.ts`, `src/sessions/published-upgrade.ts`, `src/migrate-main.ts`

**Job.** There is no schema file to read. Each store module owns an ordered list of migrations; `SESSION_MIGRATIONS` begins with `TENANCY`, so the tenancy tables exist before any other.

**Key idea.** Three kinds of database must converge on one schema. An empty one runs a _base schema_ migration (`sessions/store/0047-base-schema`; runs and the directory have their own) that creates the tables in one step, then everything after it. One that followed `main` already holds the earlier ids in its ledger, so the base schema does nothing. One from published release v0.1.15, the last without the base schema, holds an _anchor_ id, `sessions/store/0033-client-tools`; the migrations in `PUBLISHED_SESSION_UPGRADE` carry `upgradeFrom` that anchor, run only there, and bring it up to the base. A database older than the anchor is refused with a message to upgrade through an intermediate release.

**Surprising.** (1) Released migrations are frozen. An applied migration whose text changes fails the ledger's checksum comparison at start-up. Ten migrations also carry `expectedChecksum` in source, which makes `definePgMigration` throw when their text drifts; `test/migration-policy.test.ts` constructs the session, directory and run stores, so it exercises the pins of those three stores only. A change is always a new migration. (2) Two orders exist. Start-up applies everything sorted by id. A store used before that (a script, a test) applies its own list in array order. The two do not always agree (`sessions/store/0056-persona` is listed after `sessions/store/0057-claims`), so a migration must be correct in either order. (3) `src/migrate-main.ts` builds the whole app, installs the cron queue and runs a readiness check, so it needs the same env as core. (4) Most ledger rows in an empty database are generated per table for durable maps (observed). (5) `scripts/check-published-upgrade.sh`, run in CI, migrates a database with the latest published tag and then with the current tree.

### `scripts/tenant-ratchet.ts` and `scripts/tenant-ratchet.json` — counting what is left

**Job.** The CI step `Tenant ratchet` (`npm run lint:tenancy`) uses the TypeScript type checker to count calls, in non-test code reachable from `src/`, to the functions that depend on the ambient binding. It compares the totals with the JSON baseline.

**Key idea.** Four counters: `mintSites` (`withTenant`), `implicitQueries` (`PgPool.q`, `PgPool.query`, `PgPool.pool`, `PgPool.sessionPool`, `withPgTransaction`), `ambientReads` (`boundTenant`, `ambientTenant`, `currentTenant`) and `ambientCaches` (`perTenant`, `tenantListeners`, `onTenantLoad`). CI fails if a count rises, if it falls without the baseline being lowered, or if the JSON names a metric the script does not count.

**Surprising.** (1) New code that calls `pg.q(...)` raises the `implicitQueries` total and fails CI unless the same change removes another counted call. It must take a `Tenant` and use `forTenant`. (2) `--update` only lowers the baseline; raising it is a hand edit. `--list` prints per-file counts. (3) Only calls count: passing `pg.q` by reference is invisible. Helpers that wrap `withTenant`, such as `inTenant` and `inBootTenant`, count once. (4) Most query sites are still implicit. The converted stores are admin grants, ACL grants, the audit log and event sinks, decisions, budgets and teams, plus one to three calls each in other stores.

### `src/cron/job-queue.ts` — the one schema QM does not define

**Job (as a storage consumer).** Cron fires are queued with the pg-boss library, which keeps its tables in a separate Postgres schema, `pgboss`.

**Key idea.** `installCronQueue` creates or upgrades that schema at start-up and in `src/migrate-main.ts`. The running queue opens it with `migrate: false` and refuses to start if the installed version is not the one the library expects.

**Surprising.** (1) Its tables are outside the ledger and have no row security; each job carries its `tenantId` in the payload. (2) It queries through the shared query pool, so it goes through the pooler. (3) If core's login may not install it, start-up logs a misconfiguration line and continues. See [background work](./background-work.md).

## Where the complexity lives

- **Three carriers of one fact.** Which tenant a query belongs to is held in the `AsyncLocalStorage` binding, in the `Tenant` token and in the Postgres setting `qm.tenant_id`. The first is being replaced by the second; the ratchet baseline is the size of what remains. Until it reaches zero, a function's signature does not say whether it needs a tenant. Transitional.
- **Settings that multiply.** Boot tenant or not, owner or app login, pooler or not, local disk or S3. Behaviour differs across the combinations: row security filters under only one kind of login; core migrates at start-up under only the other; sandbox settings in `tenants.settings` apply only without a boot tenant. The master's _Config-matrix expansion_ lens covers this kind of growth.
- **The migration machinery outweighs the schema.** Six opt-in forms in the runner; `tenantTables` emits seven migrations for each group of tables and every durable map about a dozen; three kinds of starting database. Code that serves only databases from older releases is still carried: `src/tenants/retire-0116-tenancy.ts`, `src/tenants/prebuilt-indexes.ts`, `src/sessions/published-upgrade.ts`, `src/sessions/legacy-history-migrations.ts`. The master's _Historylessness_ lens describes this kind of sediment.
- **Parallel mechanisms.** Four things answer "only one process does this": advisory locks, leader leases, claim functions over the run queue (see [turns](./turns.md)) and the pg-boss cron queue. **[interpretation]** They overlap in purpose; each was read as a separate mechanism.
- **Two byte-store interfaces.** `BlobTransferStore` and `DurableByteStore` each have local, S3 and in-memory variants, and the choice `config.snapshotStore === "s3" && config.s3Bucket` is written out at six call sites (five in `src/wiring.ts`, one in `src/web/shell.ts`) beside the one for `config.transferStore`. The master's _Duplication_ lens covers this.
- **Abstractions with one implementation.** `DurableMap` has only `createPostgresMap`. `AdvisoryLock` and `LeaderLease` each have a Postgres implementation and a no-op. Outside tests and the smoke scripts under `scripts/`, the no-op lock appears only as a default argument in `src/deploy/render-deploy-provider.ts`, and the no-op lease is not used.
- **One shared query pool.** Every store, the cron queue and notification sends in a process share 20 connections. The master's _Performance_ lens records an admin list query that starved turns this way.
- **Process memory.** The ambient per-tenant caches are plain maps that never evict. The master's _Non-durability_ lens records what happened when state of this kind was treated as the source of truth.

## Contracts

**Connections.** `DATABASE_URL` must reach Postgres directly, because locks, leases, `LISTEN` and migrations need a session. `DATABASE_POOL_URL` is a transaction-mode pooler in front of the same database. Removing it and restarting sends queries back to the direct URL; no data changes.

| Use                                                               | Connects to                                     | Pool, per process and URL |
| ----------------------------------------------------------------- | ----------------------------------------------- | ------------------------- |
| Ordinary queries and transactions, the cron queue, `NOTIFY` sends | `DATABASE_POOL_URL` if set, else `DATABASE_URL` | query, up to 20           |
| Advisory locks, leader leases, `LISTEN`                           | `DATABASE_URL`                                  | session, up to 64         |
| Migrations                                                        | `DATABASE_URL`                                  | migration, 1              |

Count every core and worker process when sizing the server. `scripts/test-pgbouncer.sh` (workflow `.github/workflows/pgbouncer.yml`, on every pull request) runs the pool, lock, timeout, migration and queue paths through a one-connection transaction pooler; `test/postgres-listener.test.ts` covers notification delivery, reconnect and teardown.

**Database logins.** A login may apply migrations if it owns the schema, or has `CREATE` on it and owns `qm_schema_migrations` (before the ledger exists, `CREATE` is enough). `qm db grant <role>` gives an app login, on schemas `public` and `pgboss`: `USAGE, CREATE` on the schema; `SELECT, INSERT, UPDATE, DELETE, TRUNCATE` on tables; `USAGE, SELECT, UPDATE` on sequences; `EXECUTE` on functions; the same as default privileges for objects the owner creates later; and on `tenants`, write privileges revoked and `REFERENCES` granted. Run it as the owner after migrations.

**Migrations.** An id matches `^[a-z0-9][a-z0-9._/-]*$`, case-insensitively, and contains no `..`. Each array element is exactly one SQL statement. The checksum is the SHA-256 of the JSON array of trimmed statements. The ledger is `qm_schema_migrations(id TEXT PRIMARY KEY, checksum TEXT, applied_at TIMESTAMPTZ)`. A recorded checksum that differs from source stops start-up; the fix is never to edit the ledger.

**SQL surface.** The setting `qm.tenant_id` (a lowercase UUID, transaction-local) and the functions `qm_bound_tenant()`, `qm_boot_tenant()`, `qm_serving_tenants()`, `qm_tenant_for_<key>(text)` and `claim_*`.

**Operator commands**, run from a checkout with the owner login in `DATABASE_URL`: `qm tenant create [--brand-name <name>]`, `qm tenant list`, `qm tenant settings set <tenant> <key> <json>` (`null` removes the key), `qm tenant members add <tenant> <email> [--admin]`, `qm db grant <role>`.

**Workspace provisioner.** For a new self-served tenant core sends `POST` to `WORKSPACE_PROVISIONER_URL` with JSON `{ tenant, brandName, issuer, externalOrg: { id, name }, nonce }` and the headers `x-timestamp` and `x-signature` (`signedRequestHeaders` in `plugins/chassis/src/source-auth-sign.ts`; the key is derived from `CORE_SIGNING_SECRET` by `provisionerSigningKey`). It expects, within 30 seconds, without redirects and in at most 65,536 bytes, `{ "settings": { "modelGatewayKey": "<key>" } }`.

**Object layout.** Transfer blobs: `<S3_PREFIX>transfer/<32 hex characters>`, with the bucket lifecycle rule `qm-transfer-expiry`. Durable bytes are stored by content hash as `files/<sha256>` beneath `<S3_PREFIX>` itself (file contents), `<S3_PREFIX>tool-output/<tenant id>/`, `<S3_PREFIX>session-shares/` and `<S3_PREFIX>deploy-git/`; web UI releases (`web-ui/`) and direct uploads (`files/uploads/<32 hex characters>`, which stay at that key as the file's bytes and are not stored by content hash) also live under `<S3_PREFIX>`. On local disk the same data sits under `DATA_DIR` in `transfer`, `docstore`, `tool-output/<tenant id>`, `session-shares` and `web-ui`. `DATA_DIR` also holds `deployments` (snapshots of published apps' files) and `deploy-git` (the apps' git repositories, unless `DEPLOY_GIT_DIR` names another place); without S3 the git archives are kept as base64 in the `deploy_git_repos` map, not in a byte store.

**Ratchet baseline.** `scripts/tenant-ratchet.json` is one JSON object with exactly the numeric keys `mintSites`, `implicitQueries`, `ambientReads` and `ambientCaches`.
