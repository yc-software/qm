# Web UI and clients

_Verified against `main` at eb148f69d (2026-11-24). Statements were read in the code at that commit unless marked **[interpretation]**._

## In one paragraph

A person reaches QM through a browser page, a desktop app or an iPhone app. All three are thin: they sign in, list conversations, send messages and draw what comes back. None of them runs a model. The only agent work a client carries out is on the person's own machine: the desktop app can drive Mac apps when the agent asks. Core, the server, does the rest. When `PUBLIC_PORT` is set, core listens on a second port, the _front door_. There it signs the person in and sets a cookie, serves the web page as a static _release_ read from object storage, and passes the page's `/api/...` calls to core's ordinary `/v1` routes, which accept the cookie as proof of who is calling. The page sends a message with one POST and then follows that turn over a server-sent event stream. A second, per-person event stream tells every open tab which conversations changed. Because the page is a release named by a pointer file, an operator can swap it without restarting core, and an open tab reloads itself into the new release when it is idle. The desktop app is the same page inside an Electron window. The iOS app is native SwiftUI over the same `/api` calls.

## One visit, traced end to end

The running example: Ada, at Acme, opens `https://qm.example.com/`, asks "What changed in the billing repo this week?", and an operator publishes a new web UI release while her tab is open.

1. **Core opens the front door.** `startQm` (`src/start.ts`) builds the app. If `PUBLIC_PORT` is set it also creates the web shell (`createWebShell`), the web events hub (`createWebEvents`) and the static part of the `/me` answer (`webMeConfig`). It starts the API server on `PORT`, then calls `startFrontDoor` (`src/web/front-door.ts`), which imports `plugins/portal` into the same process and has it listen on the public port. There is no separate portal or web UI service.
2. **Sign-in gate.** Ada's `GET /` reaches the portal's `handle` (`plugins/portal/src/index.ts`). She has no `portal_session` cookie and the request wants HTML, so it redirects her to `/auth/login`. Sign-in itself belongs to [scopes](./scopes.md). It ends with a sealed `portal_session` cookie that names Ada, her organization and, in a [Multi-tenant deployment](../SPEC.md#deployment-shapes), her tenant.
3. **The shell serves the live release.** With the cookie, `handle` passes `GET /` to core through the `CoreHandoff` object `startFrontDoor` gave it. `/` is not an API path, so the handoff's `shell` function runs `serve` (`src/web/shell.ts`) inside Ada's tenant. `serve` asks the release reader (`createWebReleaseReader`, `src/web/releases.ts`) which release is live, reads that release's `index.html`, adds `<meta name="qm-release" content="<id>">`, injects the organization's branding, sets the content security policy and sends it with `cache-control: no-cache`. The scripts and styles it names are under `/assets/`, have content hashes in their names, and are served as immutable.
   - _No model provider yet:_ before handing over an HTML request, the portal checks whether core has a model provider. If not, an admin is redirected to `/settings/onboarding` and anyone else gets a 503 "not configured" page.
4. **The page asks who it is.** `boot` (`plugins/web-ui/src/shell.ts`) fetches `/me`. The portal recognizes an API path and calls the handoff's `handle`, which re-emits the request on core's API server in process, with no network hop. `front` (`src/api/server.ts`) rewrites `/me` to `/v1/web/me` with `apiAlias` (`src/api/browser-session.ts`). `gate` sees a route marked `browser` and a cookie, so it calls `browserIdentity`, which opens the cookie, checks that its tenant matches the request and refuses cross-origin writes. The handler in `src/api/routes/web-me.ts` answers with her id, display name, a list of permissions, branding and the optional analytics and error-reporting settings. Every answer on this path carries an `x-qm-release` header naming the release core is serving now.
5. **Sidebar and the per-person stream.** `refreshSessions` (`plugins/web-ui/src/sessions.ts`) calls `GET /api/sessions` and draws the sidebar. `ensureDeliveryStream` (`plugins/web-ui/src/conversations.ts`) opens an `EventSource` on `/api/deliveries/events`, the alias of `/v1/web/events`. The hub (`src/api/routes/web-events.ts`) keeps her response open, filed under her tenant and her id.
6. **Send.** Ada presses Enter. Each conversation in the page holds a Pi `Agent`, a client-side state machine from the Pi library, used here only to hold messages and streaming state. Its model call is replaced by `makeCoreStreamFn` (`plugins/web-ui/src/core-bridge.ts`), which POSTs `/api/turn` with the text, a thread ref the page minted (`web:<ada>:<uuid>`), an idempotency key, her time zone and her model picks. `webTurn` (`src/api/routes/web-turns.ts`) checks the thread and scope, builds a turn request with `surface: "web"` and a `human` origin, and calls `postTurn` with `async=1`. Core answers at once with a run id. What happens to the run is in [turns](./turns.md).
   - _Attachments:_ the page uploads each file first (`POST /api/blobs`) and the turn carries blob ids.
7. **Follow the run.** `followRun` opens `GET /api/runs/<id>/events` (`src/api/routes/run-events.ts`). Reply text arrives as `delta` frames addressed by character offset, reasoning as `reasoning` frames, and the whole run as `run` snapshots until `RUN_FINISHED`. If the stream does not open within four seconds or goes silent, `pollRun` polls `GET /api/runs/<id>` instead. The text Ada sees is the text core wrote to the session's item log; a reload reads it from there.
8. **Her other tabs hear about it.** Core publishes session-state events (`working`, `awaiting_approval`, `idle`) on a Postgres notify bus, so they reach every core instance. `createWebEvents` forwards each one to the open streams of that session's participants. When core queues a delivery for a web thread (a cron's report, for example), the hub's sweep finds it, sends a `delivery` frame naming the thread and acknowledges it; the page then refetches that transcript.
9. **A release is published while the tab is open.** The operator runs `qm ui publish --dir plugins/web-ui/dist-web`. `runUiPublish` (`cli/src/commands/ui.ts`) uploads the hashed assets, then the release's own files with `index.html` last, then rewrites `live.json`. Each core re-reads that pointer at most every two seconds. Ada's tab keeps working, because the chunks its release needs are still under `assets/`. Her next API answer carries the new id in `x-qm-release`; `webFetch` remembers it; `reloadIntoServedRelease` (`plugins/web-ui/src/stale-release.ts`) reloads the page the next time the tab gains focus, becomes visible or comes back online, unless a draft, an attachment, a running reply or an open dialog would be lost.

Where other paths diverge:

- **Desktop app.** `desktop/main.mjs` loads the same URL in a sandboxed Electron window with its own persistent cookie store. Sign-in happens in the person's default browser and returns through the `qm-desktop://auth/callback` link. The page notices `window.qmDesktop` and labels its turns `x-qm-client: desktop`. Steps 3 to 9 are unchanged.
- **iOS app.** There is no web page. SwiftUI screens call the same `/api/...` aliases with the `portal_session` cookie kept in the device Keychain, follow a run over the same run event stream, and poll every five seconds instead of opening the per-person stream.
- **A turn Ada did not send.** A cron fire or a subagent wake runs with no page following it. Her tabs learn of it from the per-person stream. If she opens that conversation while it runs, the page asks `GET /api/runs/active` for the thread's live run (`activeRunForThread`) and follows it as in step 7.
- **Slack.** A Slack conversation does not pass through this area to run ([surfaces](./surfaces.md)). It still appears in Ada's sidebar, because all surfaces share one session store, and the page opens it read-only.
- **One tenant or many.** The cookie's tenant selects branding and the events lane. The web UI release is one per deployment; every tenant gets the same page.

## The parts

### `src/web/front-door.ts`

**Job.** Start the portal on the public port and give it three functions for reaching core: `serves` (is this an API alias?), `handle` (run it on core's API server), `shell` (serve the page). **Key idea.** The portal and core are one process joined by function calls; the portal still reads its settings from environment variables, so `startFrontDoor` writes `CORE_API_URL`, `CORE_ORG_ID` and `PUBLIC_WEB_URL` into the environment before importing it. **Surprising.** It throws at boot if `PORTAL_SESSION_SECRET` is missing. A deployment with `PUBLIC_PORT` set and no secret does not start.

### `src/web/shell.ts`

**Job.** Answer every non-API GET on the public port: `index.html` for any path without a file extension, files from the live release, `/manifest.webmanifest`, and the read-only page for a shared conversation (`sharePage`, filled from `shared.html`). **Key idea.** It never reads the page from the image's disk at request time. It reads from a release store: S3 when `SNAPSHOT_STORE=s3` and `S3_BUCKET` are set, otherwise a directory under `DATA_DIR` ([storage](./storage.md)). **Surprising.** The content security policy is built from optional settings (analytics origins, the browser error-reporting origin, the managed Slack service), so adding a third-party script to the page means changing this file or those settings, not the HTML. `/app-edit` and `/app-share` get a looser `frame-ancestors` so one app subdomain can frame them, and only when `DEPLOY_APPS_DOMAIN` is set ([artifacts](./artifacts.md)).

### `src/web/releases.ts` and `cli/src/web-release.ts`

**Job.** Store, publish and read releases. `cli/src/web-release.ts` holds the layout both sides must agree on (key names, how a release id is computed, the pointer format); core imports it from the CLI package. **Key idea.** Two fields in `live.json`. `release` is what to serve. `deployed` is the release the newest core image carried. At boot, `deployBundledRelease` uploads the image's bundle if the store lacks it and takes over the pointer only when `deployed` names a different release. So deploying a new core ships its web UI, while restarting the same image keeps whatever `qm ui publish` made live since. **Surprising.** A core whose own bundle is not the `deployed` one (an old instance during a rolling or blue-green deploy) ignores `release` and serves its own bundle, so page and API always come from the same build. If the pointer becomes unreadable, core keeps serving the release it last read and reports the failure; a core that has never read one answers 503 `web_ui_unavailable`.

### `cli/src/commands/ui.ts`

**Job.** `qm ui publish --dir <bundle>` makes a built bundle live; `qm ui publish --release <id>` rolls back to an uploaded release. **Key idea.** It writes with the operator's own AWS CLI, in an order that is safe to interrupt: assets, then documents, then `index.html` (whose presence marks the release complete), then the pointer. It leaves `deployed` unchanged and prints the previous release id, which is what a rollback needs. **Surprising.** It only works where the operator can write the bucket core reads: on the `aws` target the deployment's object bucket, elsewhere `S3_BUCKET` from `env.core`, with `AWS_ENDPOINT_URL_S3` for an S3-compatible store. It refuses on the `render` target, on any target whose core does not use S3, and on the `fly` target without an S3 endpoint in the environment; those deployments ship web UI changes with `qm up` ([deployments](./deployments.md)). Nothing in the command checks that a published bundle matches the running core's API; publish bundles built from the deployed source line.

### `src/api/browser-session.ts`

**Job.** Map the page's paths to `/v1` routes and turn the session cookie into an identity. **Key idea.** `API_ALIASES` is an explicit list of about 170 entries, plus every `/v1/admin/` route marked `browser`. An alias resolves only if its target route is marked `browser` or is public. A path that is not listed does not exist for the page, even if a `/v1` route for it does. **Surprising.** `browser` has three values. `true` accepts same-origin writes only. `"embed"` also accepts writes from origins listed in `PORTAL_API_ALLOWED_ORIGINS`. `"self"` is same-origin and refuses a session in which an admin is impersonating someone. The lane applies only when the request has the cookie and neither a capability header nor a signature.

### `src/api/routes/web-turns.ts`, `web-me.ts`, `web-events.ts`

**Job.** The routes only a web client uses: send a turn, answer an approval, signal a live run (stop, steer), delete an ephemeral chat; describe the signed-in person; hold the per-person stream. **Key idea.** `web-turns.ts` is a translator. It turns a small browser body into a full turn request and forwards it to the same `postTurn` every other caller uses, so web turns get no private path into core. **Surprising.** The events hub lives in memory in each core process and nothing is replayed. A client that reconnects is expected to refetch (the page treats every reopen as a resync). A web delivery whose owner has no open stream is kept for a minute and then acknowledged anyway; nothing is lost, because the reply is already in the item log **[interpretation]**.

### `src/api/routes/web-push.ts` and `src/notifications`

**Job.** Tell a person about a reply in a web conversation they are not viewing. **Key idea.** `watchReplyNotices` listens for a session going idle or waiting for approval, claims a notice per participant in one SQL update (so each reply notifies once), and sends it two ways: as a `notify` event on the web events stream, and as Web Push to stored subscriptions. **Surprising.** Three independent conditions: the person must have the `web_notifications` flag; push additionally needs an `https` public URL, without which the push routes answer 404; and the browser must grant permission.

### `src/api/routes/ui-canvas.ts`

**Job.** Let the agent place live HTML, CSS and JavaScript in a person's page, and read a snapshot of what the page shows. **Key idea.** The agent calls `/v1/ui/canvas` and `/v1/ui/observe` from its sandbox with its capability token; the page loads the canvas through the cookie-authenticated `/v1/ui/canvases/...` routes. **Surprising.** Canvas script runs unsandboxed in the person's page with their full session. It is gated by the `ui_canvas` flag for that one person and works only during a turn that person started from the web UI.

### `src/api/routes/voice.ts` and `src/voice`

**Job.** Speech: transcribe a recording (`/v1/web/dictation`) and open a live voice session over WebRTC (`/v1/web/voice/sessions`), both through OpenAI with the deployment's `OPENAI_API_KEY`. **Key idea.** Live voice does not run tasks. The voice model is given one function, `ask_qm`, and the client sends each delegated request as an ordinary turn. **Surprising.** At this commit the web page has no microphone control: only the iOS app calls the voice routes, and no client in the repository calls the dictation routes (iOS dictation is on the device).

### `src/surfaces/client-relay.ts`, `src/surfaces/desktop-calls.ts`, `src/api/routes/desktop-calls.ts`

**Job.** Carry a tool call from a running turn to a client program and bring the result back. **Key idea.** `relayToClient` writes a pending record to `web_ui_state`, emits a UI signal on the session-state bus addressed to one person, and waits for a `client_result` run signal. For the `desktop` tool, an open desktop app sees the signal on its web events stream, claims the call (`claimDesktopCall`, first claim wins), runs it and posts the result. **Surprising.** The `desktop` tool is declared on every turn, on every surface. Whether it does anything is decided at call time. It runs only if the turn began with a message a person addressed to the agent (`mayDriveDesktop`); otherwise the call returns a fixed refusal. If no desktop app claims it before the deadline, the call returns "no desktop app answered". A turn sent from a desktop window is pinned to that window; a turn from Slack or a browser can be claimed by any desktop app that person has open.

### `src/api/web-context.ts`

**Job.** Answer the agent when it asks to read "this conversation" on the web surface. **Surprising.** Web has no channel history: only the current thread is readable, a file request is refused with a sentence the model can read, and a search across conversations returns nothing, marked as unconfigured.

### `src/feature-flags.ts`

**Job.** The list of feature names and the store that says which scopes have each. **Key idea.** A flag is on for a person when its row lists the organization scope or that person's personal scope. No row means off. **Surprising.** Several flags are marked `personalOnly`, and flags are edited by admins in the admin UI, not in deployment configuration, so two people on one deployment can see different products.

### `plugins/web-ui`

**Job.** The browser application: about 55,000 lines of TypeScript on Lit and 22,000 lines of CSS, built by Vite into two entry documents (`index.html`, `shared.html`). **Key idea.** It imports nothing from core. It shares code only through `plugins/chassis` and talks to core only over the aliases, almost always through `webFetch` and `api` in `core-bridge.ts`. The weight is in `chat.ts` (transcript, about 4,000 lines), `core-bridge.ts` (the whole client side of the API, about 2,500), `sessions.ts` (sidebar), `composer.ts`, `inbox.ts` and `split.ts` (multiview: several conversations and other panes side by side, built on dockview, with the layout synced through UI state). Browse pages (files, crons, webhooks, skills, apps, memory, personas, contexts) are one file each over a small shared page frame (`plugins/web-ui/src/list-page.ts`). **Surprising.** Its own `README.md` describes product behavior in detail and stays in the repository; this document covers structure. The app keeps its own copy of the session item shape (`plugins/web-ui/src/items.ts`). `plugins/web-ui/public/sw.js` is a service worker used only for push notifications, not for offline use. In development the dev-instance supervisor builds the bundle (`scripts/dev/lib/deps.ts`) and core serves it as a release; no separate dev server sits in the request path.

### `plugins/web-ui/src/admin`

**Job.** The admin UI: organization settings, users, spend, logs and artifact browsers, about 8,000 lines, under `/settings/<view>`. **Key idea.** It is mounted inside the chat app's Settings view by `adminMounter` (`plugins/web-ui/src/admin/sections.ts`) and calls `/api/admin/...`, the aliases of `/v1/admin/...`. **Surprising.** It is different code with its own stylesheet (`admin.css`, about 3,000 lines) and its own layout classes, not the chat app's components. Admin routes refuse impersonated sessions.

### `plugins/chassis`

**Job.** Dependency-free helpers importable by relative path from core, the portal, the auth broker and the web UI: HTTP helpers, error reporting, branding injection, the analytics and browser-error settings parsers, the `desktop` tool definition, the client-surface header. About 1,900 lines. **Surprising.** It never imports core, which is what lets browser code import it. Anything both the page and core must agree on belongs here.

### `plugins/portal`, as the front door uses it

**Job.** Sign-in, the session cookie, tenant choice, and the first routing decision for every public request. **Key idea.** Once a person is signed in, the portal mostly routes: API aliases go to core's API server, app paths under `/d/` to the app proxy ([artifacts](./artifacts.md)), everything else to the web shell. Hashed `/assets/` files are served without a session. **Surprising.** Requests under `/v1/` on the public port are not the browser lane: the portal forwards a short list of signed or token-bearing kinds and answers 404 to the rest. Old `/web-ui/...` links are redirected to the root.

### `desktop/`

**Job.** An Electron shell around an existing deployment's web UI, about 2,600 lines of JavaScript, plus `desk`, a Rust helper of about 8,500 lines that observes and drives Mac apps. **Key idea.** The app adds three things to the page through a preload script: window chrome, `openBrowser`, and `computer.call`, which the page uses to carry out claimed desktop calls. It bundles no backend. **Surprising.** Computer use is macOS only (the page ignores the bridge on other platforms). Automatic updates run only in packaged Apple Silicon builds and read a static feed attached to this repository's `desktop-updates` release.

### `ios/`

**Job.** A native iOS client, about 21,000 lines of Swift. **Key idea.** It reuses the desktop sign-in endpoints and the browser lane. The one server-side accommodation is a `qm://` return link for app-connection callbacks (`mobileReturn` in `src/api/routes/connectors.ts`). **Surprising.** It is a second implementation of most screens, not a web view, so a web UI change does not reach it. Organization administration is not in the app.

## Where the complexity lives

- **Admin UI and chat UI are two interfaces in one bundle.** Separate stylesheets, layouts and controls, joined only by the Settings view. This is the master's _Mismatched UI_ lens.
- **`chat.ts` owns too much.** Transcript rendering, pane lifecycle, approvals, run recovery and forking share one closure (`createChatSurface`). This is the master's _God files_ lens.
- **Four ways to learn that something changed.** The run event stream, its polling fallback, the per-person stream, and the iOS app's five-second polling. Each client combines them differently, and the per-person stream carries five unrelated kinds of message on one connection.
- **Three return paths for a client-run tool call, one of them unused.** Desktop calls return through the claim and result routes. Page snapshots return through `/v1/ui/observe/:callId/result`. A page-declared tool returns as a `client_result` signal on `/v1/web/runs/:id/signal`. All three end as the same run signal, and no client in the repository declares page tools or sends that third form.
- **Three hand-kept copies of the item shape.** Core (`src/sessions/items.ts`), the web UI (`plugins/web-ui/src/items.ts`) and the iOS app (`ios/QM/Item.swift`) each define what a transcript item looks like. This is the master's _Duplication_ lens. **[interpretation]**
- **Every screen exists up to twice.** The alias list is the real client API, and the web UI and the iOS app implement it separately, so a behavior change multiplies by clients.
- **The alias table is a second routing layer.** A new browser feature needs a `/v1` route, a `browser` mark and an alias entry; missing any one gives a 404 that looks like a missing route.
- **Feature flags multiply the product.** At least nine flags change what the web UI shows or how web turns behave, per person. Combined with optional keys and storage choices, two deployments, or two people on one, can see different web UIs. This is the master's _Config-matrix expansion_ lens. **[interpretation]**
- **Transitional code still present.** The page keeps a "dev" sign-in mode (`submitDevSignin` posts to `/signin`, and its `AuthMode` type still includes `dev`), but no server in the repository serves `/signin` and `/v1/web/me` always answers `mode: "portal"`. `WEB_UI_BASE` can still build the bundle for a path prefix, but the web shell maps only root paths to release files **[interpretation]**.

## Contracts

**Release store.** Keys are relative to `<S3_PREFIX>web-ui/` in `S3_BUCKET`, or to the `web-ui` directory under `DATA_DIR`:

| Key                    | Contents                                                                                                             |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `assets/<name>`        | Hashed scripts, styles, fonts and images, with `.gz` siblings; shared by all releases and never deleted by a publish |
| `releases/<id>/<file>` | The release's documents and unhashed files; `index.html` is written last and marks the release complete              |
| `live.json`            | `{"release": "<id>", "deployed": "<id of the last core image's bundle>"}`                                            |

A release id is 64 hex characters: the SHA-256 over one line per bundle file, sorted by path, each line `<path>\0<sha256 of the file>\n`.

**Headers and markers.** Clients send `x-qm-client: browser | desktop | ios`; without it, a CFNetwork user agent is taken as `ios` and anything else as `browser`. Core adds `x-qm-release: <id>` to every cookie-authenticated API answer, and `<meta name="qm-release">` to the document. Hashed assets are served `cache-control: public, max-age=31536000, immutable`; documents `no-cache`.

**Web events stream** (`GET /api/deliveries/events`). Named events: `session_state` (JSON with `threadRef`, `sessionId`, `state`, `at`, and `ui` or `notice` when present), `delivery` (`{threadRef}`), `inbox_item` (`{loopId, itemId, op}`), `session_state_resync` and `inbox_resync` (refetch everything), and `ping` every 15 seconds.

**Run event stream** (`GET /api/runs/:id/events`). JSON frames with `type`: `RUN_STARTED`, then `CUSTOM` frames named `delta` (`offset`, `delta`, `startOffset`), `reasoning` (`step`, `index`, `offset`, `delta`) and `run` (a full run snapshot), then `RUN_FINISHED`.

**`WEB_UI_ANALYTICS`.** A JSON object with `module` (a same-origin path or an HTTPS URL of an ES module), optional `connect` (a list of HTTPS origins the module may call) and optional `options`. The module must export `createAnalytics({ org, user, options })`, returning an object with optional `page`, `track` and `stop` methods. QM ships no analytics vendor.

**`SENTRY_BROWSER_DSN`.** A public HTTPS DSN with no secret key, for example `https://public@sentry.example.com/1`.

**`WEB_UI_SUGGESTED_ACTIVITIES`.** A JSON array of at most 12 objects and 20,000 characters, each with a unique `id` (lowercase letters, digits and hyphens, up to 64), `title` (up to 65), `prompt` (up to 1,200) and `icon` (one emoji or a built-in icon name).

**Desktop bridge.** Inside the desktop app the page sees `window.qmDesktop` with `platform`, `openBrowser(url)` and `computer.call(args, clientId, deadline)` / `computer.stop(clientId)`. The helper's wire protocol is in `desktop/desk/PROTOCOL.md`. Desktop and iOS sign in through `/auth/desktop` and `/auth/desktop/redeem` ([scopes](./scopes.md)).
