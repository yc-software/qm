# Security: postures, approvals, screening and egress

_Verified against `main` at eb148f69d (2026-11-24). Statements were read in the code at that commit unless marked **[interpretation]**._

## In one paragraph

This area is the policy layer around a turn. It decides what the agent may do without asking, when it must stop for a person, how text written by someone else is checked before the model reads it, which hosts a sandbox may reach, and what is written down. Each turn starts by resolving a few settings for its scope: a _security posture_, a _sharing posture_, a _command policy_, an _egress policy_ and the allowed _approval grant modes_. Three gates then use them. Shell commands are matched against the command policy, and a matching rule can allow, deny or require approval. A tool call can require approval because the tool declares it or because the posture is Strict. Content from outside (tool output, attachments, messages the person did not type) is sent to a classifier, but only if the deployment turns _content screening_ on. When a gate needs a person, the turn does not fail: core stores a _pending approval_, shows a card to the person who asked, and carries on when they answer. Separately, a sandbox's outbound traffic passes an egress proxy that checks every destination against the turn's egress policy, if the sandbox backend has such a proxy. Approval answers, classifier verdicts, policy changes and proxy decisions are appended to audit tables in Postgres. All of it is defence in depth, not a boundary: [`SECURITY.md`](../../SECURITY.md) holds the threat model and the known limitations, and this document does not restate them.

## One gated command and one screened result, traced end to end

The example: Acme runs one deployment with the default posture, Auto. An Acme admin has saved one org-wide command-policy rule: `{ "pattern": "\\brm\\s+-rf\\b", "decision": "require_approval", "reason": "recursive delete" }`. Ada, in her web DM, asks the agent to clear a build directory and then summarise `https://example.com/changelog`.

1. **Resolve the policy.** `createResolutionService().resolve` in `src/resolution/resolution-service.ts` builds the turn's `Resolution` (`src/types.ts`). It joins the org and scope command policies (`composePolicy`), reads the posture through `getSecurityPostureDurable` in `src/resolution/config-store.ts` (which applies `composeSecurityPosture`), turns posture plus the deployment's screening mode into a `ResolvedSecurityPolicy` (`resolveSecurityPolicy` in `src/security/security-posture.ts`), and computes the egress policy for everyone in the conversation (`audienceEgressFloor` and `audienceDeniedFloor` in `src/resolution/audience-floor.ts`). For Ada this gives posture `auto`, screening `off`, one command rule and no egress rules.
2. **Screen what came in.** `screenInboundInput` in `src/core/orchestrator/security-screen.ts` does nothing while screening is `off`. When it is on, Ada's own typed words are still not screened: `wordsToScreen` in `src/core/orchestrator/intake.ts` returns text only for another person's words, a message from another session, or an automation payload. What gets screened is what others wrote: overheard channel messages, attachments, the conversation header.
   - _Cron, webhook or monitor fire:_ the payload carried in `origin.screenData` is screened, labelled with the surface name.
3. **Load standing approvals.** `createApprovalLedger` in `src/core/orchestrator/approvals.ts` reads Ada's rows from the `approval_grants` table and builds a per-turn counter of remaining uses per _approval key_. A grant whose mode an admin has since disabled is skipped.
4. **Mint the egress token.** `mintTurnCapabilities` in `src/core/orchestrator/capability-tokens.ts` signs a capability token for audience `egress-proxy` whose `egress` claim is the policy from step 1. `egressClaimAllowingControlPlane` adds core's own host so the sandbox can still call back. Under Auto the claim also sets `denyPrivateNetworks`.
5. **The command is checked.** The agent calls `execute` with `rm -rf build`. Inside `createToolContext` (`src/tools/primitives.ts`), `authorizeExecution` calls `evaluateCommandWithLayer` in `src/policy/command-policy.ts`. The command is parsed as bash and rendered to a _scannable_ text (`scannableCommand`); rules are tried in order and the first match wins. Here the result is `require_approval`. The ledger has no use for this rule, so the function throws `NeedsApproval`. A `deny` rule would throw `CommandDenied` instead: the tool returns `[denied by policy]` and the turn continues without the command.
6. **The turn pauses.** The `execute` tool catches the error; `blockOnApproval` in `createToolKit` (`src/agent/agent-tools/kit.ts`) adds a pending approval to the turn and returns a tool result that ends the model loop.
7. **The approval is stored.** `selectTurnResult` in `src/core/orchestrator/settle.ts` derives a stable id (`commandApprovalId` in `src/core/approval-id.ts`), asks a model for a one-line summary, and writes a `PendingApprovalRecord` to the `approvals` table. The record holds a replayable copy of Ada's request. The turn result has status `pending_approval`.
8. **The card reaches Ada.** The web UI gets the pending approval in the turn result (`pendingApprovals`) and from `GET /v1/approvals/pending`. For Slack and generic chat, `createApprovalStore().put` in `src/surfaces/approval-store.ts` enqueues a delivery to the requester (in Slack, their DM) with buttons from `approvalButtons` in `src/surfaces/approval-cards.ts`: Allow once, Allow session, Allow always, Deny. One sweeper retries card delivery every 30 seconds; another expires unanswered cards after 60 minutes (`expireStaleApprovals` in `src/core/approval-requester.ts`).
   - _Cron fire:_ the request has no surface route, so the store's automation route sends the card to the person the fire runs as, in generic chat or Slack, or leaves it to the web UI when the session lives there.
   - _Bot or system requester:_ nobody can approve, so `unavailableApprovalRefusal` refuses the step and audits `command_approval.unavailable`.
9. **Ada clicks Allow once.** `POST /v1/web/approvals/:requestId` (`src/api/routes/web-turns.ts`) replays the stored request as a new turn carrying `approval: { requestId, approved: true, scope: "once" }`. A Slack click does the same from `src/slack/approvals.ts`. Both paths take a signed-in person, not the agent's capability token, so the agent cannot answer its own card.
10. **The decision is applied.** `applyTurnApprovals` (`src/core/orchestrator/approvals.ts`) checks that the record exists, belongs to this session and was requested by the person clicking (`samePerson`). It claims the record with an atomic `take`, so a second click loses. It appends an `ElicitationResponse` item to the session log, adds one use for the rule's key to the ledger and audits `command_approval.once`. Allow session and Allow always also write a `CommandApprovalGrant` row.
11. **The command runs.** The model is told the operation was approved and issues `rm -rf build` again; this time the ledger has a use and `authorizeExecution` lets it through.
    - _Connector tools differ:_ a tool that declares `needsApproval` gets a key bound to its exact arguments (`toolCallApprovalKey`), the record stores the call itself, and on approval core runs that stored call and records the result; the model does not repeat it. If Ada's run is still alive the decision is steered into it (`resolveLiveApproval`) instead of starting a new turn. These cards offer Allow once only.
12. **The page request leaves the sandbox.** The agent runs `curl https://example.com/changelog`. On a backend with an egress proxy, the command's environment points `HTTPS_PROXY` at the proxy with the token from step 4 as the proxy password (`forceThroughProxyEnv` in `src/sandbox/sandbox-env.ts`). Envoy asks the decision service built by `buildEgressAuthzServer` (`src/egress-authz-main.ts`), which verifies the token, applies `egressDecision` (`src/resolution/egress-policy.ts`), resolves the host, rejects loopback, link-local and cloud-metadata addresses always and private addresses under Auto, and records the decision in `egress_events`.
    - _No egress proxy:_ nothing checks the destination. For backends that could use the proxy, core logs a warning at start and continues.
13. **The page text is classified.** Every tool result passes `recordResult` (built by `createRecorder` in `src/agent/agent-tools/record.ts`). `toolResultProvenance` labels `execute` output `external`.
    - _Screening `off` (Acme's default):_ no screen function is installed. The model reads the text as it is.
    - _`observe`:_ `createToolResultScreen` cuts the text into chunks; `createSecurityClassifier` starts classification in the background and answers allow at once. The verdict lands in the audit log as `security_screen.classify` with status `allow` or `would_block`.
    - _`enforce`:_ classification is awaited. A flagged result is replaced with a quarantine notice, audited as `security_posture.tool_result_quarantine`, and a release card (Allow once only) shows Ada the blocked text. If she releases it, that exact text is appended as a hidden message labelled untrusted data. If the classifier fails or times out, the result passes with a `[NOT security-screened …]` prefix and an audit row.

**Other postures.** Under Strict, every tool call pauses with "strict posture: this tool call requires human approval" unless a grant covers the tool; `finish_silently`, `tool_search` and `withdraw_approval` are exempt, and `mcp_call` only dispatches to a gated target. Strict turns also get no self-API handle and no sandbox model-gateway token. Under Dangerous there is no posture gate, no private-network denial, and screening never goes above `observe`. Command-policy rules and connector-declared approvals apply under all three.

## The parts

The gates are called from `handleTurn` in `src/core/orchestrator.ts`, which belongs to [turns](./turns.md).

### `src/security`

**Job.** Define postures and what each implies; hold the classifier prompt, chunking and verdict parsing; talk to an external classifier; mask secret values in text.

**Key idea.** A posture is a small lookup table (`POSTURE_POLICIES`). Outside it, three places test the posture by name, all for Strict. `resolveSecurityPolicy` is the only place posture and screening mode meet.

**Surprising.** (1) Postures are not a strict ladder. Auto is the only posture that denies private networks; Strict does not. (2) Screening is not a posture feature. It is a deployment setting, off by default, and posture only caps it under Dangerous. (3) `secret-masking.ts` is unrelated to screening: `createSecretValueMasker` replaces environment values of eight characters or more (raw, URL-encoded and base64 forms) with `<redacted:NAME>` in command text and errors.

### `src/policy/command-policy.ts`

**Job.** Decide allow, deny or require approval for one shell command.

**Key idea.** Rules never see the raw string. The command is parsed with tree-sitter's bash grammar; quoted text that is not a plain word is blanked, comments are dropped, and text that will itself be executed is pulled out and scanned too: `bash -c` and `eval` arguments, heredocs and `echo` output fed to a shell, SQL passed to clients such as `psql -c`, commands behind wrappers such as `sudo` or `xargs`. Rules are case-insensitive regexes matched against that text.

**Surprising.** (1) It ships with no rules: `defaultOrgPolicy` is an empty denylist, so every command is allowed until an admin or a deployment tool descriptor adds a rule. (2) Org rules come first and the first match wins, so a scope cannot override an org rule; the mode is `allowlist` if the org says so, otherwise the scope's. (3) Deployment-layer rules are tried last and skipped in allowlist mode; the admin simulate route does not evaluate them. (4) Rules apply in every posture, Dangerous included. (5) Patterns pass `compileSafeRegex`: no lookarounds or backreferences.

### Approvals

`src/core/orchestrator/approvals.ts` holds the ledger and decisions; `src/core/approval-id.ts` the ids and keys; `src/core/approval-requester.ts` refusal, expiry and undeliverable cards; `src/surfaces/approval-store.ts` and `approval-cards.ts` delivery and buttons; `src/credentials/keychain-approval.ts` the separate credential ask.

**Job.** Turn "this step needs a person" into a durable record, get it in front of the right person, and apply their answer exactly once.

**Key idea.** An approval is resolved by a new turn, not a callback. The record stores the original request; the click replays it with a decision attached, and the ledger then lets the step through. Authority comes from the request's author: only the person whose request raised the card can answer it.

**Surprising.** (1) Two resume styles coexist. Command-policy and Strict approvals grant uses of a key and the model re-issues the step. Connector-tool approvals store the exact call and core runs it. (2) A command approval covers the rule, not the exact text: Allow once lets the next command matching that rule through, and Allow always exempts the rule pattern for that person. A Strict approval likewise covers the tool, not its arguments. On a flagged-input card, a standing answer exempts later flagged input from that surface. (3) Quarantine releases and exact-call approvals are once only. (4) Disabling a grant mode also suspends existing grants of that mode. (5) An unanswered card expires after 60 minutes; the session gets a hidden note saying so. (6) A decision recorded on a crashed attempt is recovered from the session log on retry (`approvedCallsOnEarlierAttempt`).

### `src/core/orchestrator/security-screen.ts`

**Job.** Run the classifier wherever outside content enters a turn, and act on the verdict.

**Key idea.** One classifier closure (`createSecurityClassifier`) used at seven entry points: inbound request data, text documents, files saved to the inbox, skills carried from another scope, tool results (which include messages from other sessions), mid-turn messages (`screenSecuritySteer` in `orchestrator.ts`) and a refreshed web inbox header (`intake.ts`). In `observe` it never blocks or waits; in `enforce` it waits and can hold the content.

**Surprising.** (1) Enforce fails open: if the classifier is missing, errors or times out, content passes with a "not screened" notice and an audit row. Mid-turn messages are stricter and are withheld when there is no classifier, the person is over budget, the text is too long or another check is in flight. (2) Inbound content too long to screen (over 200,000 characters) does not pass: a message waits for a once-only approval, and a file or document is withheld with a notice. (3) A flagged inbound request becomes a pending approval of kind `input` before the turn starts; approving replays it without screening again. (4) The model classifier's calls are recorded as model requests and count toward the budget, except in observe.

### Egress policy and the proxy

`src/resolution/egress-policy.ts` parses and evaluates rules; `src/resolution/audience-floor.ts` composes them; `src/egress-authz-main.ts` is the decision service; `deploy/egress-proxy` is the Envoy image; `src/util/network.ts` holds the address lists.

**Job.** Say which hosts a turn's sandbox may reach, and enforce it outside the sandbox.

**Key idea.** The policy travels inside the signed token. The proxy holds no state and never asks core: it verifies the token, reads the `egress` claim, checks the name, resolves it, checks the addresses, and tells Envoy which address to dial.

**Surprising.** (1) Enforcement exists only where the sandbox backend routes traffic through the proxy. Without `EGRESS_PROXY_URL`, or on the `aws`, `local`, `agent37` and `superserve` backends, saved egress rules have no effect on sandboxes. The admin API reports this per scope as `egressEnforcement`. (2) Allow lists do not only tighten. A person's list is the union of the org, conversation, personal and team lists; the turn gets the intersection across the audience. Deny lists are the union. (3) Loopback, link-local and metadata addresses are refused whatever the policy says. (4) A request with no token gets 407 unless `EGRESS_TOKENLESS=open`; an invalid token is denied everything. (5) Core's own outbound calls to URLs that admins or other outside parties supply use a second guard, `publicFetch` in `src/util/network.ts`, which refuses private addresses unless the origin is listed in `PRIVATE_NETWORK_ALLOWED_ORIGINS`. (6) The `egress` list in a deployment tool descriptor is checked by the CLI and never enforced at runtime.

### `src/decisions`

**Job.** Let an org admin attach classifier-backed rules to two points of a turn. At `turn_start` a rule can keep, switch runtime or switch persona. At `turn_end` it can keep the reply or send it back with a message.

**Key idea.** A rule is a question with two to eight described options; a provider returns a probability per option; `settle` picks the most likely and falls back to the rule's `onError` option on any failure. Observe rules run in the background and only audit; enforce rules are awaited for at most five seconds.

**Surprising.** (1) Despite sitting next to screening, decision rules do not block content: the `user_input`, `tool_response` and `goal_check` hooks are declared and rejected as "not available yet". (2) Rules are org-wide only. (3) The reply check is skipped for automation and session turns. Runtime routing is described in [models](./models.md), personas in [context](./context.md).

### `src/audit` and the admin read routes

**Job.** One interface, `AuditLog`, implemented by `createPostgresAuditLog` in `src/admin/postgres-audit-log.ts`. Admins read it through `GET /v1/admin/audit`, flagged screening events through `GET /v1/admin/security/flags` (`src/api/routes/admin/security.ts`), and proxy plus credential-broker traffic through `GET /v1/admin/egress`.

**Key idea.** `record` never blocks the action it describes: the insert is not awaited and a failed insert is reported, not thrown.

**Surprising.** Audit records an action; it does not prevent one. Reading the audit log is itself audited.

### `src/ratelimit`

Refuses a turn before it starts when spend is over a cap. The two caps, pricing and spend recording belong to [models](./models.md). The directory holds no request rate limiter.

### Settings: `src/config.ts` and `src/resolution/config-store.ts`

**Job.** Environment gives deployment-wide defaults; `ScopedConfigStore` holds per-scope rows an admin edits through `PUT /v1/admin/scopes/<scopeId>/<resource>` (resources `security-posture`, `sharing-posture`, `command-policy`, `egress`, `approval-grant-modes`, `spend-limit`, `decisions`).

**Key idea.** Each setting composes from the org down to the scope by its own hand-written rule: a floor for security posture (a scope can only tighten), a ceiling for sharing posture (Isolated wins at any level), AND for grant modes, ordered concatenation for command rules, union then intersection for egress.

**Surprising.** (1) A stored org row beats the environment default. (2) A scope's security posture is clamped to the org floor when saved and again when read. (3) Sharing posture reads three rows: the org, the speaker's personal scope and the conversation's scope. A turn from outside the organization is always Isolated.

## Where the complexity lives

- **Screening sites × modes × failure rules.** Seven entry points, three modes, and per-site rules for chunk size, batching, what counts as unscreenable and whether failure passes or blocks. The master's Wall of shame records the earlier growth of screening settings under _Config-matrix expansion_; the settings are now one mode, the sites are not one function.
- **Approval raising sites.** A pending approval is raised from five places (the tool gate `withToolApprovalGate`, `blockOnApproval`, the quarantine paths in `createToolResultScreen` and `record.ts`, and flagged inbound input) and written to the store from three (`selectTurnResult`, the `NeedsApproval` catch at the end of `handleTurn`, and the flagged-input branch). The Wall of shame's _God files_ entry on the orchestrator names approval handling among what it absorbed.
- **Two resume styles for one concept.** Key-and-re-issue (commands, Strict, flagged input) and stored-call-run-by-core (connector tools), with a third route when the run is still alive (`resolveLiveApproval`).
- **Parallel mechanisms.**

  | Job                          | Mechanism A                                               | Mechanism B                                                                  |
  | ---------------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------- |
  | Ask a person before acting   | Pending approval (`approvals`)                            | Keychain ask (`keychain_asks`), own cards and decide path                    |
  | Classify text with a model   | Content screening                                         | Decision rules, with their own providers, modes and audit action             |
  | Cap spend                    | Budget (`budget_spend`, environment)                      | Spend limit (`spend_limit_configs`, admin)                                   |
  | Stop unwanted outbound calls | Egress proxy with per-turn token                          | `publicFetch` guard inside core                                              |
  | Hide secrets in text         | `createSecretValueMasker`, `createExactSecretValueMasker` | `redactSecrets` in the chassis plugin, regexes in `redactCommand`            |
  | Store an audit trail         | `audit_log`                                               | `egress_events`, plus credential-usage rows merged by the egress admin route |

- **Hand-written composition per setting.** Five settings, five rules (see Settings above), each coded separately in `config-store.ts`, `command-policy.ts` and `audience-floor.ts`.
- **Cut-off card text.** `redactCommand` both redacts and cuts to 500 characters, and exact-call cards are built from it. Recorded in the Wall of shame under _Arbitrary limits_.
- **Interfaces with one implementation.** `AuditLog`, `DecisionStore`, `DecisionBackend`, `BudgetTracker` and `SecurityScreener` each have one implementation under `src`.
- **Transitional: standing quarantine grants.** New release cards are once only, but a stored grant keyed `quarantine:<tool>` still skips screening for that tool (`quarantineReleaseKey`). That path audits `security_posture.tool_result_released`; the current paths audit `security_posture.tool_result_release`.
- **Transitional: the attended/unattended split.** None of this area's own files read a presence flag: approvals key on the requester's identity and on bot or system actors. The split the master's Background work paragraph says is being removed still surrounds them: `mintTurnCapabilities` puts `liveAuthor` and `triggered` claims on the control token, and callers such as `src/api/control-service.ts` refuse webhook registration and edits outright instead of raising a card. The call sites are listed in [background-work](./background-work.md) and [scopes](./scopes.md). Do not extend them.

## Contracts

**Admin resources.** `PUT /v1/admin/scopes/<scopeId>/<resource>` with these bodies:

- `security-posture`: `{ "posture": "dangerous" | "auto" | "strict" }`
- `sharing-posture`: `{ "posture": "isolated" | "open" }` or `{ "inherit": true }`
- `approval-grant-modes`: `{ "session": boolean, "always": boolean }`
- `command-policy`: `{ "mode": "denylist" | "allowlist", "rules": [{ "pattern": string, "decision": "allow" | "deny" | "require_approval", "reason"?: string }] }`. Patterns are case-insensitive regexes of at most 256 characters.
- `egress`: `{ "allowedHosts": string[], "deniedHosts": string[] }`. Bare host names only: no scheme, wildcard, port or path, and no host in both lists.
- `command-policy-simulate`: `{ "command": string, "policy"?: … }` returns the decision, the matched text and which rule matched, without saving.

**Deployment configuration.** In `qm.config.jsonc`: `"securityScreen": { "mode": "off" | "observe" | "enforce", "classifier": "model" | "proxy", "provider": string, "endpoint": string }`. `provider` (a lowercase DNS label) and `endpoint` (an HTTPS URL) are required with `proxy` and rejected otherwise; the token goes in `secretEnv.core.SECURITY_SCREEN_PROXY_TOKEN`. The CLI turns this into the `SECURITY_SCREEN*` variables and refuses hand-set copies of them. The older keys `backend`, `allPostures` and `rollout` are refused, except that `{ "backend": "off" }` alone still loads as mode `off` with a warning.

**External classifier.** Core sends `POST <endpoint>` with headers `content-type: application/json` and `x-api-key: <token>`, and body `{ "text": string, "hook": "user_input" | "tool_response", "metadata": { "surface"?, "origin"?, "request"?, "qm": { "request_id", "input_index", "chunk_index", "chunk_count" } } }`. The same coordinates are repeated under a key named after the provider. A payload is at most 16,000 characters and is sent in chunks of at most 1,600 that overlap by 256, two requests in flight at a time. The reply must be JSON `{ "score": number, "threshold": number, "primary_outcome"?: string }` with both numbers between 0 and 1; `score >= threshold` flags the chunk. A 429 is retried up to three times, honouring `Retry-After`. Redirects, other error statuses and replies over 64 KB count as failures.

**Screening audit record.** Each classification writes one `audit_log` row with action `security_screen.classify`, resource the classifier's provider name (or `model`), and status `allow`, `block`, `would_block` or `error`. The detail is JSON with `hook`, `mode`, `sources`, `requestId`, `attempts`, and when known `surface`, `origin`, `sessionId`, `runId`, `thread`, `score`, `threshold`, `outcome`. It never holds the screened text.

**Egress proxy.** Sandboxes use it as an HTTP proxy on port 48080 and present the turn's token as `Proxy-Authorization`, either `Bearer <token>` or `Basic` with the token as password. For each connection Envoy calls the decision service on `127.0.0.1:48081` with `GET /check` and the headers `x-egress-authority`, `x-egress-scheme` and the `proxy-authorization` value. It answers 200 with `x-egress-upstream-address: <ip>:<port>`, 403, or 407. If the decision service is down, nothing leaves. The service reads `CAPABILITY_SECRET`, `AUTHZ_PORT`, `EGRESS_TOKENLESS`, `CORE_API_URL`, `CORE_SIGNING_SECRET` and `DATABASE_URL`. The container needs `NET_ADMIN` to install its own block on the cloud metadata address; without it the proxy logs a warning and keeps serving.

**Egress audit relay.** The proxy posts batches to core at `POST /v1/egress-audit`, signed with the core signing secret: `{ "records": [{ "host", "verdict", "scopeLabel"?, "principalId"?, "tenant"?, "port"?, "via"?, "peerIp"? }] }`, at most 500 per request. Core answers `{ "accepted", "rejected" }`. A record is allowed only when `verdict` is `ok`.

**Decision providers.** A provider names one of three wire protocols, `chat-completions`, `decisions` or `systemone`, each a `POST` to a fixed path under the provider's base URL; request and response shapes are the `PROTOCOLS` table in `src/decisions/providers.ts`.
