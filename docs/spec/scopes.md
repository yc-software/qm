# Identity, scopes and access

_Verified against `main` at bd371980c (2026-11-24): statements were read in the code at c6056de14 and re-read where later commits changed it, unless marked **[interpretation]**._

## In one paragraph

This area answers three questions on every request: who is asking, what do they own, and what else may they touch. **Who:** a browser signs in at the front door, a chat surface vouches for the people in a conversation, and a sandbox presents a token minted for its turn. Each ends as a _principal_: an id string plus a type, `internal` or `guest`. One person can arrive under several ids (an email, a Slack user id, a subject from a trusted identity provider); a _principal link_ folds them into one canonical id. **What they own:** every durable thing (memory, files, skills, crons, apps, settings) belongs to a _scope_, a string such as `personal:ada@example.com` or `channel:C123`. A conversation's scope is computed from where it takes place. **What else:** a turn writes to its own scope and reads the organization scope and its team scopes. Three things reach further: a _grant_ (a row saying scope A lets scope B read or write one resource), an _open sharing posture_ (a setting that lets a person's rooms and personal scope read each other), and an _admin role_ (a row that lets an `org_admin` read and change the settings of any scope, and an `owner` those of the organization scope). These rows are kept per tenant, and a tenant is one organization.

## One person, traced end to end

Ada works at Acme. Acme runs a [package deployment](../SPEC.md#deployment-shapes) scaffolded by `qm init` with the services `core`, `slack` and `auth`, and `ORG_ID=acme`. Ada signs in on the web with her email, turns out to be a second person in Slack, is linked, shares a skill with a channel, and an org admin, Bo, reads a setting.

1. **The front door.** Core serves sign-in and the web UI itself. `startFrontDoor` (`src/web/front-door.ts`) starts the portal (`plugins/portal/src/index.ts`) inside the core process on `PUBLIC_PORT`. Ada has no session, so the portal's `handle` sends her to `/auth/login`. `authLogin` puts a state, a nonce and a PKCE verifier in a ten-minute signed cookie and redirects her to `OIDC_AUTH_ENDPOINT`.
2. **The email broker.** Because `auth` is a listed service, the CLI (`brokerWiring` in `cli/src/services.ts`) pointed the `OIDC_*` client id, issuer and endpoints at the built-in broker (`plugins/auth`). The portal starts it on loopback when `AUTH_EMBEDDED=1` and exposes it only under `/idp`. `createAuthHandler` (`plugins/auth/src/server.ts`) asks for an email, checks that the address is admitted (its own allow-list, else core's `GET /v1/auth/broker/email-allowed`), mails a one-time link, and then answers the portal's code exchange like any OpenID Connect provider. Links and codes are single-use because core records each one in `source_auth_replay` (`claimBrokerNonce` in `src/api/routes/auth-broker.ts`).
   - _External provider instead:_ drop `auth` and set `OIDC_*` to any OpenID Connect provider. Steps 3 to 5 do not change. With nothing set, the portal's defaults are Slack's OpenID Connect endpoints.
3. **The callback.** `authCallback` exchanges the code and verifies the id token (`verifyIdToken` in `plugins/portal/src/oidc.ts`); `finishSignIn` then calls `resolvePrincipal`, which chooses the principal id: the verified email (`OIDC_PRINCIPAL_CLAIM=email`, the default) or the provider's subject. Ada becomes `ada@example.com`. With the broker wired, or when the portal's own allow-list (`OIDC_ALLOWED_EMAILS`, `OIDC_ALLOWED_EMAIL_DOMAIN`) would refuse the email, core is asked once more (`admission` in `auth-broker.ts`): a manually deactivated person is refused, and a person who holds nothing but a shared app gets a session that can only open apps.
4. **The session.** `setAuthenticatedSession` writes the `portal_session` cookie: `{ sub, org, t?, exp }`, signed with a key derived from `PORTAL_SESSION_SECRET`, seven days by default. `org` is `ORG_ID`. `t` is the tenant that already knows her email; on a first sign-in it is absent and her requests fall back to the boot tenant. No session row is written: the session is only the cookie. When the provider returns a name (the broker does not), sign-in also stores it on her `users` row through `POST /v1/principals/profile`.
   - _[Multi-tenant deployment](../SPEC.md#deployment-shapes):_ the organization is a row in `tenants`, not `ORG_ID`, which is the same in every tenant. The operator configures its own identity provider as the _trusted issuer_ (`PORTAL_TRUSTED_OIDC`). `/auth/trusted/login` runs `createTrustedEntry` (`plugins/portal/src/trusted-entry.ts`) and the principal is `oidc:<sha256 of issuer>:<base64url of subject>`. `settleTrusted` (`plugins/portal/src/tenant-choice.ts`) asks core which tenants know that principal or her verified email. One tenant: she is signed in with `t` set. Several: a chooser page. None: when self-serve is on, core finds or creates the tenant for an organization named in her `orgs` claim and, if she is not yet a user there, grants her an admin role (`selfServeWorkspace`, `provisionSelfServe`); with several organizations she first picks one.
5. **A request.** Her browser calls `GET /api/sessions`. The portal asks core who the cookie's subject is now (`createCanonicalResolver` in `plugins/portal/src/canonical.ts`, cached for a minute) and hands the request to core in the same process. Core first binds a tenant (`withRequestTenant` in `src/api/request-tenant.ts`): the capability token's tenant, else the signed identity's, else the cookie's `t`, else the boot tenant; none is a 401 unless the route marks the tenant optional. Then `browserIdentity` (`src/api/browser-session.ts`) opens the cookie, checks organization, tenant and origin, deletes any identity headers the browser sent, and returns her canonical id. `src/api/server.ts` refuses the request if she is no longer internal or if a `principalId` in the query or body is not hers.
   - _Other callers:_ surfaces and plugins sign the request with `CORE_SIGNING_SECRET` (_source auth_) and name the person in a signed `x-portal-identity` header. A sandbox sends a capability token ([credentials](./credentials.md)).
6. **Slack sees someone else.** Ada messages the bot in Slack. A surface does not send a principal. It sends an _actor assertion_: an external id, a guest flag and a bot flag. `classifyUser` (`src/slack/identity.ts`) uses her email as the id in email mode and her Slack user id in Slack-id mode; with `SLACK_IDENTITY_EMAIL` unset the mode is probed at start, and is Slack-id only when the workspace's members are listed and none of their emails is visible. Acme removed the `SLACK_IDENTITY_EMAIL=1` its scaffold set, and its Slack app cannot read emails, so the id is `U0ADA`. (With the `1` kept, a member whose email Slack does not show is classified as a guest and no turn runs for her.) Turn intake (`turn` in `src/api/app-turn.ts`; see [turns](./turns.md)) calls `resolve` on the identity service (`createIdentityService` in `src/identity/identity-service.ts`) and gets `{ id: "U0ADA", type: "internal" }`. `conversationScope` (`src/resolution/resolution-service.ts`) names her DM's scope `personal:U0ADA`. Her web scope is `personal:ada@example.com`. QM now holds two Adas, each with its own memory, files and credentials.
   - _Email keying:_ had Slack shown emails, both sign-ins would yield `ada@example.com` and no link would be needed.
7. **The link.** Bo calls `POST /v1/admin/principal-links` with `{ principalId: "ada@example.com", canonicalId: "U0ADA", evidence: "confirmed in person" }`. `createPrincipalLink` (`src/api/routes/admin/principal-links.ts`) insists that the directory member stays canonical and that the link hands nobody an admin role. `link` (`createPrincipalLinkService` in `src/identity/principal-links.ts`) keeps links flat and refuses system actors. `linkInTransaction` (`src/identity/user-store.ts`) refuses bots, adds a `user_links` row and merges the two `users` rows. From then on `canonicalPerson("ada@example.com")` returns `U0ADA`, so her next web request (step 5) acts as `U0ADA`. Rows that already name either id (scopes, sessions, credentials) are not rewritten: ownership checks compare ids with `samePerson`, which treats both as her.
   - _Self-service:_ the Connect Slack flow (`src/api/routes/composio.ts`, needs the Composio integration) proves the Slack account through an OAuth connection and links the other way round: the web principal stays canonical.
8. **A share is a grant.** Ada owns a skill in her personal scope and shares it with the channel `#launch`: `POST /v1/shares/skill/<id>` with `{ scope: "channel:C123", access: "view" }`. `changeShares` (`src/api/routes/sharing.ts`) calls `shareArtifact` (`src/api/control-service.ts`), which finds the skill's home scope, checks that Ada manages it and that she belongs to the channel (a current member, or any internal person when the channel is public), then calls `grant` on the ACL store (`createAclStore` in `src/acl/acl-store.ts`). That repeats the manager check and inserts one `acl_grants` row: owner `personal:U0ADA`, resource `skill:<id>`, grantee `channel:C123`, permission `read`. An audit event `grant` is recorded.
9. **The grant is used.** On the next turn in `#launch`, `resolve` (`createResolutionService`) builds the turn's `Resolution`, and `resolveTurnContext` (`src/resolution/turn-context.ts`) lists skills through `sharedOfKindForAudience`. A grant counts only if someone in the audience is entitled to the grantee scope and everyone in it is entitled to the grantee or the owner scope. The test is on the _audience_ (everyone the surface says is in the conversation), not on the speaker alone.
10. **An admin reads a setting.** Bo is an org admin because of an `admin_grants` row `(bo@example.com, org:acme, org_admin)`, seeded from `ADMIN_GRANTS` at first boot. His browser asks `GET /api/admin/scopes/channel:C123`, an alias (`API_ALIASES` in `src/api/browser-session.ts`) for `/v1/admin/scopes/:scope`. `getScopeConfig` (`src/api/routes/admin/scope-config.ts`) calls `authorizeAdmin` (`src/api/routes/shared.ts`): canonical id, still active, role from `adminStatusFromGrants` (`src/admin/admin-service.ts`). It then reads each resource in `ADMIN_RESOURCES` (`src/api/routes/admin-resources.ts`), most of them from the config store (`createConfigStore` in `src/resolution/config-store.ts`), which returns the security posture, the sharing posture, the approval modes and the external-Slack-participants flag combined with the organization's value and the rest uncombined (the scope's own stored value, an org-wide value, or nothing for an org-only switch read on another scope), and records the audit event `config.read`.

- _Through the agent:_ a turn may call admin routes with its own token; `capabilityAdminDenied` (`src/api/server.ts`) decides. A read that returns private content is refused when the turn runs outside a personal scope, unless the sharing posture there is open or, on routes marked `unless-org-scope` such as this one, the target is the org scope.

## The parts

### `src/types.ts`: principals and scope ids

**Job.** Define `Principal`, `ScopeId`, the scope kinds and the helpers that build and parse them (`scopeId`, `personalScope`, `parseScopeId`). **Key idea.** A scope is only a string; nothing has to create it. **Surprising.** A scope may act as itself: `scopeActor` returns `system:<scope>` and `actsAsScope` lets that id pass membership checks. `isSystemActor` is a prefix test on `system:`.

### `src/identity`: who is active, and which ids are one person

**Job.** Classify an id as internal or guest (`identity-service.ts`), keep the list of people and their sign-ins (`user-store.ts`), and create and remove links (`principal-links.ts`). About two fifths of the directory is migrations in `user-store.ts` and `user-tenancy.ts`. **Key idea.** `classify` never looks a person up. An id is internal unless something says otherwise: the surface's guest flag, a deactivation, or an expired invitation. Admission happens earlier, at sign-in or in the surface. **Surprising.** (1) Deactivations, invitations and links are cached per tenant for ten seconds, so a change can take that long to reach the other core instances. (2) Links are flat and have a direction: the admin route keeps the directory member canonical, the self-service flow keeps the web principal canonical. (3) A link merges the two `users` rows; deleting the link does not split them again. Deactivation is looked up by canonical id, so deactivating one sign-in deactivates every linked one. (4) A turn from a linked sign-in is refused at turn intake when the surface flags the speaker as a bot, or when that sign-in or its canonical id is a bot or app, until an admin deletes the link; each directory sync of members moves a bot sign-in that was linked onto another user to an app user of its own (`applyDirectoryBots`).

### `src/directory`: the roster and the same-person tests

**Job.** Store what the chat surface reports (`postgres-directory-store.ts`, `directory-sync.ts`) and provide the id comparisons everything else uses (`person.ts`). **Key idea.** Never compare principal ids with `===`. `samePerson`, `personKey` and `canonicalPerson` fold email case and follow links. **Surprising.** (1) `person.ts` reads links through a module-level resolver installed once by `installPrincipalLinks`; the functions look pure but depend on the bound tenant. (2) A directory row pairs a principal id with a Slack id, which is a second, implicit link: `samePersonInDirectory` and the membership checks consult it, `samePerson` does not. (3) The directory is whatever a surface last pushed: the built-in Slack surface pushes in process through `pushDirectory` (`src/api/slack-core-client.ts`), and `POST /v1/directory` takes the same push over HTTP. With no chat surface it is empty. `withSignInMembers` (`sign-in-members.ts`) answers a name lookup the stored roster cannot match from configured emails, invited people and past participants. (4) `channelMembership` and `groupMembership` answers are three-valued: `true`, `false`, or `undefined` for "no roster known" (and for a non-member of a public channel); `channelMember` and `groupMember` answer only `true` or `false`.

### `src/auth`: proving which service is calling

**Job.** Verify request signatures (`source-auth.ts`), sign and verify small JSON payloads (`signed-token.ts`), carry a person's identity between trusted services (`portal-identity.ts`), and hold the email broker's remembered sessions (`broker-sessions.ts`). Capability tokens also live here; see [credentials](./credentials.md). **Key idea.** Three different secrets prove three different things: `CORE_SIGNING_SECRET` that a service is trusted, `PORTAL_IDENTITY_SECRET` which person it speaks for, `CAPABILITY_SECRET` what one turn may do. **Surprising.** (1) The last two fall back to `CORE_SIGNING_SECRET` when unset; `createServer` (`src/api/server.ts`) refuses that in production. (2) A signed non-GET request is single-use, so callers add a nonce to the query. (3) `verifySignedPayload` still accepts an older two-part token format.

### `src/acl`: grants

**Job.** Store grants and answer "which shared resources may this audience use". **Key idea.** `audienceReaches`: a grant applies to a conversation only when everyone present is entitled to it. **Surprising.** (1) Only someone who manages the owner scope may grant; holding a grant does not let you share onward. For org, team and persona owner scopes the store itself checks nothing, and the caller is the gate: `shareArtifact` checks `mayShare` (`src/api/control-service.ts`), while `POST /v1/grants` takes `grantedBy` from a source-authenticated caller and adds no manager check. (2) A file grant must name an enabled Files record owned by the granting scope. (3) Grants to an app (`deployment:<id>`) also decide who may sign in at all: a person whose only access is such a grant gets an app-only session.

### `src/resolution`: what a turn may see

**Job.** Turn a conversation and an actor into a `Resolution` (`resolution-service.ts`), decide scope membership (`scope-membership.ts`), widen the view when sharing is open (`sharing-access.ts`, `turn-context.ts`), and store the per-scope settings in `CONFIG_STORE_TABLES` (`config-store.ts`). The config store is the largest file. **Key idea.** The scope follows from the conversation: a DM is `personal:<actor>`, a group chat `group:<ref>`, a channel `channel:<ref>`. Settings are combined organization first, then scope. **Surprising.** (1) Membership rules differ by verb. `createCanReadScope` lets any internal person read a public channel's scope; `createCanWriteScope` needs current membership; `createCanManageScope` covers only personal, persona, group and private-channel scopes. (2) The combining rule differs by setting and is written by hand each time: the security posture can only be tightened by a scope, the sharing posture is `isolated` if any of organization, person or room says so. (3) A conversation with an outside audience resolves with no stored instructions, no read-only scopes, no grants and sharing forced to `isolated`; how a surface marks an audience as outside is in [surfaces](./surfaces.md). (4) Persona scopes and their roles are covered in [context](./context.md); security postures, command policy and egress in [security](./security.md).

### `src/teams` and `src/projects`: two kinds of managed group

**Job.** Teams give a set of people a shared `team:<id>` scope. Projects give a web group chat a roster. **Key idea.** Both are rosters QM keeps itself instead of reading them from a chat surface. **Surprising.** (1) A project is not a scope kind. It is a `group` scope whose ref starts with `web-project-`, recognised by `isProjectGroupRef`. (2) A project's members are its own list plus the roster of a linked Slack channel, and nobody is a member once the owner is deactivated. (3) Team membership is decided per turn (`teamsForTurn`): a team the speaker is on applies in their own DM, in rooms configured for it, when everyone present is on it, or when sharing is open and the team is not marked `isolatedInOpen`.

### `src/admin`: admin roles

**Job.** Hold admin grants and answer "may this person administer that scope" (`admin-service.ts`, `admin-grant-store.ts`). The directory also holds the audit log and usage sinks; see [security](./security.md). **Key idea.** Two roles, both granted on the org scope. **Surprising.** (1) `ADMIN_GRANTS` only seeds: it is applied only to an empty table, in the boot tenant, checked once per process. (2) The last org admin cannot be revoked. (3) `createGrant` accepts only the scope `org:<ORG_ID>`.

### `src/reach`: addressing someone else

**Job.** Turn "send this to Bo", "to #launch" or "to these people" into a delivery destination (`resolveReachTarget`), checking that the sender may see the target (`isVisible` in `src/directory/visibility.ts`). Delivery itself is in [surfaces](./surfaces.md). **Surprising.** A private channel or group chat is reachable only by a member. A sender refused there whose id has no directory row is told their login may not be linked (`identity_unverified`); an unlinked second identity as in step 6 gets that answer.

### `plugins/portal`: the front door

**Job.** Every browser request enters here: sign-in, session renewal, the tenant chooser, impersonation by admins, and hand-off to core. Nearly half of it is `index.ts`. **Key idea.** Three sign-in modes: an external OpenID Connect provider (what the code does with nothing configured), the built-in email broker (what `qm init` scaffolds), and a trusted issuer that can sit beside either. They all end in one cookie, minted by several entrances: `/auth/callback`, `/auth/trusted/callback`, `/auth/tenant` (after the tenant chooser), `/auth/invite` (invitation link), `/auth/admin-login` (a link printed by `qm admin-login`), `/auth/desktop/redeem` and the app-host hand-off. **Surprising.** (1) It is not a separate service: it runs inside core, and core reads the same cookie again in `browserIdentity`. (2) Admin routes refuse an impersonated session. (3) `bootChecks` refuses to start in production without an identity boundary: an allowed email list, an allowed domain or an expected Slack workspace.

### `plugins/auth`: the built-in email broker

**Job.** Be a minimal OpenID Connect provider for deployments without one: one-time email links and, optionally, passwords. **Key idea.** It holds no state of its own. Single-use claims and remembered sessions live in core's database, reached with source auth. **Surprising.** It refuses to start without an allow-list (`AUTH_ALLOWED_EMAILS` or `AUTH_ALLOWED_EMAIL_DOMAIN`), because otherwise anyone with an inbox could sign in.

### The HTTP routes

**Job.** `src/api/browser-session.ts` authenticates cookie-bearing requests and maps the browser's `/api/…` paths onto `/v1/…` routes. `src/api/routes/auth-broker.ts` serves the portal and broker (admission, tenant lookup, single-use claims, invitations, trusted admin and self-serve). `directory.ts` takes roster pushes and answers the canonical-id lookup. `projects.ts` manages rosters. `sharing.ts` reads and changes grants on files, skills, apps and crons. `session-sharing.ts` makes and serves conversation snapshots. `admin/users.ts`, `admin/principal-links.ts`, `admin/offboard.ts` and `admin/scope-config.ts` are the admin side. `src/api/conversation-write-access.ts` decides whether an actor may speak in a project, a web conversation or a subagent thread; a turn from another surface in any other conversation passes it unchecked. **Surprising.** (1) Offboarding is a plan of steps, previewed by default and run only with `apply`: deactivate and sign out and revoke admin roles; then, unless the acting admin is an `owner`, archive the person's crons, pause their loops, disable their webhooks, revoke their keychain grants, archive their apps and skills, retire their computers and hand over their personas. (2) A session share copies messages and files at creation; later messages never appear and there is no revoke. It stops resolving once its creator is deactivated or loses access to the conversation. (3) Only user messages, the agent's replies (final or posted) and their attachments are copied; reasoning and other tool traffic are never included.

## Where the complexity lives

- **Three ways to say "same person".** Explicit links (`user_links`), the directory row that pairs a principal id with a Slack id, and email keying that makes the ids equal to begin with. `samePerson` follows only the first; `samePersonInDirectory`, `personKeys` and the alias expansion in `scope-membership.ts` each add the second in their own way, while `rosterIds` expands only links. A check that uses `samePerson` where the directory pairing is needed fails only for people whose Slack id and email are paired by a directory row and were never linked.
- **Two organization identifiers.** `ORG_ID` is one value per deployment. It names the org scope, is stamped into every session cookie, project and admin grant, and fills an `org_id` column in the directory tables. In a multi-tenant deployment it is identical for every organization and the tenant id does the separating. Code that treats `ORG_ID` as "which organization" is wrong there. Each tenant's `deployment_identity` row records the `ORG_ID` it was first loaded under, and the config store refuses to load under a different one.
- **Four doors through scope isolation.** Grants, the open sharing posture, admin roles, and the read-only organization and team scopes an internal turn gets. Grants (`acl_grants`), admin roles (`admin_grants`), postures (`sharing_postures`) and team rosters (`team_members`) are all rows, but only a grant row names the resource it opens; a read through an open posture and an admin's read of a scope's settings each leave an audit event (`sharing.cross_context_read`, `config.read`).
- **Verbs × scope kinds.** Read, write, manage and "manages this artifact's home" are four predicates in `scope-membership.ts`, each with its own branch per scope kind and per channel privacy. `scopeMembershipSnapshot` loads the same facts in one batch for list endpoints; the master's Wall of shame records the per-row form of these reads under Performance.
- **One setting, three accessors.** Fewer than half the settings in `config-store.ts` have a cached getter, a `…Durable` getter that reads the database, and a setter; the instructions, command policy and egress have only the cached getter, the security posture, sharing posture and approval modes only the `…Durable` one. Organization and scope values are composed by a rule written per setting, some inside the getter (the postures) and some by the caller (`composeSoul` and `composePolicy`, called from `resolve`).
- **Authority, not presence.** `sharingSourcesForTurn` opens sharing only for a turn with `personAuthority`; `changeShares` gates app sharing on `requirePersonAuthority` (which is `carriesPersonAuthority`: the claim set and `botActor` not; a request with no capability token passes), sets `personAuthority: true` for browser callers and, for an agent's token, holds an app share, a public link or an org-wide skill promotion for an approval card (`actionApproved` in `src/api/action-approval.ts`); `capabilityAdminDenied` uses `carriesPersonAuthority`; `selfReadAudience` (`src/auth/self-read-audience.ts`) reads the token's `origin` claim to choose the audience. `personAuthorityTurn` in `src/core/orchestrator.ts` sets the claim: an internal audience, not a bot's work, and either a person speaking, an automation fire whose actor is a person (not a `system:` actor or a swarm), or a session turn delegated from either. The master spec's Background work paragraph gives the rule: a turn acts with the authority of the person whose instructions it carries, and the audience narrows that once, where the token is minted, so a check for person authority needs no separate audience check. Do not reintroduce a presence flag or add a second audience check beside the claim.
- **Transitional: old shapes still read.** `verifySignedPayload` accepts a pre-JWS token format, and the first user migration still imports an older `principal_links` table.
- **Interfaces with one implementation.** `GrantPersistence`, `AdminGrantPersistence`, `UserStore` and `DirectoryStore` each have a single Postgres implementation outside tests (`withSignInMembers` only wraps the last).
- **God file.** `plugins/portal/src/index.ts` holds configuration, every sign-in entrance, proxying and boot checks in one module (God files lens).

## Contracts

| Contract              | Exact form                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Scope id              | `<kind>:<ref>`, split at the first colon. Kinds: `personal`, `channel`, `group`, `team`, `org`, `persona`. A project is `group:web-project-<id>`.                                                                                                                                                                                                                                                                                                               |
| Principal id          | An email (compared lower-cased), a chat-surface user id, `oidc:<sha256 hex of issuer>:<base64url of subject>`, or `system:<name>`. At most 255 characters in a link.                                                                                                                                                                                                                                                                                            |
| Source auth           | Headers `x-timestamp` (Unix seconds) and `x-signature: v0=<hex>`, where hex is HMAC-SHA256 with `CORE_SIGNING_SECRET` over `v0:<timestamp>:<METHOD>\n<path and query>\n<raw body>`. Five-minute window. A non-GET signature is accepted once.                                                                                                                                                                                                                   |
| Portal identity       | Header `x-portal-identity`: a compact JWS (HS256, `PORTAL_IDENTITY_SECRET`) over `{ p, authenticatedAs?, n?, imp?, t?, exp }`, `exp` in epoch milliseconds. `p` is the person, `imp` the admin impersonating them, `t` the tenant.                                                                                                                                                                                                                              |
| Session cookie        | `portal_session` = `<base64url JSON>.<base64url HMAC-SHA256>`. Claims: `k: "session"`, `sub`, `org`, `iat`, `exp` (seconds), optional `auth`, `name`, `appOnly`, `t`.                                                                                                                                                                                                                                                                                           |
| Admin actor header    | `x-admin-actor: <principal>@<ORG_ID>` on source-authenticated admin calls. Core reads it only when the call carries neither a capability token nor `x-portal-identity`; where signed identity is required (always in production), the routes wrapped by `withAdmin` need `x-portal-identity` and this header alone gets a 401. The raw app proxy under `/v1/admin/apps/:id/proxy` is the exception: it authorizes on this header, which its signature covers.   |
| Link API              | `GET /v1/admin/principal-links`; `POST /v1/admin/principal-links` with `{ principalId, canonicalId, evidence }`; `DELETE /v1/admin/principal-links/:principalId`. Org admins only, and never with an agent's token. `GET /v1/principals/:id/canonical` returns `{ principalId, canonicalId, displayName?, storedName? }` to source-authenticated callers.                                                                                                       |
| Trusted issuer config | `PORTAL_TRUSTED_OIDC` is JSON `{ issuer, authEndpoint, tokenEndpoint, userinfoEndpoint, jwksUri, clientId }`. The optional `orgs` claim, read from userinfo and else from the id token, is `[{ id, name }]`.                                                                                                                                                                                                                                                    |
| Trusted assertion     | Body `{ assertion }`: a compact JWS (HS256, `PORTAL_IDENTITY_SECRET`) with `purpose`, `issuer`, `subject`, `org: "org:<ORG_ID>"`, `exp` at most 60 seconds ahead in milliseconds, and a UUID `jti` that is accepted once.                                                                                                                                                                                                                                       |
| Attested actor        | Services configured to receive a person's identity get `x-qm-actor` (the canonical id) and `x-qm-actor-aliases` (a JSON array of that person's other sign-ins). Only ids of 1 to 256 visible ASCII characters are sent; otherwise the call fails with `invalid_actor`. Sent by default only in the person's own personal scope; outside it the refusal is `private_only`. Where it is switched on: [credentials](./credentials.md) and [context](./context.md). |
| Session share links   | `/share/internal/<token>` needs an internal sign-in; `/share/external/<token>` needs none and is forwardable. Files are under `…/files/<fileId>` and resolve only for that snapshot. Limits at creation: 100 attachments, 100 MB of files, 2 MB of text, and fewer than 10,000 deliveries in the conversation.                                                                                                                                                  |
