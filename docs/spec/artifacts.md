# Artifacts: apps, files and sharing

_Verified against `main` at eb148f69d (2026-11-24). Statements were read in the code at that commit unless marked **[interpretation]**._

## In one paragraph

An artifact is a durable thing an agent makes that people keep and share. There are four kinds: published apps, files, skills and crons. This subspec covers apps, files and the sharing all four use; skills are in [context](./context.md) and crons in [background work](./background-work.md). A published app is a directory of files plus a start command. Core keeps the files in a git repository of its own (one per app), records the app in Postgres, and asks the deployment's one _deploy provider_ (the system that runs apps: a Docker host, a cloud microVM service, a sandbox vendor) to start it. Browsers never reach an app directly: every request passes through core, which checks who is asking and then relays it. A file is a Postgres record that points at bytes in object storage or on core's disk. Every artifact has a home scope (a person, a channel, the organization; see [scopes](./scopes.md)) and is private to it until a _grant_ row gives another scope view or manage access. Apps have two wider doors, both off until switched on: a public link and access for outside email addresses.

## One app, traced end to end

Ada, at Acme, is in her web DM. She asks for a small dashboard; the agent writes it into `dash/` in her sandbox and publishes it. She shares it with a channel, her colleague Bo opens it, and she ships a change.

1. **Tool call.** The model calls the `apps` tool with action `publish` (`workspaceTools` in `src/agent/agent-tools/workspace.ts`), passing `dir`, `entrypoint` and `name: "dash"`. The tool calls `publish` on the turn's tool context (`createToolContext` in `src/tools/primitives.ts`).
2. **Collect.** `publish` reads the directory out of the sandbox (`collectTree`: one export call where the sandbox supports it, otherwise file by file) and drops git metadata. It sets the owner to Ada's personal scope and `createdInScope` to the conversation's scope. An app is always born in its publisher's personal scope, whatever the conversation.
3. **Record.** `deployOrUpdate` in `src/deploy/deploy-service.ts` finds no app named `dash`, so it calls `deploy`: check the name and the provider's size limit, copy the files to core's disk under `<DATA_DIR>/deployments/`, then `create` in `src/deploy/deploy-store.ts`, which commits the files to the app's git repository and writes a `deployments` row holding version 1.
   - _Channel instead of DM:_ when the conversation is a channel, `deploy` also writes a view grant for that channel. A DM leaves the app private to Ada.
4. **Place.** `applyVersion` hands version 1 to the provider (`DeployProvider` in `src/deploy/deploy-provider.ts`). The provider puts the files on a machine, runs the entrypoint with `PORT` set, and waits until that port is listening (`waitAppReady` in `src/deploy/shared-deploy-provider.ts`). It returns an _endpoint_: the host and port core should dial, plus any headers core must send. The endpoint is saved on the row and the app is marked `running`.
   - _Two providers:_ `docker` runs a container on core's own host, publishes the port on `127.0.0.1` and mounts the files read-only; nothing the app writes survives a redeploy. `aws` starts a microVM, checks the commit out of a git bundle, can keep `/data` in object storage, and core dials it over TLS with a short-lived token header.
5. **URL.** `appUrlOf` in `src/deploy/deploy-store.ts` picks the first that exists: `https://<handle>-dash.<apps domain>/`, the provider's own public URL, or `<PUBLIC_WEB_URL>/d/dash/`. The tool result gives that URL and says who can open the app.
6. **Share.** Ada picks a channel in the web share dialog, which sends `POST /v1/shares/deploy/dash` (`changeShares` in `src/api/routes/sharing.ts`). Asking the agent instead runs the `apps` tool's `share` action (`controlPlaneTools` in `src/agent/agent-tools/control.ts`). Both end in `shareArtifact` in `src/api/control-service.ts`. It resolves the target (`resolveShareTarget` in `src/api/artifact-share.ts`), checks that Ada manages the app's home and belongs to the channel, and calls `grant` in `src/api/app-sessions.ts`, which writes one `acl_grants` row (Ada's scope, `deployment:<id>`, the channel, `read`) and an audit event.
   - _Cron or webhook turn:_ app sharing is refused with `human_consent_required` unless the turn's token says a live person started it (`personAtKeyboard`). The master spec marks this attended/unattended split as transitional.
   - _Email or public link:_ an email address goes through `inviteToApp` in `src/api/app-published-apps.ts`, a public link through `setAppPublic`. Both need the `external_app_sharing` flag.
7. **Open.** Bo, a member of the channel, opens the URL.
   - _With an apps domain:_ the portal (the sign-in front door, see [web clients](./web-clients.md)) sees a host under the apps domain and forwards the request to core (`proxyToAppHost` in `plugins/portal/src/proxy.ts`). `proxyAppSubdomain` in `src/api/routes/apps.ts` finds the organization from the host label, reads Bo's sign-in cookie (`portalSession` in `src/deploy/viewer-session.ts`) or sends him to sign in, and asks `effectiveAppPermission` in `src/api/app-helpers.ts`, which finds the channel grant and Bo's membership. `reachApp` then asks the provider for a live endpoint, waking or re-placing the app if it is gone, and `proxyReach` relays the request with the provider's headers and a signed `x-portal-identity` header that names Bo to the app. A row goes into `app_page_views`.
   - _Without one:_ Bo opens `/d/dash/` on the web UI's own origin. `proxyApp` runs the same permission check and relay, and adds a sandbox content-security policy, so that app code cannot act as the web UI **[interpretation]**.
   - _Not shared:_ Bo gets a "not shared" page; its button posts to `/__claw__/request-access`, which sends Ada a message.
   - _Ada herself:_ on an app host, someone who can manage the app gets the _app shell_ (`appShellHtml` in `src/deploy/app-shell.ts`): the app in a frame under a bar with the access control and a chat for editing it.
8. **New version.** Ada asks for a change and the agent publishes `dash` again. `deployOrUpdate` finds the app and calls `redeploy`: `addVersion` commits version 2, the provider replaces the running copy, and the row moves to version 2. Access does not change. `rollbackTo: 1` places version 1 again.
   - _Live edit (only `aws`):_ when only files changed, `save` in `src/deploy/live-edits.ts` writes the changed files into the running app and records a _draft_ instead. A timer turns the draft into version 2 two minutes after the last edit.
   - _Other ways in:_ a `git push` to the app's remote (`serveAppGit`, then `pushGit`) and the `app_files` tool in the chat beside the app (`editSource`) end in the same two paths.
   - _Many organizations:_ in a [Multi-tenant deployment](../SPEC.md#deployment-shapes) each step runs inside one tenant. `deployments` rows carry `tenant_id`, names are unique per tenant, and the host label starts with the organization's app handle, so two organizations can each have a `dash`. The provider, the apps domain and the sign-in secret are shared by every tenant.

## The parts

### `src/deploy/deploy-service.ts` and `deploy-store.ts` — an app's life

**Job.** Create, update, roll back, rename, archive, restore, move and share apps; keep them warm; decide who may manage one.

**Key idea.** One JSON row per app holds everything. Every change to an app runs under `withDeployLock`, an in-process queue plus a Postgres advisory lock, so several core instances cannot place the same app at once. Three timers in `src/wiring.ts` do the background work, each under a leader lease (one core instance at a time) and each walking every tenant: keep-warm and machine rotation every five minutes, live-edit publishing every ten seconds, and the idle reaper when configured.

**Surprising.** (1) The row is written before the provider runs, so a first publish that fails still leaves the app, with status `stopped` and its name taken; the retry is a redeploy. (2) `stopped` is not sleep. `reachApp` answers `not_found` for any app that is not `running`. An app is `stopped` after the idle reaper destroys it, and only a publish or rollback makes it `running` again. Apps the provider puts to sleep stay `running` in the row. (3) `reachAllowed` in this file is not the access check: every production caller passes `bypassAcl` after deciding in `src/api/app-helpers.ts`. (4) A connector loan is withdrawn when someone other than the publisher changes the running version, or when the app leaves the publisher's personal scope.

### `src/deploy/deploy-git-store.ts` and `live-edits.ts` — source and edits

**Job.** Keep each app's source history; apply small edits to a running app.

**Key idea.** One bare git repository per app, driven by spawning `git`. The copy on core's disk is a cache. The durable copy is a `git bundle` of the whole repository in `deploy_git_repos`: base64 in the row, or an object-storage key when bytes go to object storage. `refs/heads/current` is the commit that is placed.

**Surprising.** Every commit and every ref change bundles and stores the whole repository again. Symlinks and submodules are refused. A live edit runs `npm install` and `npm run dev` when `package.json` has a `dev` script, and the published entrypoint returns when the draft becomes a version.

### `src/deploy/*-deploy-provider.ts` — where apps run

**Job.** Implement `DeployProvider`. `apply` and `destroy` are required; `resolveEndpoint`, `logs`, `setAlwaysOn`, `reconcile`, `liveEdit`, `rotationDue` and `park` are optional.

**Key idea.** Core builds exactly one provider at boot (`buildDeployProvider` in `src/wiring.ts`). Each declares a `profile`: whether the platform itself sleeps idle apps (`managedScaleToZero`), the directory that survives redeploys (`dataDir`), and a size limit (`maxAppBytes`).

| Provider | Runs each app as                                                                                                                        | Core dials                                                       | Sleeps idle apps itself | Durable `$DATA_DIR`                   | Size limit      |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- | ----------------------- | ------------------------------------- | --------------- |
| `docker` | container on core's host, files read-only at `/app`                                                                                     | `127.0.0.1:<port>`                                               | no                      | none                                  | none            |
| `aws`    | microVM, replaced about every 7.5 hours                                                                                                 | HTTPS with a token header                                        | yes                     | `/data` when a data bucket resolves   | 100 MiB         |
| `fly`    | Machine in its own Fly app, or in one shared Fly app                                                                                    | private Flycast address, optionally through a local SOCKS tunnel | shared-app mode only    | `/data` when a volume size is set     | 20 MB of source |
| `porter` | sandbox on the cluster with a volume                                                                                                    | in-cluster address, or the cluster's ingress host                | no                      | `/data`                               | none            |
| `e2b`    | sandbox that pauses when idle and resumes on traffic                                                                                    | HTTPS with a traffic token header                                | yes                     | `/home/user/data`, inside the sandbox | none            |
| `render` | web service built from the QM source at the running commit, in its own isolated environment; it fetches the app over the app git remote | HTTPS with a rotating token header                               | no                      | `/data` disk                          | none            |

**Surprising.** `reconcile`, `liveEdit`, `rotationDue` and `park` exist only on `aws`, so live edits and git-bundle checkouts are an AWS-only path. On `aws`, `/data` is saved as one tar file, at most every five minutes while the app is being reached and again at rotation, and a tar over 180 MiB is skipped. Only a SQLite file at `/data/app.db` can be replicated continuously, and only when a data role is set. The `docker` provider keeps its host-port table in process memory. The `fly` private tunnel refuses to start unless core runs as a Fargate task: it reads ECS task metadata to claim a WireGuard peer (`src/deploy/fly-tunnel-manager.ts`), and shared-app mode requires the tunnel. With Porter ingress set to `public`, the URL QM hands out is the ingress host, which skips core's gate.

### `src/api/routes/apps.ts` — the app gateway

**Job.** All HTTP for apps: the `/v1/apps` routes, the two proxies (`/d/<app>/` and app hosts), the git remote, an admin proxy.

**Key idea.** `proxyReach` is the one relay: HTTP/1.1 or HTTP/2 upstream, optional SOCKS, streaming both ways, a "Starting up" page while a cold app wakes, and a short shield after the upstream answers 429. `proxyAppSubdomain` is the gate in front of it for app hosts.

**Surprising.** WebSocket upgrades are relayed for app hosts only (`upgradeFront` in `src/api/server.ts`), never under `/d/<app>/`. The gate refuses cross-origin writes, strips the portal's cookies in both directions, and answers a manager's top-level page load with the app shell rather than the app (`?__qm_no_shell=1` skips it). Signed-in viewing inside another site's frame works only for origins in the app's `embedAncestors` list: only then does the gate read the frame session cookie and send a `frame-ancestors` policy. A document request to `/d/<app>/` redirects to the app's own host when one exists.

### Sharing — `src/api/artifact-share.ts`, `src/api/routes/sharing.ts`, `shareArtifact`

**Job.** One share operation and one share dialog for the four types.

**Key idea.** A share is a grant keyed by owner scope, artifact ref and grantee scope. Refs are the bare id for a file, and `skill:<id>`, `deployment:<id>`, `cron:<id>` otherwise (`src/acl/resource-ref.ts`). `shareOffers` tells the dialog which options a type has.

**Surprising.** The types diverge inside the one function. A personal cron shared with a person becomes a linked copy, not a grant. A skill shared with the org is promoted, which only an org admin can do. Moving an artifact to another home exists for apps and skills only. Email invites and the public link exist for apps only, and only while the app sits in the caller's own personal scope (`assertAppOwner`). People outside the directory can view, never manage. The small app helpers are in `src/deploy`: `app-access.ts` (the access label), `email-access.ts`, `share-notice.ts` (the message to a person who gains access), `access-token.ts` (git and viewer tokens), `app-credentials.ts`.

### `src/files` — file artifacts

**Job.** Store the files people and agents exchange and serve them back (`src/api/routes/file-content.ts`).

**Key idea.** A `file_artifacts` row plus bytes in a `DurableByteStore`. Bytes are addressed by content hash (`files/<sha256>`), so identical bytes are stored once; a multipart upload is keyed by its upload id instead.

**Surprising.** (1) The agent's `files` tool reads and writes the sandbox workspace; `write` does not create a file artifact. Artifacts are created when an attachment enters or leaves a turn (`src/core/attachments.ts`), by a web upload, by an admin upload, or by the multipart upload under Contracts. (2) Owner and audience differ by route. An attachment belongs to the person; in a public channel it is granted to the whole organization, in a private channel to each current member, in a group chat to the group (`createFileRegistration` in `src/core/orchestrator/turn-tools.ts`). A web upload belongs to the person, with a grant to the conversation's scope. A multipart upload belongs to the conversation's scope itself. (3) A file is immutable. There are no versions; a changed file is a new record. Deleting leaves a tombstone so a retried upload cannot bring it back. (4) The Files list shows one row per distinct content per conversation. (5) File content is served under a sandbox policy, except PDFs.

### `src/search`, `src/api/app-search.ts`, `src/api/app-resource-search.ts` — two searches

**Job.** `POST /v1/search` lets an agent search conversations, files and mirrored Slack messages (see [surfaces](./surfaces.md)). `GET /v1/resources/search` lets the web UI find skills, crons, apps, webhooks and contexts by name.

**Key idea.** The agent search returns a hit only if every person in the conversation could see it; each backend enforces that itself, the conversation backend through `createIntersectionBackend`. The resource search is a Postgres full-text query per table, filtered afterwards by each type's own visibility rule.

**Surprising.** The two share nothing but the directory. File search reads file bytes at query time, and only for text-like types.

### Agent tools and the edit chat

**Job.** `apps` (`publish`, `share`), `files` (`read`, `write`, `share`) and `app_files` (`list`, `read`, `edit`, `write`, `delete`), assembled in `src/agent/agent-tools.ts`.

**Key idea.** `app_files` (`src/agent/agent-tools/app-files.ts` over `src/tools/app-files.ts`) edits the app's saved source held by core, never a sandbox. It exists only in the chat beside an app, a web conversation whose thread ref is `web:<person>:app-edit:<app>`.

**Surprising.** That chat is a stripped turn. `appEditTurnPolicy` in `src/core/orchestrator/app-edit.ts` swaps the prompt frame, the turn recalls no memory and loads no connector tools, and at most six tools remain. `appSourceShown` in `src/core/orchestrator/app-source.ts` pastes the app's files, or only the files changed since they were last shown, into the prompt inside a token budget.

### Small pieces

`src/playgrounds/playground.ts` stores an HTML file artifact and `GET /v1/playgrounds/:id` serves it under a no-network policy; the tool-context method `createPlayground` has no caller. `src/api/routes/blobs.ts` stages bytes in transit between sandboxes, browsers and core; staged blobs are temporary and are not artifacts (see [storage](./storage.md)). `src/api/routes/pins.ts` is the agent's API for pinning notes in a conversation; pins are session data (see [turns](./turns.md)). `src/api/app-published-apps.ts` passes app calls from the API's `App` object through to the deploy service and adds invite emails and git URLs. `src/api/routes/app-sharing.ts` holds the one route that lends connectors, and `app-paths.ts` tells the router how to find the tenant for `/d/` and git URLs. `src/api/routes/admin/artifacts.ts` and `admin/files.ts` list any scope's apps, crons, skills and files for an admin; `admin/app-handle.ts` sets the app handle. `src/deploy/page-views.ts` logs page views and drops them when its write backlog is full.

Two settings only tune: `DEPLOY_GIT_DIR` (default `<DATA_DIR>/deploy-git`) and `DEPLOY_DIAL_TIMEOUT_MS` (default 20 seconds).

## Where the complexity lives

**Things that multiply each other.** Six providers × seven optional methods × three profile fields. `deploy-service.ts` and `live-edits.ts` branch on whether each method exists, so publish, edit, wake and idle behave differently per provider. The master's Wall of shame records this area under three lenses: Config-matrix expansion (another deploy provider added), God files (the AWS provider absorbing unrelated duties) and Prod-like QA (two changes to app serving merged without a real run on the provider they affect). App addresses multiply too: three URL forms × two gates (`proxyApp`, `proxyAppSubdomain`) × public, signed-in and app-only viewers.

**Parallel mechanisms doing one job.**

| Job                                        | Mechanisms                                                                                                                                                                                                                                                                              |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| "May this person open or manage this app?" | `effectiveAppPermission` and `appPermission` in `src/api/app-helpers.ts`; `canManage` and `reachAllowed` in `src/deploy/deploy-service.ts`. The first decides for the proxies, the second for listings and git, the third for publish and edit; the fourth never decides in production. |
| Write an app grant                         | `grant` in `src/api/app-sessions.ts`, used by `shareArtifact`; `shareApp` in `deploy-service.ts`, reached only through `inviteToApp`.                                                                                                                                                   |
| Change a running app                       | Publish from a sandbox, git push, `app_files`, and the `POST /v1/apps/:id/redeploy` route. Each ends in a new version or a live-edit draft.                                                                                                                                             |
| Name the apps domain                       | Two fields of `DeploySettings`: `deployAppsDomain` feeds the portal, the web shell and the boot DNS probe; `awsDeploy.appsDomain` feeds the gate, the deploy service and page views. They differ when only `PORTER_DEPLOY_APPS_DOMAIN` is set under `porter`.                           |
| Put bytes into Files                       | Attachment registration, web upload through a staged blob, admin upload, multipart upload.                                                                                                                                                                                              |

**Abstractions with one implementation.** `DeployStore`, `DeployGitStore`, `FileArtifactStore`, `FileUploadStore`, `AppPageViewLog` and `ResourceSearchStore` each have one Postgres-backed implementation. `createMemoryDurableByteStore` has no production caller.

**Transitional code still present.** Provider-neutral settings keep AWS names (`AWS_DEPLOY_GATE_SECRET`, `awsDeploy.appsDomain`). `migrateArchive` moves base64 bundles to object storage one app at a time, as each is touched. `qm_tenant_for_app_host` falls back to routing a host that carries only an app name. `personAtKeyboard` gates app sharing.

**How far each type is from the master's goal** (shareable in one familiar dialog, versioned, tracked in Postgres or object storage):

## Contracts

**What a published app may rely on.** The entrypoint runs from the app's root directory. The app must listen on `PORT`. Env vars passed to `publish` are set; a publish that names env vars replaces them all, and one that does not keeps the previous ones. `DATA_DIR` is set when the provider has a durable directory; nothing else on disk survives a redeploy. Where app identity is configured, each relayed request from a signed-in viewer carries `x-portal-identity`, verifiable with `VIEWER_IDENTITY_KEY`. The headers core uses for its own authentication are not forwarded.

**App failure records.** A published app's failures become operator error records in its owner's scope, category `deploy`, through `appReporter` in `src/deploy/shared-deploy-provider.ts`: `app_start_failed` (the version never listened on its port, its entrypoint exited, or it answered 5xx on `/` for the whole readiness window), `app_restarted` (the app exited and was restarted since the last check) and `app_down` (the app stopped and nothing restarted it). Each carries up to 4,000 bytes of the app's recent output, with the version's env values and known secret patterns masked. The probes are shell run beside the app, so the app image must provide `sh`; they read the HTTP status with `curl`, else `wget`, and with neither, listening on the port alone counts as ready.

**Apps export.** With `SPEND_EXPORT_TOKEN` set, `GET /v1/apps/export?principalId=<id>` accepts `Authorization: Bearer <token>` and lists the apps that person can see. Each call is audited as `app.export`.

**The app git remote.** `GET /v1/apps/:id/git-url` (agent token only) returns the URL `<api base>/v1/apps/<id>/git` with user `app` and a token as the password, valid for one hour, read or write according to the caller's permission. It speaks git smart HTTP: `info/refs`, `git-upload-pack`, `git-receive-pack`. A push that moves `refs/heads/current` becomes a version or a live-edit draft. Core re-checks the token holder's access on every request.

**Multipart file upload** (object storage only; `src/files/direct-file-upload.ts`, routes in `src/api/routes/file-uploads.ts`). Bytes go from the client straight to object storage; core authorizes each part and publishes the file after verifying the stored object.

| Method | Endpoint                              | Meaning                                                                                                   |
| ------ | ------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| GET    | `/v1/files/upload-client`             | A Python helper that implements this protocol with curl, resumes, and prints the file and its content URL |
| POST   | `/v1/files/uploads`                   | Begin: `name`, `sizeBytes`, ordered `checksums`, optional `mimetype`, `scopeId`, `requestId`              |
| GET    | `/v1/files/uploads`                   | The caller's unfinished sessions in this scope; `elsewhere` counts the rest                               |
| GET    | `/v1/files/uploads/:id`               | One session's state                                                                                       |
| POST   | `/v1/files/uploads/:id/parts/:number` | A signed PUT URL and the headers to send with it                                                          |
| POST   | `/v1/files/uploads/:id/complete`      | Verify the parts and publish the file                                                                     |
| DELETE | `/v1/files/uploads/:id`               | Abort, allowed until completion starts                                                                    |

- Parts are 64 MiB. `checksums` holds one base64 SHA-256 per part; an empty file has one empty part. `requestId` is 32 lowercase hex characters and makes a repeated begin return the same session; reuse with a different manifest is refused.
- Limits: 100 GiB per file; four unfinished uploads and 500 GiB of declared bytes per person, refused with 429 `upload_quota` and the list of unfinished sessions. A session lasts 24 hours and a signed URL at most 15 minutes.
- Completion trusts the part sizes, checksums and ETags the store reports, not the client. Once it has started, retry it rather than abort; core can finish it after a lost response. A timer runs each minute, aborts expired sessions, and aborts stray multipart uploads older than a day under the uploads prefix.
- The published file has `sha256: null`: the store's composite checksum is not a hash of the whole file. The file belongs to the scope it was uploaded in; an agent token cannot upload into, or list the sessions of, another scope.
- Core's storage role needs `s3:GetObject`, `s3:PutObject`, `s3:AbortMultipartUpload` and `s3:ListMultipartUploadParts` on the files prefix, and `s3:ListBucket` and `s3:ListBucketMultipartUploads` on the bucket; the template in `cli/templates/aws/main.tf` grants them. The uploading machine needs HTTPS to the store and no credentials of its own.
- Other uploads (attachments, the web uploader) pass through core and are capped at 1 GB each.
